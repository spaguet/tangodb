# Персональные тарифы: длительность, пересчёт, раздельные платежи

Статус: **этап 1 реализован** (`2.8.0`, Промпты 0–9). Этапы 2–3 — в очереди.  
Дата: 2026-08-15.  
Редакция: 2026-08-16 (повторная проверка vs CRM `2.7.26` / миграция `20260916000001`: пакет+автопересчёт, сторно копирует снимок, restate→касса, архивный тариф, выручка после DELETE прайса).  
Текущая CRM на дату ревью: `2.7.26`. Последняя миграция: `20260916000001_restate_personal_lesson_amount.sql`.  
Контур: персональные уроки, прайс, дебиторка, журнал платежей, финансовая выручка.  
Конфликтов со схемой нет: все новые колонки nullable, `payments.price_id` сейчас **нет** (у разовых визитов `price_id` живёт в `single_visits`, не в `payments`). Можно приступать: **Промпт 0** → Промпты 1–9 этапа 1.

Документ фиксирует, **почему ручной коэффициент — плохая основа**, и как сделать предсказуемую модель: тариф знает свою длительность, сумма считается из факта урока, долг висит на конкретном плательщике.

---

## 0. Зачем этот документ

Сейчас система умеет:

- тариф персонального урока = **сумма без длительности** (`prices.price`, `category = private`, `lessons = 1`);
- длительность урока = `time_end − time_start`, но **не участвует в цене**;
- одно начисление на урок (`personal_lessons.price` / `paid_amount`); продажа пишет `parseFloat(customPrice)` — поле **редактируемое**, не обязательно `tariff.price`;
- RPC оплаты всегда пишет платёж на `client_id1` (хук принимает `clientId` / `clientDisplay`, но в RPC не передаёт — popup всегда шлёт `lesson.clientId1`);
- **два overload RPC** после миграции 780: UI шлёт `p_venue_rule_acknowledged` → сигнатура 5 параметров (wrapper из 530) → `_record_personal_lesson_payment_before_venue_rules` **без** логики partial/top-up из 780; сигнатура 4 параметров (780) с partial payments **не** получает venue ack;
- на уроке нет `price_id` — только `price`; пересчёт billed при смене времени до оплаты в to-be неоткуда взять тариф;
- фильтр тарифов: `filterTariffsForSale` умеет `teacherMemberId`, но обёртка `filterPrivateLessonTariffsForSale` в типе его **не принимает**; `PersonalLessonSaleForm` хранит педагога, в обёртку не передаёт (только площадка + дисциплина). У `PayPersonalLessonTarget` нет `teacherMemberId` / `clientId4` / `payerClientId` / `priceId`; `paidAmount` уже опционален — **финансы** (`2.7.25+`) его передают вместе с `price = billedAmount`, **расписание** (`ScheduleDebtorsBlock`) — нет. `DebtorEntry` и `ScheduleDebtorEntry` педагога **уже имеют** (`teacher_member_id` с `20260914000001`) — в target оплаты не прокидывают;
- в **финансовой** дебиторке pair/trio/quad: одна строка «Иванов & Петров» (`financial_debtors_v` concat только `client_id1…3`, `client_id4` **не входит**). На расписании `clientDisplay` урока **включает** четвёртого (`buildClientDisplay`). `openPersonalPayment` требует `clientId1` и не знает плательщика;
- popup оплаты подбирает тариф как `find(t => t.price === lesson.price)` — после длительности два тарифа с одной ценой разъедутся. Клик «разовый» вызывает `applyLessonTariff` и **перебивает сумму `tariff.price`**, даже если в поле уже был остаток долга.

Из этого следуют ошибки, которые нельзя лечить чекбоксом «увеличить тариф в N»:

1. Оператор забывает коэффициент → час с четвертью продаётся как 45 минут.
2. Тариф «300 за 45 мин» нигде не записан — через год нельзя объяснить, почему платёж 600.
3. Двое на уроке, платит один — долг числится «за обоими».
4. Отчёт «продажи по тарифам» не из чего собрать: у платежа нет `price_id`.

Цель модели: **минимум ручных коэффициентов, максимум выводимых величин**. Ручная сумма остаётся только как явный режим «оплата текущей суммы / договорная цена».

Состав урока: solo / pair / trio / **quad** (`client_id1`…`client_id4`). Везде ниже «pair+» = 2…4 клиента.

## 2. Целевые принципы (to-be)

1. **Тариф персонального урока имеет длительность**, которую задаёт пользователь при создании (45 / 60 / 90 минут и т.д.). Цена тарифа — за этот квант, не «за любую запись».
2. **Стоимость урока по тарифу считается автоматически** из длительности записи и длительности тарифа. Оператор не вводит коэффициент как основной сценарий.
3. **Начисление появляется в момент продажи/записи**, а не только в кассе. Неоплаченный 90-мин урок с тарифом 45/300 сразу должен висеть как 600.
4. **Несовпадение длительностей — предупреждение, не молчаливая ошибка.** Можно продолжить (сумма уже пересчитана) или сменить тариф / время.
5. **Участник ≠ плательщик.** На уроке могут быть двое; долг и платежи ведутся **по клиенту**. Если платит один — второй в дебиторке не фигурирует.
6. **Снимок на платеже.** В журнале видно: какой тариф, сколько единиц, какая длительность урока. Старые платежи без тарифа = «без тарифа».
7. **Ручная сумма — отдельный режим**, без тарифа. Не маскировать её под «тариф × коэффициент».
8. **Переоценка долга** (`restate_…`) и **оплата** — разные действия. Тариф не должен тихо перебивать ручную переоценку: после restate `price_id` обнуляется, автопересчёт по слоту выключается.

### Инварианты реализации (не нарушать)

1. **Billed = multiply-first**, не `price × (minutes/duration)` в IEEE `number`. Иначе тот же баг 399.99, от которого уходим в §3.2.
2. **Не восстанавливать billed из `units_snap`.** Снимок единиц — только UI/журнал.
3. **Не суммировать `tariff_units` по платежам.** Топ-ап 400+200 пишет два раза `×2`; сумма единиц ≠ «продано уроков». Выручка = нетто-операции и нетто-сумма.
4. **Автопересчёт billed только если `price_id` задан, платежей нет и урок не пакетный** (`subscription_id IS NULL`). Эвристика `price === tariff.price` запрещена: после restate в 300 при тарифе 300 она откатит ручную цену. Пакет (`subscription_id` задан, `price = 0`) **не должен иметь `price_id`** — иначе смена слота пересчитает 0 → 400/600 и снимет `paid = yes`.
5. **`personal_lesson_charge_id` не в этапе 1.** Колонку и `p_charge_id` не добавлять, пока нет таблицы charges. NOT NULL — только для новых платежей после этапа 2.
6. **`tariff_units` без DEFAULT 1.** Новые outstanding: `price_id` и `tariff_units` оба NULL. `×1` в UI не показывать, если тарифа нет.
7. **Сторно и корректировка копируют снимок тарифа.** `_storno_payment_impl` и `correct_payment` сейчас INSERT с явным списком колонок — без `price_id` / `tariff_*` / `lesson_duration_minutes` сторно уйдёт в «без тарифа» и сломает S10 / S19. Копировать с исходного платежа.
8. **Кап остатком — в RPC для всех вызовов**, не только в UI. Скрипты/импорт, которые сейчас могут провести `amount > remaining`, после этапа 1 получат ошибку. Уже существующая переплата (`paid_amount > price`) не пересчитывается; новый платёж на такой урок → `already_fully_paid`.

## 3. Логика пересчёта

### 3.1. Длительность урока

На записи урока **не дублировать** минуты отдельной колонкой — считать из слота:

```
lesson_minutes = timeToMinutes(time_end) − timeToMinutes(time_start)
```

Ограничения (уже есть в `validateTimeRange`): конец позже начала, без перехода через полночь. Если минут ≤ 0 — тарифицировать нельзя.

На **платеже** хранить снимок `lesson_duration_minutes`: урок могут удалить, журнал не должен потерять длительность.

Формат для UI — **через i18n** (`durationParts` + ключи), не хардкод «ч.» / «мин.» в JSX и не в `personalTariffPricing.ts`. Примеры готовых строк (ru):

- ровно N часов, 0 минут: `1ч.` / `2ч.`
- меньше часа: `45 мин.`
- часы + минуты: `1ч. 30мин.`

Дефолт нового слота (as-is): при открытии ячейки всегда **+60 мин** (`computeAutoTimeEnd(..., [])`, потолок 23:45). Обрезка до старта следующего урока **той же площадки** — только если оператор меняет начало (`handleTimeStartChange` передаёт `sameDayLessons`). Если основной тариф студии 45 мин, warn «длиннее тарифа» на создании из ячейки на 60 мин — **типичный** случай, не баг. Не подгонять автоматически конец слота под тариф в v1 (это ломает сетку расписания).

Серия «повторять еженедельно»: **каждая** созданная запись получает свой `price_id` и billed из длительности **этого** слота (обычно одинаковые). Не одну сумму на всю серию.

### 3.2. Единицы тарифа и сумма (источник истины)

**Нельзя** считать сумму как `round(price × units_4dp, 2)`: `60/45` в 4 знаках = `1.3333`, `1.3333 × 300 = 399.99`, а не 400.

Тот же капкан — **делить минуты первыми** в IEEE `number`: `300 × (60/45)` даёт `399.999…`. Формула «через units_exact, потом × price» в JS **запрещена**, даже если units не округлять до 4 знаков.

Источник истины — **минуты, умножение первым**, деньги как numeric / целые копейки:

```
billed     = round_half_up( (tariff.price × lesson_minutes) / tariff.duration_minutes , 2)
units_exact = lesson_minutes / tariff.duration_minutes          -- только для UI
units_snap = round_half_up(units_exact, 4)                     -- только снимок/журнал
```

**Legacy:** если `duration_minutes IS NULL` — `billed = tariff.price` без пересчёта по слоту; `units_exact` / `units_snap` не писать (warn §3.4 приоритет 1).

- SQL: `ROUND(price * lesson_minutes / duration_minutes, 2)` на `numeric`, не `float8`.
- JS: считать в **копейках** (`price_cents * lesson_minutes / duration_minutes`, затем half-up до целых копеек). Не копировать `Math.round(x * 100) / 100` из `rentalBillingProfile` на промежуточное `price * (a/b)`.
- `round_half_up` — как `ROUND(numeric, 2)` в PostgreSQL (половину от нуля вверх по модулю). Одна функция в `personalTariffPricing.ts` и тот же ROUND в SQL.
- **Никогда** не восстанавливать billed из `units_snap` или из `units_exact`.

Примеры (цена тарифа 300):

| Тариф | Урок | units_exact | units_snap | billed |
|---|---|---|---|---|
| 45 мин | 45 мин | 1 | 1.0000 | 300.00 |
| 45 мин | 90 мин | 2 | 2.0000 | 600.00 |
| 45 мин | 60 мин | 1.333… | 1.3333 | **400.00** (не 399.99) |
| 60 мин | 90 мин | 1.5 | 1.5000 | 450.00 |
| 60 мин | 45 мин | 0.75 | 0.7500 | 225.00 |

Квантование «только целыми уроками» (60 мин от 45 мин запретить) **не делать в v1**: студии режут 60/75/80 минут. Вместо запрета — предупреждение, если `lesson_minutes % tariff.duration_minutes ≠ 0`.

### 3.3. Когда пересчитывать billed

Пересчёт **начисления** (`personal_lessons.price` или сумма charge):

| Событие | Пересчёт |
|---|---|
| Выбор тарифа в **продаже** / создание неоплаченного урока | Да: сразу писать `price_id` + billed |
| Смена `time_start` / `time_end`, `price_id` задан, **платежей нет**, не пакет | Да |
| Смена времени, `price_id IS NULL` (restate / legacy / тариф удалили) | **Нет** — billed уже зафиксирован |
| Смена времени, платежи уже есть | **Нет** (S6): warn в edit-popup |
| Смена времени, пакет (`subscription_id` задан) | **Нет** — `price` остаётся 0, `price_id` не ставить |
| Первая оплата по тарифу, у урока уже есть `price_id` | **Нет** — платить остаток |
| Первая оплата по тарифу, `price_id IS NULL` (legacy **или после restate без платежей**), оператор **выбрал тариф в popup** | Да: записать `price_id` + billed, затем платёж. Это **явный** возврат к тарифной модели (S5c), не тихий автопересчёт слота |
| `price_id IS NULL` и платежи уже есть (restate после частичной оплаты) | **Нет** пересчёта; режим A недоступен, только B |
| Смена тарифа в popup, платежей нет | Да: новый `price_id` + billed |
| Смена тарифа в popup, платежи уже есть | **Нет** — lock на `price_id` урока |
| Топ-ап / повторная оплата по тарифу | **Нет** — только платёж, сумма = остаток |
| Режим «оплата текущей суммы» | Нет |
| `restate_personal_lesson_amount` | Нет автопересчёта; **обнулить `price_id`** (явный режим без тарифа) |

Не использовать `price === tariff.price` как признак «ещё не пересчитали»: 45-мин урок с T45 легитимно равен цене тарифа; restate в ту же сумму откатится. После этапа 1 продажа всегда пишет `price_id`; legacy без `price_id` пересчитывается только когда оператор явно выбрал тариф в кассе.

As-is сегодня можно выбрать в popup тариф на 600, заплатить 600, а `personal_lessons.price` оставить 300. Поэтому billed пишется при продаже, а касса не перебивает начисление, если `price_id` уже есть.

### 3.4. Предупреждения о длительности

Уровень **warn** (можно продолжить), не hard-block. Не стопкать три баннера: одно сообщение по приоритету.

| Приоритет | Условие | Смысл |
|---|---|---|
| 1 | Тариф без длительности (legacy) | Цена как за один урок, независимо от времени. Рекомендуется указать длительность в прайсе. |
| 2 | `lesson_minutes < duration` | Урок короче тарифа. Сумма меньше цены тарифа. |
| 3 | `lesson_minutes > duration` и не кратно | Длиннее и не кратно (60 при тарифе 45). Сумма пересчитана, проверьте. |
| 4 | `lesson_minutes > duration` и кратно | Длиннее, N квантов (90 = 2 × 45). |

Приоритеты 2–4 покрывают все реальные случаи. Случай «равно и не кратно» невозможен — не кодировать отдельным приоритетом.

Hard-block: нет длительности урока; тариф не найден; `duration_minutes` тарифа ≤ 0; `lesson_minutes ≤ 0`; `billed < 0`; в режиме **«оплата по тарифу»** `billed ≤ 0` (кассой по тарифу закрывать нечего). Пакет и промо `price = 0` идут **другими** путями, не этим режимом; режим «текущая сумма» — отдельно, с `amount > 0`. RPC по-прежнему требует `amount > 0`.

Показ: баннер в popup оплаты и при создании записи, если тариф уже выбран.

### 3.5. Почему не делать чекбокс «коэффициент» основой

| Ручной коэффициент | Длительность на тарифе |
|---|---|
| Оператор должен вспомнить 1.5 | Система считает 90/60 сама |
| Нельзя аудировать «за что 1.5» | Есть `duration_minutes` тарифа + факт слота |
| Легко забыть чекбокс | Пересчёт по умолчанию |
| Отчёт по тарифам врёт | `price_id` + `units_snap` на платеже |

Допускается **скрытое** поле единиц в UI (read-only: «2 × 45 мин») и ручная сумма только в режиме без тарифа.

## 4. Раздельный платёж и дебиторка

### 4.1. Проблема

Урок pair: клиенты A и B, цена 600. Платит только A.

Сейчас: платёж 600 на A (`client_id1`), в дебиторке строка «A & B», долг 0. Либо платит 300 — долг 300 висит на «A & B», хотя B ничего не должен.

Нужно: долг только у того, на кого повесили начисление.

### 4.2. Модель charge (этап 2, не v1)

Одна запись урока, **несколько начислений**:

```
personal_lesson_charges
  id
  organization_id
  personal_lesson_id
  client_id              -- должник; должен быть участником урока
  billed_amount          -- доля этого клиента
  -- paid_amount не хранить: считать из payments
  created_at
  UNIQUE (organization_id, id)
  UNIQUE (organization_id, personal_lesson_id, client_id)
```

Платёж (поля появляются поэтапно, см. §6.1):

```
payments.personal_lesson_id
payments.client_id                    -- уже есть
payments.personal_lesson_charge_id    -- NULL до этапа 2; NOT NULL только для новых строк после этапа 2
payments.price_id                     -- nullable: тариф или «без тарифа»
payments.tariff_duration_minutes      -- снимок, nullable
payments.tariff_units                 -- numeric(12,4), снимок; NULL если без тарифа; без DEFAULT
payments.tariff_price                 -- снимок цены кванта тарифа (nullable)
payments.tariff_label                 -- снимок названия тарифа (nullable; для журнала после DELETE прайса)
payments.lesson_duration_minutes      -- снимок минут слота
```

Для «без тарифа» **не** писать `tariff_units = 1` как будто это квант: в UI «без тарифа», без «×1». Колонка **без DEFAULT**: INSERT без поля иначе молча запишет 1 и сломает отчёт. Новые outstanding: `price_id` и `tariff_units` оба NULL. Если в данных встретится `units = 1` без `price_id` — всё равно «без тарифа».

Долг клиента по уроку:

```
charge.billed_amount − SUM(active payments on this charge)
```

Активные = нетто с учётом сторно (`operation_kind`), как сейчас `personal_lesson_net_payment`.

Дебиторка: **одна строка на unpaid charge**, не на урок.  
`client_display` = имя **должника**. В деталях: «персональный, с Петровым» (остальные участники справочно). Для quad перечислить остальных.

Статус урока `paid`:

- `yes`, если сумма оплат по всем charge ≥ сумма billed всех charge;
- иначе `no`.

`personal_lessons.price` оставить как **сумму billed всех charge** (денормализация для старых отчётов), синхронизировать RPC. Не использовать как единственный источник долга.

**Тариф считает урок, split только режет.** Оплата по тарифу не пересчитывает «долю A» отдельно — иначе A+B разъедутся с длительностью.

### 4.3. Политика «кто платит» при создании урока

Поле на форме записи (обязательное при 2+ клиентах):

| Режим | Поведение |
|---|---|
| **Один плательщик** (дефолт этапа 1) | 100% billed на выбранного клиента. Остальные — только участники. |
| **Поровну** (этап 2) | `splitBilledEqually`: `round_half_up(billed/n, 2)`, остаток копеек **на первого выбранного плательщика**. |
| **Вручную** (этап 2, если понадобится) | Оператор вводит доли; сумма долей = billed урока. |

Для solo: всегда один charge на единственного клиента. UI режима скрыт.

«Оплачивает один» ≠ скрыть второго из карточки урока. Второй остаётся в расписании, посещаемости, Google Calendar.

### 4.4. Три денежных действия (не путать)

Уже в продукте намечены **две кнопки оплаты** в дебиторке плюс отдельно «изменить сумму». Их и фиксируем.

**A. Оплата по тарифу** (касса)

- Плательщик (select, если 2+ участников / несколько charge).
- Тариф: показывать из `price_id` урока, если задан (**не** подбирать по `price === lesson.price`). Если строка прайса **архивная** — всё равно показать её (lock / read-only), не искать замену в `usePrices` (там только `active`). **Lock смены тарифа** — только если по уроку уже есть платежи (§3.3, S10c); `price_id` без платежей (продажа ещё не оплачена) — тариф можно сменить. Если `price_id` нет и платежей нет — оператор выбирает тариф, billed пишется по §3.2 (в т.ч. явный возврат после restate, S5c). Если `price_id` нет и платежи есть — режим A **скрыть**, только B.
- Поле суммы **заблокировано** = **остаток долга** после синхрона начисления (не всегда полный billed: топ-ап платит остаток).
- Длительность + warn.
- Способ оплаты. Пакета нет.
- Пишет `price_id`, `tariff_units` (`units_snap`), `tariff_duration_minutes`, `tariff_price`, `tariff_label`, `lesson_duration_minutes`.
- Первая оплата выставляет billed только по правилам §3.3 (legacy без `price_id`). Топ-ап billed не трогает.
- Сумма **не больше остатка** (hard-block). Переплату, которую RPC сейчас пропускает, в этих режимах закрыть.

**B. Оплата текущей суммы** (касса)

- Данные записи, длительность, плательщик, сумма из остатка (можно **уменьшить**), способ оплаты.
- Пакета нет, тарифа нет: `price_id IS NULL`, `tariff_units IS NULL`.
- Начисление не пересчитывается.
- Сумма > 0 и ≤ остатка.

**C. Переоценка начисления** (уже есть, не касса)

- `restate_personal_lesson_amount`: меняет `price` / charge billed.
- Нельзя опустить ниже уже оплаченного.
- Не подменять кнопкой «оплата по тарифу».

Пакет — только в popup расписания / персональных, **не** в дебиторке (как задумано кнопками).

Частичная оплата: несколько платежей на один charge (топ-апы уже есть). Сторно — как сейчас, с привязкой к charge на этапе 2.

Один платёж **не** закрывает чужой charge. Чтобы принять деньги за должника B: платёж вешается на charge/клиент B; кто принёс наличные — в комментарии. В журнале клиент = чей долг закрыт.

## 5. Сценарии

Обозначения: T45 = тариф 300 / 45 мин; T60 = 300 / 60 мин; A, B — клиенты.

### 5.1. Тариф и длительность

**S1. Совпадение.** Урок 19:00–19:45, T45.  
Ожидание: warn нет, billed = 300, units = 1. Оплата по тарифу → платёж 300, долг 0.

**S2. Длиннее, кратно.** Урок 90 мин, T45.  
Ожидание: warn «длиннее, 2 × 45 мин», billed = 600 **уже при создании** неоплаченного урока. Оплата 600. В журнале: длительность `1ч. 30мин.`, тариф T45, единицы `×2`.

**S3. Длиннее, не кратно.** Урок 60 мин, T45.  
Ожидание: **один** warn «длиннее и не кратно», billed = 400.00. Можно сменить время на 45/90 или подтвердить 400.

**S4. Короче тарифа.** Урок 30 мин, T45.  
Ожидание: warn «короче тарифа», billed = 200.00.

**S5. Смена времени после выбора тарифа, платежей нет.** Было 45 мин / 300, поставили 90 мин.  
Ожидание: billed → 600, повторный warn.

**S5b. Restate, затем смена времени.** Billed вручную 250, `price_id` сброшен, слот двигают на 90 мин.  
Ожидание: billed остаётся 250. Не возвращать тарифный пересчёт.

**S5c. Restate без платежей, затем «оплата по тарифу».** Billed вручную 250, `price_id` сброшен, платежей нет. Оператор в кассе выбирает T45 на слоте 45 мин.  
Ожидание: billed → 300, дальше платёж по тарифу. Это **явный** возврат к тарифу, не баг. Чтобы сохранить 250 — только режим B.  
Если restate был **после** частичной оплаты (`price_id` NULL, платежи есть) — режим A скрыт, только B.

**S6. Смена времени после оплаты** (полной или частичной). Урок 45 мин, billed 300, уже есть платёж (300 целиком или, например, 150), двигают на 90 мин.  
Ожидание: длительность слота менять можно, начисление **не** трогать автоматически; warn в edit-popup. Не пересчитывать молча в 600. Правило то же, что в §3.3: **любые** платежи по уроку выключают автопересчёт.

**S7. Legacy-тариф без duration.**  
Ожидание: billed = `prices.price` независимо от слота, warn «у тарифа не задана длительность». В отчёте тариф виден по `price_id`, единицы в UI не показываем как квант времени (или прочерк). Не писать фиктивные `×1` как «1 урок тарифа 45 мин».

**S8. Оплата текущей суммы.** Долг 600 (после S2, не платили). Оператор берёт 500 вручную.  
Ожидание: платёж 500 без `price_id`, billed остаётся 600, долг 100. В выручке 500 в «без тарифа».

**S9. Пакет.** Списание занятия с private subscription.  
Ожидание: cash-платежа нет (`price = 0` / `paid = yes`). `price_id` на уроке **NULL** (не писать тариф продажи). Смена слота не пересчитывает 0 в billed. В «продажах по тарифам» **не** учитывать.

**S10. Сторно тарифа.** Оплатили 600 по T45, сторно.  
Ожидание: нетто 0 по тарифу T45 за период; начисление снова открыто на 600.

**S10b. Топ-ап по тарифу.** Billed 600, уже оплачено 400 по T45, остаток 200. Снова «по тарифу».  
Ожидание: сумма lock = 200, тот же `price_id`/`units_snap`, billed остаётся 600. Не пытаться провести ещё 600. В выручке это **2 платежа**, не 1 урок; `tariff_units` **не складывать** (2+2 ≠ 4 кванта).

**S10c. Смена тарифа в кассе после частичной оплаты.**  
Ожидание: тариф lock, billed не менять. Новый тариф можно выбрать только если платежей нет.

**S11. Еженедельная серия.** 8 слотов 90 мин, T45.  
Ожидание: 8 записей, у каждой `price_id` и billed 600. Не одна сумма на серию.

### 5.2. Несколько клиентов

**S12. Pair, платит один (основной).** A+B, T60, 60 мин, режим «плательщик A».  
Ожидание: одно начисление 300 на A. Дебиторка: строка A на 300, B нет. Оплата A 300 → долг 0. B в карточке урока остаётся.

**S13. Pair, платит «не первый».** Плательщик B, в форме B выбран вторым.  
Ожидание: начисление и платёж на B. Нельзя молча писать на `client_id1`.

**S14. Pair, поровну.** billed 600, поровну. Этап 2.  
Ожидание: charge A 300, charge B 300. Дебиторка две строки. A платит 300 → остаётся только B 300.

**S15. Pair, A принёс деньги за долг B.**  
Ожидание: платёж на charge B, в журнале клиент B. Комментарий «оплатил Иванов». Нельзя одним платежом закрыть два charge. Не размазывать сумму без выбора должника.

**S16. Trio / quad, один плательщик.**  
Ожидание: как S12, одно начисление. Дебиторка показывает имя плательщика; в деталях — остальные участники, включая четвёртого.

**S17. Один из двух уже оплатил пакет, второй — деньгами.**  
Ожидание: v1 **не смешивать**. Если урок списан с пакета — весь урок пакетный (`price = 0`). Гибрид — этап 3+.

**S18. Оплата из дебиторки, pair.** Строка «A, 300».  
Ожидание: popup открывается на должнике A, не на «A & B». `openPersonalPayment` передаёт `payerClientId` (не только `clientId1`).

### 5.3. Отчёты

**S19. Финансы → Выручка, месяц.** 3 платежа T45 на 600+300+300, 1 платёж без тарифа 500, 1 сторно T45 −300.

| Строка | Платежей (нетто операций) | Сумма нетто |
|---|---|---|
| T45 (45 мин) | 3 − 1 = 2 | 600+300+300−300 = 900 |
| Без тарифа | 1 | 500 |

«Платежей» = число денежных операций нетто (сторно уменьшает count на 1), **не** «уроков» и **не** сумма `tariff_units`. Топ-ап 400+200 по одному уроку = 2 платежа; оба могут нести `units_snap = 2` — в агрегат единиц это не складывать. Абонементы, разовые, аренда в этот блок **не входят**.

Место в UI: **Финансы → Выручка** (`FinanceRevenuePage`) за выбранный месяц. На дашборде (`FinancialDashboard`) достаточно текущего `personalTotal`, без разбивки по тарифам.

**S20. Журнал платежей, раскрытая строка.** Персональный платёж.  
Поля: клиент (чей долг), длительность урока (снимок, иначе из слота), тариф или «без тарифа», единицы (`×2` только если есть тариф и `tariff_units`), сумма, способ.  
Legacy без `price_id`: «без тарифа», без выдуманного «×1».  
Подсказка по единицам: клик сразу, hover ~0.5 с — «сколько квантов тарифа в длительности урока; задаётся длительностью тарифа в прайсе, не вручную».

**S21. Payroll.**  
Уже % от строк `payments` урока. После split **не менять**: по-прежнему нетто-платежи, не `price` урока. Отдельное решение не требуется, пока не появится гибрид пакет+cash.

## 6. Архитектура

### 6.1. Слой данных

**Этап 1 — одна миграция** (timestamp после `20260916000001`, не отдельные релизы внутри подверсии):

**Длительность тарифа**

```
prices.duration_minutes INT NULL
  CHECK (duration_minutes IS NULL OR duration_minutes > 0)
```

- Обязательно в UI при создании тарифа **персонального урока** (`private` + 1 занятие, не пакет).
- Пакетные private (`lessons > 1`): в v1 то же поле = длительность **одного** занятия пакета (для слота списания / warn); в кассу пакета не входит. Форматы пакета в UI: solo / pair / trio (`PrivatePackageFormat`); **quad** только у разового тарифа (`personal_quad`), не у пакета.
- Group / single_visit: `NULL` (не используется).
- Backfill существующих personal_solo/pair/trio/quad: **NULL = legacy fixed**, в UI «указать длительность». Не ставить авто-60: при повторном открытии оплаты старые 45-мин слоты пересчитаются.

**Тариф на уроке (для пересчёта до оплаты)**

```
personal_lessons.price_id UUID NULL
  FK (organization_id, price_id) → prices  ON DELETE SET NULL
```

Заполнять при продаже / выборе тарифа в форме. Смена времени (§3.3) и warn читают `price_id` + слот. Оплата «текущей суммы» не требует тарифа; ручная переоценка может обнулить `price_id` (явный режим без тарифа).

**Плательщик без charges** (закрывает S12–S13, S18; обязательная часть этапа 1, не отдельный релиз)

```
personal_lessons.payer_client_id UUID NULL
  -- NULL = client_id1 (legacy)
  -- CHECK нельзя писать как payer IN (client_id1..client_id4):
  -- NULL-слоты делают IN неизвестным, CHECK пропустит чужого клиента.
  CHECK (
    payer_client_id IS NULL
    OR payer_client_id = client_id1
    OR (client_id2 IS NOT NULL AND payer_client_id = client_id2)
    OR (client_id3 IS NOT NULL AND payer_client_id = client_id3)
    OR (client_id4 IS NOT NULL AND payer_client_id = client_id4)
  )
```

Дебиторка: `client_display` = payer, не concat. В view и `DebtorEntry` — `payer_client_id` (+ `client_id4` для состава). `openPersonalPayment` не должен требовать, чтобы payer == `client_id1`. Долг всё ещё один на урок. «Поровну» нет.

Смена состава урока: payer обязан остаться в `{client_id1…4}`. Если плательщика убрали — потребовать нового, не молча падать на `client_id1`.

**Снимок на платеже**

`payments.price_id` сейчас **нет** (проверить: колонка не добавлялась; у разовых визитов `price_id` в таблице `single_visits`). Это **новая** nullable-колонка, не reuse.

```
payments.price_id UUID NULL
  FK (organization_id, price_id) → prices  ON DELETE SET NULL
payments.tariff_duration_minutes INT NULL
payments.tariff_units NUMERIC(12,4) NULL CHECK (tariff_units IS NULL OR tariff_units > 0)
  -- без DEFAULT
payments.tariff_price NUMERIC NULL CHECK (tariff_price IS NULL OR tariff_price >= 0)
payments.tariff_label TEXT NULL
payments.lesson_duration_minutes INT NULL CHECK (lesson_duration_minutes IS NULL OR lesson_duration_minutes > 0)
-- personal_lesson_charge_id: не добавлять в этапе 1. Колонка + FK + NOT NULL для новых строк — этап 2.
```

Снимок тарифа (`tariff_*`, `tariff_label`) остаётся, даже если строку прайса потом удалят (`price_id` обнулится).  
`personal_lessons.price_id ON DELETE SET NULL` согласован с §3.3: урок становится «без тарифа», billed не пересчитывается. Не нужен RESTRICT.

`_storno_payment_impl` и `correct_payment` (явный INSERT колонок) **обязаны** копировать `price_id` + все `tariff_*` + `lesson_duration_minutes` с исходного платежа. Иначе S10/S19 разъедутся: платёж T45, сторно «без тарифа».

`update_personal_lesson` (актуально `20260846000001`) принимает `price` в payload, но не `price_id` / `payer_client_id`. В той же поставке этапа 1: разрешить оба поля; при смене слота — пересчёт billed **в RPC** по §3.3 (не только в JSX); при смене состава — CHECK payer, иначе 500. Пакетный путь (`subscription_id`, `price = 0`) обнуляет `price_id`.

RPC `record_personal_lesson_payment` — **одна** публичная сигнатура с `p_venue_rule_acknowledged` и логикой partial/top-up из 780. Не оставлять параллельный 4-param overload и stale `_record_personal_lesson_payment_before_venue_rules`: wrapper из 530 должен вызывать новое тело, либо wrapper убрать, venue guard встроить в основную функцию (как у `record_single_visit` после follow-up).

```
p_price_id uuid DEFAULT NULL
p_tariff_units numeric DEFAULT NULL
p_tariff_duration_minutes int DEFAULT NULL
p_tariff_price numeric DEFAULT NULL
p_tariff_label text DEFAULT NULL
p_lesson_duration_minutes int DEFAULT NULL
p_client_id uuid DEFAULT NULL   -- NULL = client_id1 (legacy); этап 1 передавать явно
-- p_charge_id: не добавлять в этапе 1 (charges нет). Этап 2.
p_venue_rule_acknowledged boolean DEFAULT false
```

Идемпотентный fingerprint: lesson, amount, method, venue_ack, price_id, units, client. Charge — в этапе 2.

Кап: `p_amount ≤ remaining` после синка billed — **в RPC для всех вызовов**, не только UI. Режим тарифа может сначала обновить billed (§3.3), затем проверить остаток.

`restate_personal_lesson_amount`: при успехе **обнулять** `personal_lessons.price_id` (явный режим без тарифа, §3.3).

На этапе 2: один charge из `payer_client_id` (или `client_id1`), затем колонку не использовать как источник истины (можно оставить как кэш / дропнуть в follow-up). **Не** держать параллельно payer и charges.

**Этап 2 — charges**

Таблица `personal_lesson_charges` (§4.2).  
RPC создания урока создаёт 1..N charge.  
`sync_personal_lesson_paid_status` считает по сумме charge.

## 9. Критерии готовности

Общий «можно закрывать продукт» = все три этапа. Для PR — только свой этап.

### Этап 1

1. В прайсе у нового персонального тарифа нельзя сохранить без длительности.
2. Создание: 90 мин + тариф 45 / 300 → `price_id` на урок, в дебиторке 600 без ручного коэффициента.
3. 30 мин + тот же тариф → предупреждение и 200.00, оплату не блокирует.
4. 60 мин + T45 / 300 → **400.00**, не 399.99.
5. Pair+: выбран плательщик A → в дебиторке только A (не «A & B»); оплата из дебиторки идёт на A, даже если A не `client_id1`.
6. «Оплата по тарифу»: сумма lock = остаток, нет пакета, есть `price_id` на платеже; тариф не подбирается по равенству цены.
7. «Оплата текущей суммы»: нет пакета и тарифа, сумма из долга, редактируется вниз, есть способ оплаты.
8. В журнале у персонального платежа видны длительность и тариф/единицы; у legacy — «без тарифа».
9. SQL-тесты на RPC; формулы в `lib/` (multiply-first → 400.00), не только в JSX.

### Этап 2

10. Поровну: две строки дебиторки; платёж A не закрывает charge B.

### Этап 3

11. В Финансы → Выручка за месяц — таблица тарифов + «без тарифа» (платежей нетто и сумма нетто).
