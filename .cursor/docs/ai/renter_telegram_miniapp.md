## 1. Сценарий

### 1.1. Кто и зачем

Владелец студии сдаёт зал людям «с улицы» и преподавателям, которые берут зал **как арендаторы**. Арендатор живёт в Telegram: видит занятость, бронирует разово или на 4 недели, держит деньги на балансе (аванс), приносит чек через чат с студией. Студия подтверждает пополнение в CRM. Уроки студии и аренда **не накладываются**: чтобы поставить урок на занятое арендой время, владелец / директор / полный admin сначала отменяет бронь.

Один Telegram-пользователь может быть преподавателем в CRM и арендатором в Mini App — **две роли, два входа**.

### 1.2. Вход и регистрация

- Каждая студия даёт **свою** ссылку на Mini App (свой бот + `organization_id` в **подписанном** `start_param`). Формат ссылки: `t.me/<bot>/<app>?startapp=<organization_id>` — тогда org id попадает в `initData.start_param` и входит в HMAC (`data_check_string`). Таблица Telegram до сих пор описывает `start_param` как `startattach` / attachment menu; Direct Link `?startapp=` **тоже** кладёт значение в `initData.start_param` — это наш канал, attachment menu не требовать. `startapp` / `start_param`: 1–64 символа, только `A–Z a–z 0–9 _ -` (UUID с дефисами проходит, 36 символов). После HMAC `start_param` **парсить как UUID**; иначе generic отказ (не «битый id»). Голый query `?org=` и `initDataUnsafe` **не** источник истины. Открытие Mini App из меню бота **без** `startapp` → `start_param` пустой → отказ (нужна ссылка студии; кнопка меню BotFather тоже с `startapp`). Чужая студия по этой ссылке недоступна. Хостинг клиента один (`tangodb-renter/`); не отдельный деплой на каждую студию. Supabase-сессия на этом origin **namespace по `organization_id`** (`auth.storageKey`), не дефолтный ключ на весь origin: Telegram Web шарит `localStorage` между ботами одной Mini App URL, иначе студия B перезапишет JWT студии A.
- Арендатор входит через Telegram Mini App (`initData`). Идентификатор — **Telegram ID** (`user.id` из подписанного initData, целое > 0). Telegram гарантирует ≤52 значащих бит (JS `number` не теряет), на проводе всё равно десятичная **строка**, в БД `bigint` (не `number` leftover `database.ts`). Не собирать id из отдельного поля тела запроса. Не брать identity из `chat.id` (открытие из группы) и не из `receiver` (attachment / inline) — после HMAC эти поля отбросить. `user.is_bot` в поле `user` обычно нет (дока: только `receiver`) — если `true`, отказ.
- Саморегистрация **без** подтверждения персонала: при первом входе upsert `renters` по `(organization_id, telegram_id)`. Если пары нет — новая карточка (`counterparty_type = individual`, `status = active`). Юридические поля кассы 2.5 (`sole_proprietor` / `company`) не обязательны. **Не** мержить автоматически с уже существующей кассовой карточкой без `telegram_id` (иначе ложный match по имени/телефону). Персонал может заранее проставить `telegram_id` на кассовую карточку — тогда Mini App попадёт в неё. Проставить id, который уже занят другой карточкой той же org — **отказ** (partial unique), не молча. Смена или очистка `telegram_id` на карточке → `revoke_auth_sessions_for_user` по её `auth_user_id` (иначе JWT ходит в карточку без этого Telegram). Дубль после факта — ручная склейка, не auth. После склейки источник истины на RPC — `(organization_id, telegram_id)`, не устаревший `renter_id` в JWT (иначе stale сессия ходит в старую карточку).
- Имя из Telegram (`first_name` / `last_name` → `display_name`) — **только INSERT**. Повторный вход **не** затирает правки персонала или арендатора. Арендатор может править `display_name` и `contact_phone` (колонки уже есть; отдельные `first_name` / `last_name` на `renters` не плодить). Длина и XSS: обрезка на сервере (потолок `display_name` 80, `contact_phone` через существующий `normalize_renter_phone`), управляющие символы срезать, в UI как текст, не HTML. После ручной склейки карточек — `revoke_auth_sessions_for_user` по старому `auth_user_id` и опора RPC на `(organization_id, telegram_id)`, не на устаревший `renter_id` в JWT.
- Тот же Telegram ID может быть арендатором в нескольких студиях — только через **разные** боты/ссылки, не через общий список школ. Сессия **на пару** `(organization_id, telegram_id)`, не один глобальный `auth.users` на Telegram ID (иначе вторая студия перезапишет JWT).
- Email GoTrue **не угадываемый** и не логин: не `renter+<telegram_id>+<org>@…` (это публичный шаблон: invite этой почты в команду → хук может выдать org-claims). Формат: непредсказуемый local-part + `@users.invalid` (TLD `.invalid`), таблица связи `auth_user_id` на `renters`. Invite / `organization_members` INSERT для `app_metadata.actor = renter` — отказ.
- `telegram_id` — ключ входа. Строка `renter_contacts.telegram` (контакт для персонала) **не** заменяет его, **не** участвует в HMAC и **не** автосклеивает карточки.

### 1.3. Кабинет арендатора (два раздела)

1. **Расписание** — сетка **выбранного** зала из локаций с `miniapp_enabled` (если зал один — без выбора): только **Занято / Свободно**. Занято: уроки студии (группа, персональные), мероприятия, чужие и свои брони аренды (включая холд «ожидает оплаты»). Без имён, без типа занятия. Свои слоты визуально отличаются, чтобы открыть карточку. Залы без флага в кабинете не показываются (занятость уроков не светить «улице» по всей студии).
2. **Мои записи** — свои брони, баланс, долг, заявки на пополнение, надёжность (если нужна прозрачность — см. §6.5).

Горизонт сетки: **текущая неделя пн–вс + две будущие** — 3 календарные недели в `organization_settings.timezone`. Граница недели — ISO weekday (пн=1), **как договорённость CRM-сетки** (`getWeekRange` всегда от понедельника). Не копировать браузерный `Date` из текущего `getWeekRange` (он на TZ клиента, не org). Поле `week_starts_on` в settings **есть** (General settings) и **не** источник истины для Mini App, пока CRM-сетка его не читает. Не скользящие 21 сутки: в воскресенье окно короче, чем в понедельник. Разовую бронь можно создать только внутри этих трёх недель. Клиент occupancy — refetch при фокусе / `visibilityChanged`; «свободно» в кэше не источник истины (create сериализует conflict RPC).

### 1.4. Бронь: время и зал

- Арендатор **выбирает зал** среди `miniapp_enabled` локаций своей org.
- Старт только с шагом **30 минут** (12:00, 12:30, …).
- Минимум **1 час**, далее шаг **30 минут** (1:00, 1:30, 2:00, …).
- Нельзя создать бронь, если начало слота **строго раньше**, чем через 1 час (`time_start_ts < now() + 1 hour`). Ровно через час — можно. Elapsed: `now` vs `timestamptz` начала = локальные `rental_date` + `time_start` в `organization_settings.timezone` (как GCAL: DATE+TIME → timestamptz; календарный день — `_org_local_date` / HALL-RENT-9). У локации своей TZ нет. Сообщение: бронирование недоступно в ближайший час, выберите другой слот. `time_end` > `time_start` в ту же календарную дату (ночь через полночь — отказ, как кассовая форма). Прошедшая дата текущей недели тоже отсекается этим правилом.
- Нельзя встать поверх урока, мероприятия или другой аренды (включая холд). Студия не ставит урок поверх аренды (сначала отмена — §1.1 / §4.4).

### 1.5. Разовая и постоянная аренда

У каждой локации канала Mini App **свои** почасовые ставки (не путать с `rental_tariffs` кассы 2.5). Локация в кабинете только при `miniapp_enabled` и полном наборе 3 kind:

| Режим | Ставка | Горизонт создания |
|---|---|---|
| Разовая | тариф разовой аренды локации | только 3 видимые недели |
| Постоянная (еженедельно, дни и часы) | тариф постоянной аренды локации | пакет **4 недели = 28 календарных дней** от даты начала до даты конца **включительно** (`valid_to = valid_from + 27 days`) |

Дата **начала** пакета = дата **первой occurrence** (не произвольный календарный день до первого выбранного weekday). Она должна попасть в окно 3 недель. `valid_from` = эта дата, `valid_to = valid_from + 27 days`. Так 4 полных недели содержат по 4 вхождения каждого выбранного weekday. Хвост пакета (4-я неделя) может выходить за сетку Mini App: он есть в «Мои записи» и в CRM; в сетке арендатора появится, когда окно 3 недель доедет. **Чужая** сетка 3 недель хвост не показывает — разовую бронь туда всё равно нельзя (окно). Create/preview пакета **обязан** conflict-check **все** occurrence, включая даты за UI-окном: иначе пакет B стартует в «свободный» понедельник видимой недели и бьётся о хвост пакета A. Мастер пакета: **`renter_quote_booking`** на `[valid_from, valid_to]` (макс. 28 дней), busy/free без PII, не годовой выгрузкой и не второе RPC. Generic конфликт, без имён.

После пакета арендатор оформляет **новую** постоянную аренду на следующие 4 недели. Бесконечной серии нет. Один пакет = одна `location_id` (как `rental_series`); два зала — два пакета. Успешное прохождение всех дат (`settled` / `debt` по used) → `rental_series.status = completed`, **без** пересчёта на разовый тариф.

**Создание пакета — атомарно:** конфликт, правило «1 час», отсутствие ставки или нехватка условий на **любой** дате → весь пакет не создаётся. После успешного create пакет разворачивается в **несколько независимых** `rentals` (по одной на дату) плюс строка `rental_series`. У каждого слота свой холд 24 ч, своя активация 50 % и FIFO.

**Пакет нельзя оставить с неактивированными холдами:** в той же транзакции — вставка + FIFO; если **хотя бы одна** дата пакета остаётся `awaiting_payment` → **ROLLBACK** всего пакета (сообщение: недостаточно баланса с учётом уже ожидающих слотов и FIFO). Иначе 4 несгоревших холда первого пакета = `completed ≥ 4` и бан 75 % с первой попытки. Разовая бронь без денег (§1.6) **не** подпадает под этот порог. UI пакета показывает, что все даты активируются сейчас (после успеха — так и есть).

**Раннее закрытие пакета** (пересчёт used на разовый) — только если будущих дат не осталось **и** хотя бы одна дата снята, не дойдя до used (`cancelled` / `hold_deleted` / `auto_deleted`). Триггеры: отмена пакета целиком; отмена / удаление холда / автоудаление **последней** будущей даты; бан 75 % (§1.10). Тогда `rental_series.status = cancelled`; стоимость **использованного** времени (слоты, у которых `time_end` уже наступил: `settled` / `debt` / `prepaid_charged` с прошедшим концом) пересчитывается по ставке **разовой** аренды; если действует штрафник — `max(one_time, penalty)` на дату слота (не снижать used ниже штрафного часа). Разница — доначисление / долг (§4.3). **Порядок RPC:** сначала закрыть будущее (§1.8: снять резервы / refund), **затем** surcharge used. Иначе surcharge считает `spendable` при ещё живых резервах будущих дат и вешает лишний долг. Неиспользованное будущее — по правилам отмены §1.8.

Отмена **части** будущих дат (или удаление части холдов), пока в пакете ещё остаются будущие occurrence, **не** переводит использованное на разовый тариф; пакет продолжается (`status = active`).

### 1.6. Деньги: кошелёк, 50 %, списания

Кошелёк = развитие текущих **авансов** (`rental_advances` + регистр). Пополнение попадает на баланс, не «приклеивается» к одной брони заранее.

**Создание разовой брони без денег разрешено** (слот занимает холд). **Пакет 4 недель — нет:** см. ROLLBACK §1.5. Сумма для **активации** = **50 % стоимости этой брони** (пропорционально часам: 1.5 ч → 50 % от цены 1.5 ч). Одни и те же деньги не активируют несколько броней сразу: свободный баланс распределяется **по возрастанию даты/времени начала**, затем `created_at` (FIFO). FIFO **не** активирует слот, если `now ≥ time_start` **или** `now ≥ hold_expires_at` — его забирает catch-up/expiry, не «оживление» просроченного холда опоздавшим topup. Что не покрыто — остаётся «ожидает оплаты».

«Свободный баланс» для FIFO — **вычисляемый** (не отдельная таблица резервов): `available = wallet_balance − Σ prepay` по броням в `active` без фактического списания предоплаты. **Пока у арендатора есть непогашенный Mini App-долг (`Σ debt_amount > 0`), `available` для FIFO = 0**: пополнение копится к порогу целого `debt_settle`, а не «съедается» **новой** активацией холдов. Уже выставленные резервы `active` не снимать в момент появления долга. Таймеры `awaiting_payment` **не** замораживать (иначе вечный холд без 50 %). Тик T−24 ч / charge внутри окна для **уже** `active` **выполняется** (резерв уже выделен; это не новая FIFO-активация).

`debt_settle`, `surcharge` **и remainder в `time_end`** тратят только `spendable = wallet_balance − reserved_prepay`, не «съедая» деньги под 50 % already-`active` **других** слотов. Иначе T−24 ч по чужому резерву сорвётся, и правило «резерв не снимать» пустое. Инвариант: `wallet_balance >= reserved_prepay` (эти три операции и `prepay_charge` его не ломают). Списание в ledger кошелька — только в фазах T−24 ч / активация внутри окна / remainder / refund / surcharge / debt_settle (§4.2). Подтверждённое пополнение = кассовый inflow; сами 50/50 **не** второй кассовый приход (§3 п.3).

Порядок после подтверждённого пополнения: зачисление на кошелёк → погашение долгов целиком по одному rental (FIFO по `time_end`) пока `spendable >= debt_amount` этого слота → затем FIFO-активация холдов, если долгов не осталось.

Цепочка по одной записи:

1. Холд занимает слот (`booking_status = confirmed`, `lifecycle = awaiting_payment`). Если `available` не хватает на 50 % — остаётся **ожидает оплаты**, таймер §4.1. Если хватает — активация: вне окна 24 ч → `active`; внутри окна — п.2 (charge в той же транзакции).
2. За **24 часа до начала** с кошелька списываются 50 % (предоплата) — переход в `prepaid_charged`. Если **create или поздняя FIFO-активация** уже внутри горизонта «≥ 1 ч и < 24 ч до старта» — эти 50 % списываются **в той же транзакции, что активация** (не оставлять `active` без charge до worker: иначе 1–2 мин дыры и гонка с отменой). Краткий промежуточный `active` без charge внутри окна допустим только внутри RPC, наружу — сразу `prepaid_charged` при успехе. Если charge в этом RPC не удался — наружу `awaiting_payment`, не `active`.
3. Если к T−24 ч (или к активации внутри окна, пока `now < time_start`) списание не удалось — снова **ожидает оплаты**, новый таймер холда (§4.1), уведомление. Слот по-прежнему занят, пока холд не истёк. Если `now ≥ time_start` и слот всё ещё `active` без charge — **не** этот пункт, а catch-up §4.1 (после старта не возвращать в `awaiting_payment`).
4. Если арендатор **не отменил** бронь, в момент `time_end` автоматически начисляются **оставшиеся 50 %** (`remainder = cost − prepay` после округления) **из `spendable`**, не из денег, зарезервированных под 50 % других `active`.
5. Если к `time_end` **`spendable` < remainder** — вторая половина **не списывается**, вешается **долг** (`debt_amount` на этом rental, вне баланса кошелька). Не подменять формулировку «на балансе не хватает» целым `wallet_balance` (там ещё чужой резерв). UI Mini App и карточка CRM **обязаны** показывать `spendable` и `reserved_prepay` раздельно (иначе «на балансе 100» + долг remainder). Пополнение сначала на кошелёк; долг гасится **целиком по одному слоту** из `spendable` (частичного погашения одного `debt_amount` нет). Несколько долгов: закрывать по очереди (`time_end`, затем `created_at`), пока хватает на следующий целиком. Пока `Σ debt_amount > 0`, **новые** брони запрещены. Также запрещены, если `renters.status ≠ active` (кассовые `archived` / `blocked`) или задан `booking_banned_at`. `renter_delete_hold` и renter-cancel **уже** `active` / `prepaid_charged` (до `time_start`) при долге **разрешены** (освободить зал / вернуть резерв; refund >24 ч может закрыть долг через `debt_settle`). Уже висящие `awaiting_payment` **не** замораживаются: таймер идёт, холды могут сгореть в untimely, пока арендатор гасит долг — UI обязан предупредить «пополните с запасом на холды».
6. Полной оплаты 100 % в момент создания **нет**. «Оплатить сразу» — подсказка, не платёжная операция: на балансе достаточно и на FIFO-активацию, и на remainder к `time_end`, без долга.

### 1.7. Статус в сетке

Один визуальный статус неоплаты холда: **ожидает оплаты**. Отрисовка: **серый слот с диагональными полосами**. Слот **занят для всех** (другой арендатор не встаёт).

Когда предоплата 50 % покрыта (`active` / `prepaid_charged`) — обычный блок активной аренды (в Mini App для чужих — просто «Занято»).

`ring-rose-500` на сетке CRM **не** использовать для холда. Rose оставить финансовому долгу после `time_end` (`lifecycle = debt`) и текущему кассовому `payment_status` unpaid/partial контура 2.5. Не смешивать полосы холда и rose долга на одном блоке.

При `channel = miniapp` LessonBlock **не** берёт цвет долга из кассового `payment_status` / `paid_amount` (иначе холд с `paid_amount = 0` получит rose). Rose только `lifecycle = debt`. Кассовые слоты (`channel = cashier`) — как сейчас.

Активация при достаточном балансе **автоматическая**. Popup «слот занят» — только если ячейка уже занята уроком, мероприятием или чужой арендой.

### 1.8. Отмена и удаление холда

Два действия отмены (арендатор — до старта; персонал сетки — до `time_end`):

| Действие | Кто | Правило денег |
|---|---|---|
| Отменить **одну** дату | **Арендатор** — только пока `now < time_start` и не `awaiting_payment` (это «удалить холд»). После `time_start` renter-cancel **нет**: иначе `prepaid_charged` за минуту до `time_end` снимает remainder, зал уже использован. `active` без charge после старта — catch-up §4.1 п.3, не «отмена с удержанием». **Персонал** (owner / director / полный admin сетки) — пока `now < time_end` (освободить зал под урок). Деньги **автоматически по этой таблице**, не кассовый `CancelRentalModal` (`refund` / `transfer_to_advance` / penalty 2.5) | Граница **та же**, что charge T−24 (`now >= time_start − 24h`): **строго больше** 24 ч до начала (`now < time_start − 24h`) — возврат **уже списанных** 50 % на кошелёк (если списания не было — только снять FIFO-резерв), вторую половину не начислять. `now ≥ time_start − 24h` **и** `now < time_start`: студия удерживает 50 %. Если предоплата ещё **не** списана (`active`, `prepay_charged_at IS NULL`) — сначала списать 50 %, затем `cancelled` **без** refund (charge даже при чужом долге: удержание по этой брони, не FIFO; обходит `available = 0`; правило кошелька §4.2). Если списать нечем — `cancelled` без charge (слот не держать ради недоступных 50 %); при инварианте `wallet_balance >= reserved_prepay` эта ветка **не возникает никогда** (в т.ч. несколько `active`: `wallet − (reserved − этот prepay) ≥ этот prepay` тождественно инварианту) — только fail-safe. Occupancy персонала при `now ≥ time_start` и `now < time_end`: как внутри окна 24 ч — 50 % удерживаются (уже списаны или charge в этом RPC), remainder **не** начислять, слот свободен на остаток интервала. |
| Отменить **всю** постоянную аренду (пакет 4 недель) | то же | будущее удалить по правилу 24 ч на каждый слот; если это **раннее** закрытие (§1.5) — использованное пересчитать по §4.3. То же, если отмена / `hold_deleted` / `auto_deleted` последней будущей даты. Все 4 недели дошли до `time_end` как used → `completed`, **без** пересчёта |

После `time_end` (`settled` / `debt`) слот не отменяет никто (не переписывать историю used). Occupancy-отмена персонала Mini App — только пока `now < time_end`.

**Удалить холд** (ошибочные дата/время, статус «ожидает оплаты», предоплата ещё не списана): арендатор своих; персонал — SQL `member_can_manage_rentals()` (owner, director, полный admin; accountant нет). Слот освобождается (`booking_status = cancelled`, `lifecycle = hold_deleted`), на счётчик своевременности это **не** пишется как автоудаление за неоплату (это отказ от заявки, не просрок). Occupancy-отмена персонала слота в `awaiting_payment` без списанной предоплаты — **та же** семантика `hold_deleted` (не голый `cancelled`), иначе наследование expiry §1.8 разъедется.

Повторная бронь **пересекающегося** интервала тем же арендатором **на той же `location_id`**, пока не истёк `hold_expires_at` предыдущего `hold_deleted`, **наследует** этот expiry (нельзя обнулить таймер удали-и-создай и нельзя обойти сдвигом на 30 мин). Другой зал в то же время — **новый** таймер (griefing привязан к залу, не ко всей студии). Пересечение = тот же `schedule_time_ranges_overlap`, что conflict (`s1 < e2 AND s2 < e1`): **стык** `12:00–14:00` и `14:00–16:00` **не** overlap. Другой непересекающийся интервал — новый таймер. После `auto_deleted` (просрок) повтор того же/пересекающегося слота — новый холд 24 ч (слот успел побыть свободным). После `cancelled` **с refund** (`now < time_start − 24h`) повтор пересекающегося интервала **на той же локации** наследует cooldown до исходного `time_start` (иначе бронь → отмена с возвратом запирает зал бесплатно; сдвиг на 30 мин не обнуляет). Тот же cooldown — на `cancelled` без charge (редкий fail-safe). При `hold_deleted` / refund-`cancelled` **не NULL-ить** `hold_expires_at` и не затирать `time_start` (наследование читает терминальную строку). Лимиты незавершённых Mini App-слотов **обязательны**, **два порога** (безлимит запрещён; на арендатора по студии, не на зал). Один общий потолок «8» **не подходит**: пакет 3 weekday × 4 недели = 12 слотов (легитимно, после ROLLBACK все с 50 %), а те же 8–12 **неоплаченных** разовых холдов — griefing зала.

| Порог | Что считает | Рекомендуемый старт | Зачем |
|---|---|---|---|
| Неоплаченные холды | только `awaiting_payment` | **4** | разовые без денег; пакет в `awaiting` не живёт (ROLLBACK §1.5) |
| Все незавершённые | `awaiting_payment` + `active` + `prepaid_charged` | **32** | полный пакет 7×4 = 28 плюс несколько разовых |

Продукт может сдвинуть цифры при реализации, не схему двух порогов. Exceed любого — отказ create (весь пакет). `settled` / `debt` / терминальные отмены не считаются.

Персонал **не** может создать бронь канала Mini App арендатору с запретом бронирования, `status ≠ active`, долгом > 0 или **без** `telegram_id` (иначе некого уведомлять и нет входа в кабинет). Ручная бронь **этого канала** (те же ставки часа и RPC, что самообслуживание) — **те же** 50 %, FIFO, счётчик, долг. Кто вызывает: owner / director / полный admin — SQL `member_can_manage_rentals()`, не UI `rentals.write`. Accountant **не** создаёт канал Mini App (`member_can_create_rental()` / HALL-RENT-23 остаются для `create_rental` кассы 2.5). Текущие `CreateRentalDialog` / счета / `rental_tariffs` (касса 2.5) **не** подменяют этот канал и наоборот.

Отмена occupancy канала Mini App в CRM: SQL `member_can_manage_rentals()` (owner / director / полный admin); UI **не** показывает кассовые financial actions (`CancelRentalModal`). RPC: отдельная ветка / те же Mini App cancel RPC с JWT member, не `cancel_rental(..., financial_action)` и не `member_can_create_rental()`. Accountant по HALL-RENT-23 по-прежнему может отменять **кассовые** слоты 2.5; для Mini App (`channel = miniapp`) — нет, пока продукт явно не расширит. Кассовый UI (`list_rental_payment_inbox`) слоты Mini App не показывает и не отменяет. `member_can_manage_rentals()` **уже** false при `organization_allows_writes = false` (касса hall-rent): occupancy-отмену персонала в suspended **не** обходить этим helper'ом. Worker по-прежнему истекает неоплаченные холды.

### 1.9. Пополнение баланса

1. Арендатор в Mini App: сумма → способ: **действующие QR** студии (можно сохранить на устройство) или **наличные**. Сумма > 0, в валюте org. Потолок **обязателен** (безлимит запрещён): стартовый CHECK `amount <= 1000000` в мажорных единицах org (`NUMERIC(12,2)`); продукт может поднять цифру, не снимать потолок. Одновременно **не больше одной** `pending` заявки на арендатора; повтор — отказ, пока не confirm/reject. Confirm/reject: `UPDATE … WHERE id = $1 AND status = 'pending' RETURNING *` (0 строк = no-op, не второй ledger).
2. Создаётся заявка `pending` в **отдельном** inbox пополнений Mini App (`renter_topup_requests` / `list_renter_topup_inbox`), не в очереди неоплаченных кассовых слотов `list_rental_payment_inbox`. Сумма как ввёл арендатор (сервер округляет до minor; клиентскую валюту не принимать).
3. Кнопка открывает Telegram-чат студии. Ссылку задаёт owner/director в CRM: только `https://t.me/<username>` (5–32 символа `[A-Za-z0-9_]`) или `https://t.me/+<invite>` / `https://t.me/joinchat/<hash>` или `tg://resolve?domain=<username>` / `tg://user?id=<digits>`. **Не** `t.me/share`, `/iv`, произвольный path, любой другой `tg://`, `javascript:`, произвольный http. В Mini App открывать через `Telegram.WebApp.openTelegramLink` **только** после серверного allowlist (не сырой ввод пользователя). Чек или сообщение — в этот чат. Пока канал только Telegram.
4. Owner / director / accountant / полный admin с `rentals.payments.write` подтверждает, отклоняет или **меняет сумму**. Подтверждение — кассовая операция: `operation_date` = **сегодня в TZ организации на сервере**, не дата с клиента (иначе обход закрытого периода). Запрет при закрытом периоде (`finance_period_closed_until`, HALL-RENT-9), плюс `operation_idempotency`. Если **сегодня** уже закрыто — отказ (не «завтрашняя» дата с клиента). Повторный confirm/reject той же заявки — **no-op** (не второй ledger `topup`). В аудит — сумма заявки и сумма факт (если staff изменил).
5. Персонал с тем же `rentals.payments.write` может зачислить кошелёк **без** заявки Mini App (арендатор в студии / модуль выкл.): тот же ledger `topup` + строка `rental_advances` **без** allocation на `rental_invoices`. Не `record_rental_payment` на Mini App-слот и не кассовый allocate аванса на счёт 2.5. Тот же HALL-RENT-9 / `operation_date` с сервера. Teacher / reception — нет.
6. Подтверждение / staff-topup → зачисление на аванс (кассовый inflow) → погашение долга целиком при достаточном `spendable` → автоактивация холдов по FIFO (§1.6). Отклонение → уведомление арендатору в Telegram.

QR: owner/director загружают несколько макетов (`can_manage_settings`), отмечают **действующие**, могут добавить новые. Accountant видит hall-rent, но QR и токен бота не пишет. Один файл не копировать «на каждую задачу» — выбор из библиотеки. При замене/удалении объект в Storage **удаляется**, **кроме** пока на `qr_asset_id` висит `pending` заявка (§5.5). Повторный confirm/reject той же заявки — **no-op** (не второй `topup` / не второй reject-уведомление).

### 1.10. Надёжность (антифрод холдами)

В знаменателе **терминальные** исходы по холду, не отмены и не used после занятия:

- **on_time:** бронь дошла до `prepaid_charged` и далее до `settled` или `debt` (предоплата 50 % внесена вовремя / успешное списание по §1.6). Отмена после предоплаты **исключает** запись из знаменателя (не on_time и не untimely).
- **untimely:** **автоудалённые** за неоплату: истечение таймера холда в `awaiting_payment`; **и** catch-up §4.1 п.3 (`active` без charge уже после `time_start`, слот ещё идёт → `auto_deleted`). Не ставить `untimely++`, если в момент тика `organization_allows_writes = false` **или** add-on Mini App неактивен **или** кассовый период закрыт на «сегодня» org (`finance_period_closed_until`, HALL-RENT-9): confirm topup и staff-topup оба отказаны — арендатор не мог получить зачисление; иначе бан за закрытую кассу. Зал всё равно освобождается. Наличие `pending` заявки **без** закрытого периода **не** отменяет `untimely++` (персонал мог confirm).

Не untimely (и не on_time): catch-up §4.1 п.2 — `active` без charge **после** `time_end` → `debt` на всю `cost` (зал уже использован, это долг, не просрок холда). `hold_deleted`, отмена арендатором/персоналом, успешное прохождение пакета — вне знаменателя.

Вторая половина после занятия на счётчик **не** влияет. Не инкрементировать on_time в момент активации — только в терминальном успешном исходе; иначе отмена после предоплаты раздует on_time.

Пороги при **минимум 4** завершённых; проверять **от большего**: сначала 75 %, иначе 50 % (не два независимых `if`).

| Доля автоудалённых | Действие |
|---|---|
| ≥ 50 % | арендатору назначается **отдельный тариф штрафника** (ставка часа на локацию). Нет актуальной ставки `penalty` по локации — штрафник **не** ставить молча: алерт owner (локация Mini App обязана иметь все 3 kind, §4.3); worker **не** роняет весь maintenance tick |
| ≥ 75 % | **запрет брони**; все будущие Mini App-записи отменяются (§1.8), пакеты **рано** закрываются (будущее удаляется + пересчёт used). Порог 75 % **включает** правило 50 % (штрафник тоже действует, пока бан не снят). Нет ставки `penalty` — бан и отмена будущего **всё равно**; surcharge used без `max(one_time, penalty)` остаётся на snapshot; алерт owner. Не откатывать бан из‑за дырки в прайсе |

Снять запрет и **обнулить** счётчик могут только owner и director вручную. Сброс также снимает штрафник (`penalty_tariff_applied_at = NULL`). Уже прошедшие слоты и деньги не пересчитывать.

Долг (вторая половина) сам по себе запрещает новые брони, пока не погашен.

### 1.11. Уведомления в Telegram (бот студии)

- заявка на пополнение создана / подтверждена / отклонена (сумма факт);
- холд «ожидает оплаты» и сколько **времени** до автоудаления (таймер может быть короче 24 ч из‑за `min(..., time_start)`);
- бронь активирована;
- предоплата не списалась за 24 ч до начала — снова ожидает оплаты;
- предоплата выросла из‑за штрафника — слот снова ожидает оплаты;
- автоудаление (разовое и с будущим пакетом — по фактически удаленным датам; остальные даты пакета не трогать, кроме раннего закрытия последней будущей даты §1.5);
- долг начислен / погашен;
- запрет брони / тариф штрафника / снятие бана;
- персонал отменил бронь.

Исходящие `sendMessage` — **не** считать открытие Direct Link Mini App стартом диалога с ботом: ссылка `t.me/<bot>/<app>?startapp=` **не** шлёт `/start` и не создаёт private chat (Bot API: без chat_id / 403 `bot can't initiate conversation`). Формулировка доки «Mini App has no access to the chat» — про сообщения **от имени пользователя**, не про `sendMessage` бота; практическое правило то же: нужен Start. **Send** — только если private chat уже есть: Start / входящее `message` на webhook / `my_chat_member` member (`bot_started_at` в `renter_telegram_dialog`). `user.allows_write_to_pm` / успешный `requestWriteAccess` — согласие и UX, **не** замена Start (mint с флагом без `/start` всё равно 403). Заблокировал бота (`kicked`/`blocked`) — не слать. Иначе enqueue + backoff (в т.ч. HTTP 429) и UI «откройте бота студии». При первом открытии Mini App вызвать `requestWriteAccess` (не полагаться на Direct Link; `initData` при этом запуске **не** обновится — persist `allows_write` с HMAC на следующем mint или не считать его достаточным для send). Первое успешное auth Mini App = согласие на **сервисные** уведомления (не маркетинг); доставка всё равно требует старта бота. Без chat_id / при 403 от API не ретраить бесконечно. RPC брони **не** вызывает Bot API (только enqueue). Текст outbox — **без** `parse_mode` HTML/Markdown (или обязательный escape): `display_name` / суммы не должны ломать разметку. Потолок текста Bot API **4096** — обрезка на enqueue. Outbox: конечное число попыток + dead-letter (не бесконечный backoff на 403 / `bot can't initiate conversation` / chat not found). `sendMessage` в private: `chat_id` = `telegram_id` (`user.id`). Писать `allows_write_to_pm` / факт Start с HMAC-verified `user` при mint **и** с webhook (`message` / `my_chat_member`); persist — таблица `renter_telegram_dialog` на `(organization_id, telegram_id)` (§5.2), не только колонки `renters` (Start бывает до INSERT карточки); при block бота — не ретраить. `setWebhook allowed_updates`: `message` + `my_chat_member` (не все типы — меньше PII). Кнопка меню BotFather — тоже с `startapp=<organization_id>`, иначе `start_param` пустой и mint откажет.

### 1.12. Платный модуль Mini App + бот

- Оплата **ежемесячная**, старт заявки **в CRM** (как лицензия: сумма, QR **платформы** / процесс владельца продукта — не QR студии из §1.9). Переиспользовать `submit-purchase-request` / `platform_purchase_requests`, **не** второй платформенный inbox. В таблице сейчас **нет** типа заявки — добавить `request_kind` (`crm_license` \| `renter_miniapp_addon`), default `crm_license` для существующих строк. **Kind ставит Edge**, не клиент: в body `submit-purchase-request` — узкий enum; прямой `INSERT` `authenticated` (RLS owner/director уже есть) **не** должен уметь выставить `renter_miniapp_addon` и **не** подменять Mini App-оплату на `crm_license` (иначе lifetime CRM по цене add-on). Add-on INSERT — `service_role` / тот же Edge. Активация add-on **не** должна включать CRM: сейчас `dev-console-purchase-inbox` `activate` **всегда** вставляет consumed lifetime `access_keys`, ставит `organizations.status = licensed`, upsert `organization_licenses` и отдаёт plaintext-ключ в UI. Для `renter_miniapp_addon` эта ветка **целиком запрещена**: писать только период в `organization_addons`, без `access_keys` / без смены `organizations.status` / без `organization_licenses`. Иначе клик «активировать Mini App» на демо выдаёт **бесплатную lifetime CRM**. Тема/текст email разработчику и UI Inbox **ветвить** по `request_kind` (сейчас функция всегда пишет «полную версию»; kind не из комментария пользователя). Add-on доступен только org со статусом `licensed` (не способ обойти демо).
- Developer / администратор платформы в **Dev Console** видит, активирует, правит, приостанавливает период add-on.
- Модуль неактивен: Mini App **create** (самообслуживание и ручная бронь персонала этим каналом) и исходящий бот **не работают**. **Отмена / удаление холда своих** слотов из Mini App — **да** (иначе холд и 50 % зависают до оплаты add-on). Поэтому **mint JWT** для **уже существующей** пары `(organization_id, telegram_id)` при выкл. add-on — **да**; саморегистрация (INSERT новой карточки) — **нет**. Иначе после истечения сессии арендатор не войдёт отменить холд. Касса hall-rent 2.5 от add-on **не** зависит. Inbox пополнений, кошелёк, staff-topup и история в CRM **доступны** персоналу (иначе зависают pending и долги). Worker **продолжает** истечение холдов, T−24 ч, remainder/debt, catch-up (иначе `confirmed`-холды вечно занимают зал), но **`untimely++` не ставит** (арендатор не мог topup из Mini App). Occupancy-отмена персонала в CRM уже существующих слотов — да. `renter_submit_topup` при выкл. модуле — нет (staff-topup да).

### 1.13. Кабинет студии

- Owner / director / полный admin: список арендаторов, сетка (в т.ч. холды), карточка, надёжность, ручная бронь канала Mini App.
- Accountant и полный admin с `rentals.payments.write`: баланс, даты пополнений и списаний, задолженности Mini App (`debt_amount`, не кассовый `financial_debtors_v`), заявки на пополнение, статус надёжности (read). Сводка долгов Mini App — отдельный список/блок на карточке и в inbox пополнений, **не** через `financial_debtors_v` (там фильтр `channel = cashier`). Сетку уроков accountant по-прежнему не видит (нет operational read). Accountant не создаёт и не отменяет слоты Mini App.

## 3. Рекомендации по реализации

1. **Не возвращать Telegram-login в CRM команды.** Отдельный Edge Function только для арендатора (`renter-telegram-auth`: `verify_jwt = false`, секрет — HMAC `initData`, не `CRON_SECRET` и не `service_role` в ответе). CORS — **только origin Mini App** (не CRM, не `*`) **и только на этой функции**. Origin Mini App **не** добавлять в общий `ALLOWED_ORIGINS` (`tangodb/supabase/functions/_shared/http.ts`): иначе браузер кабинета вызовет `create-self-service-demo-org` / activate-key / recover. Свой allowlist только у `renter-telegram-auth`. Actor-check на CRM Edge всё равно обязателен (CORS не закрывает curl). Webhook Telegram и cron-worker **не** копируют этот CORS: у `api.telegram.org` / pg_net нет Mini App `Origin` (webhook без Origin; worker — как GCAL-3, секрет в заголовке). Потолок тела запроса (initData + JSON) — жёсткий (десятки КБ). HMAC `initData` по [Validating data received via the Mini App](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app): `secret_key = HMAC-SHA256(key = UTF-8 "WebAppData", message = bot_token)`, затем `hex(HMAC-SHA256(key = secret_key, message = data_check_string))`. Сравнение hash — **constant-time** (равной длины; иначе generic fail). Не наоборот (`bot_token` как key): псевдокод Telegram пишет `HMAC_SHA256(data, key)`, это не `hmac.new(key, msg)`. Не принимать hash Login Widget (другой ключ: SHA256(token), не `WebAppData`). **data-check-string (HMAC):** все поля **кроме `hash`**, ключи отсортированы **ordinal/byte** (`a < b` / Python default; **не** `String.localeCompare` — даёт `bad_hash`), `key=` + значение после **одного** URL-decode query-string (как `URLSearchParams` / `parse_qsl`); **не** `JSON.parse`/`stringify` поля `user` до HMAC. В check-string входят `start_param` и **`signature`, если поле есть**. Выкидывание `signature` из HMAC даёт `bad_hash` на живом initData Bot API 8.0+. Старые клиенты без поля `signature` — строка **без** него (не подставлять пустой `signature=`). Исключать `signature` из HMAC **нельзя** — это правило [Ed25519 third-party](https://core.telegram.org/bots/webapps#validating-data-for-third-party-use) (`except hash and signature` + префикс `bot_id:WebAppData`). Поле `signature` — Bot API **8.0+**. Мы **не** проверяем Ed25519 (есть bot token). Секрет — **бот этой org** из подписанного `start_param`, не перебор всех org. `start_param` после HMAC — UUID. Не читать `initDataUnsafe` и не `tgWebAppStartParam` (GET без HMAC). Пустой `initData` (обычный браузер) — отказ; входа по email/password / `signUp` на origin `tangodb-renter` нет. Нет `user` / `user.is_bot` / `user.id` не целое ≤ 0 — отказ. Identity только `user.id`, не `chat.id` / `receiver`. `photo_url` не хранить (SVG с t.me). `auth_date`: mint по initData только если не старше **10 минут**; `auth_date` в будущем больше чем на **60 с** — отказ (скос часов сервера). Окно 24 ч — replay украденного initData. **Повтор того же hash при свежем `auth_date` (≤ 10 мин) — идемпотентный mint** той же пары org+telegram (вернуть/обновить сессию, не второй `auth.users` и не отказ): React Strict Mode / retry сети иначе ломают вход. Свежесть = только `auth_date` ≤ 10 мин, не TTL строки хеша. Идемпотентность **только по hash недостаточна**: два открытия подряд дают разный `auth_date` → разный hash → два параллельных mint без строки renter создадут **два** `auth.users`. **Не** «один SECURITY DEFINER RPC, внутри которого createUser»: GoTrue вне Postgres, а hosted pooler (Supavisor **transaction mode**) **не держит** session-level `pg_advisory_lock` между HTTP-вызовами. Порядок: (1) RPC под `pg_advisory_xact_lock` пары `(organization_id, telegram_id)` — `INSERT` карточки / no-op по partial unique, вернуть `auth_user_id`; (2) если `auth_user_id` уже есть — сессия этому user, **не** `createUser`; (3) если NULL — Edge `createUser`, затем RPC `UPDATE renters SET auth_user_id = $uid WHERE … AND auth_user_id IS NULL`; 0 обновлённых строк → проигравшая гонка, **`auth.admin.deleteUser` orphan** (нет других ссылок). Существующий `auth_user_id` переиспользовать; новый hash ≠ новый user. Повторный mint существующего user **не** ротирует пароль GoTrue (иначе выбивает второе устройство). Edge не вызывает два `createUser` «на всякий случай». TTL **сессии GoTrue отдельно**. **Не менять глобальные** `jwt_expiry` / `timebox` проекта ради Mini App (сломает CRM; сейчас час + `timebox` 24h S12). Украденный refresh живёт до timebox — поэтому окно initData 10 мин. Revoke при бане/архиве/blocked (S29 `revoke_auth_sessions_for_user`) **выбивает кэш сессии**, не запрещает повторный mint: кабинет нужен для долга и холдов; create всё равно RPC-gate. Хеш initData для идемпотентности — TTL ~15 мин (буфер хранения строки после окна `auth_date`, не второй порог свежести), не вечная таблица. JWT с `app_metadata.actor = renter`, без членства в команде. `renter_id` / `telegram_id` / org — **только** `app_metadata`, не top-level claims и **не** `user_metadata` (клиентский `updateUser` пишет user_metadata). `app_metadata` с клиента не меняется. Не переиспользовать synthetic email `tg_{id}@tangodb.auth` и не угадываемый `renter+id+org@…` (§1.2). `auth.admin.createUser` с `email_confirm: true` (S12); пароль — CSPRNG, не производная от telegram_id; recovery/reset с клиента Mini App нет; **Edge `create-self-service-demo-org` / activate-key / accept-invite / recover / reset-password при `actor=renter` — отказ** (иначе renter JWT с подтверждённым `@users.invalid` сегодня создаёт демо-CRM). Повторный вход только через эту функцию. Ответ — JSON body с access/refresh **сессии GoTrue** (не redirect `?access_token=` / fragment: Telegram и Referer сольют токен). Не ручная подпись JWT и не `service_role`. Email `@users.invalid` проверить на первом mint (GoTrue `mail.ParseAddress` его принимает; если hosted отклонит TLD — домен платформы, не угадываемый local-part). InitData, bot token, hash, `webhook_token` **не** логировать (URL Mini App тоже: initData бывает во fragment). Клиент Mini App: `Referrer-Policy: no-referrer`; **без** аналитики CRM / Sentry-PII / третьих скриптов, куда уедет initData. Все пороги слота (`now` vs `time_start` / T−24 / `hold_expires_at` / `time_end`) — **`now()` Postgres в RPC**, не часы Edge/клиента (HMAC `auth_date` — исключение, на Edge). Rate-limit через `check_edge_rate_limit` (S13), не in-memory Map: **сначала IP** (до HMAC; `telegram_id` из неподписанного тела не ключ); после успешного HMAC — ещё `telegram_id`+org. Лимит IP не душит легитимных за NAT — порог как у других публичных Edge (S13), не «1/мин». Неизвестная org / нет токена бота / плохой HMAC / протухший auth_date / add-on выкл. для **новой** карточки / `organization_allows_writes=false` — **один** generic ответ и **один** путь dummy HMAC (не светить «орг без бота» vs «орг с ботом» разным timing). Mint при выкл. add-on: существующая карточка — да; INSERT — нет (§1.12). Нет строки add-on / статус ≠ active — **fail-closed как выкл.** (этап 3 без этапа 6 не открывает create).
2. **Не класть арендатора в `organization_members` и не в `user_active_organizations`.** Иначе хук выставит `claims.organization_id`. Сейчас `auth_organization_id()` (S29) требует **и** claim, **и** активный member — renter без member получит NULL даже с подставленным claim; этого **мало**. Другие политики/RPC могут читать claim напрямую; invite угадываемого email сделает renter ещё и member. Хук: при `app_metadata.actor = renter` — **не** читать uao **даже если строка member есть**, **не** писать `organization_id` / `member_id` / `member_role`, **стереть** top-level `organization_id` если вдруг есть, **не** затирать `actor`, **не** возвращать copy `telegram_id` в top-level claims (S39 это уже снял). Хук **не** пересобирает `claims` с нуля и **не** дропает `app_metadata` (иначе renter-RPC потеряют `actor` на refresh). Org/`renter_id`/`telegram_id` остаются в `app_metadata`. CRM SQL **никогда** не берёт org из `app_metadata` (только `auth_organization_id()`). Renter-RPC **не** вызывают `auth_organization_id()` — `auth_renter_id()` / org из `app_metadata`, сверка карточки `(organization_id, telegram_id)`; карточка не найдена или `telegram_id` не совпал — отказ, **без fallback** на `renter_id` из JWT (stale после склейки/очистки). Id из аргументов клиента не доверять. Роль JWT = `authenticated`: **тот же** роль, что у команды — `REVOKE EXECUTE` с `create_rental` и пр. **невозможен** без поломки CRM. Защита: fail-closed RPC при NULL `auth_organization_id()`, табличный RLS на `auth_organization_id()` + member helpers (сейчас `renters`/`rentals` так и устроены), **нет** политик `auth.uid() IS NOT NULL` без org. Новые таблицы кошелька/заявок: `auto_expose_new_tables = false` (S27); **только** `GRANT EXECUTE` на SECURITY DEFINER RPC (`search_path = public, pg_temp` / `public, auth` как касса), **без** `GRANT SELECT` `authenticated` на ledger/outbox/topup. Тесты: renter JWT вызывает `create_rental` / `list_rental_payment_inbox` / `get_client_card` / `set_active_organization` / **staff** `get_renter_detail` / `list_renters` / `list_renter_rentals` / `prepare_renter_document_upload` / `upsert_renter` / `create_renter` / SELECT `rentals`/`clients`/`payments`/`renters` / `financial_debtors_v` (view `security_invoker=false`, фильтр `auth_organization_id()` — при NULL org пусто; если какой-то view без org-фильтра — чинить **до** mint) / Storage / GraphQL (`graphql_public` выкл. S34 — не включать) / Edge `create-self-service-demo-org` / activate-key / recover / **и любой другой Edge с Bearer/`verify_jwt=true`, что гейтит только `getUser()` без member/actor** → отказ или пусто. Имена RPC кабинета (`renter_*` §5.3) **не** reuse staff hall-rent (`get_renter_detail` и т.п.). Триггер `organization_members` INSERT: смотрит `auth.users.raw_app_meta_data->>'actor'` **вставляемого `NEW.user_id`**, не JWT вызывающего (иначе owner/service_role INSERT обойдёт). И accept-invite Edge отказывает `actor=renter` до INSERT. Realtime: новые таблицы **не** добавлять в publication `supabase_realtime`; уже опубликованные операционные — RLS fail-closed, renter не подписан. Storage: actor=renter без upload; **до mint** инвентаризация Storage policies (`auth.uid() IS NOT NULL` без org — дыра). `GRANT SELECT ON renters TO authenticated` (S17) закрывается RLS — регрессионный тест обязателен. **До первого mint в проде:** инвентаризация всех `GRANT EXECUTE … TO authenticated` — любой SECURITY DEFINER, который гейтит только `auth.uid() IS NOT NULL` без org/member, дырявый для renter JWT; чинить fail-closed, не ограничиваться списком из этого абзаца.
3. **Кошелёк как ledger поверх авансов**, а не вторая «игрушечная» сумма в JSON. Подтверждённое пополнение = строка `rental_advances` (**это** кассовый inflow в `rental_money_register_v`, `advance_received` или тот же смысл) **плюс** строка ledger `topup` (только кошелёк, **не** второй UNION в регистр). Списания 50/50, refund на кошелёк, `debt_settle`, surcharge, remainder — **движения кошелька / признание**, не второй кассовый приход (аналог исключённых HALL-RENT-5 `rental_advance_allocations`). Иначе topup + charge удвоят выручку. Возврат денег с кошелька наружу (выдача наличных арендатору) — вне этой спеки. Стартовый баланс: одноразовый backfill = **перевод**, не копия: нераспределённый остаток (`amount − allocated_amount`) → ledger `topup`, затем `allocated_amount = amount` (или эквивалентный sink), чтобы касса 2.5 не allocate'ила те же деньги на счёт. Allocation на счета 2.5, уже сделанная до backfill, в кошелёк не входит. Backfill **не** создаёт новую кассовую строку (деньги уже в регистре). После включения канала allocate нераспределённого аванса «мимо» кошелька — отказ (или обязательный debit ledger).
4. **FIFO при активации обязательно.** Иначе 50 % одной брони визуально «оплатят» десяток холдов (§1.6 допускает **разовое** создание без денег, но не двойную активацию; пакет без полной активации — ROLLBACK §1.5). Пока есть долг — не кормить FIFO **новыми** активациями; уже `active` не деактивировать из‑за долга; T−24 ч по ним идёт. `debt_settle` / `surcharge` / **remainder** не тратят `reserved_prepay`. Пересчёт кошелька сериализовать advisory lock на `(organization_id, renter_id)` **после** слотовых локов §3 п.9, иначе два topup/worker гонки дважды активируют. FIFO **не** активирует `awaiting_payment` при `now ≥ time_start` или `now ≥ hold_expires_at` (§1.6 / §4.1). FIFO create пакета учитывает уже висящие **свои** разовые холды того же арендатора (они раньше в сортировке) — пакет может ROLLBACK из‑за их `awaiting_payment`; это ожидаемо, не баг.

## 4. Логика: состояния, деньги, конфликты

### 4.1. Жизненный цикл слота

```
create ─► awaiting_payment ─► (available ≥ 50% FIFO) ─► active
                │                      │                     │
                │                      │ внутри окна 1–24ч:   │ T−24ч (или сразу в том же RPC, если слот <24ч)
                │                      │ charge сразу         │
                │ таймер холда без 50% │                     ▼
                │                      └──────────────► prepaid_charged
                ▼                                        │
           auto_deleted                                  ├─ cancel now < time_start−24h: refund 50% если списаны, cancelled
           (слот свободен,                               ├─ cancel now ≥ time_start−24h и now < time_start: удержать 50% (charge если ещё нет), cancelled
            untimely++)                                  ├─ списание T−24ч не удалось и now < time_start
                                                         │     ─► awaiting_payment (новый таймер)
                                                         ├─ now ≥ time_start и ещё active без charge:
                                                         │     catch-up § ниже (не ждать «вечный» awaiting)
                                                         └─ time_end:
                                                              ├─ списать remainder → settled
                                                              └─ не хватает → debt, remainder не списан

awaiting_payment ─ (удалить холд / occupancy-отмена без prepay) ► hold_deleted (не untimely)
```

Occupancy (`booking_status = confirmed`): `awaiting_payment`, `active`, `prepaid_charged`, `settled`, `debt`. `cancelled` / `auto_deleted` / `hold_deleted` → `booking_status = cancelled`, зал свободен. `settled`/`debt` занимают **свой прошедший** интервал (история, rose у `debt`); новая бронь на будущее с ними не пересекается. Не утверждать, что `settled` «не занимает» в смысле `booking_status` — иначе расходится с conflict RPC.

Удаление холда: только `awaiting_payment` без списанной предоплаты → слот свободен, в untimely не идёт.

**Таймер холда** (`hold_expires_at`) — **истекшие часы** (`timestamptz`), не календарные сутки в TZ:

- Первичный: `created_at + 24h`, не сдвигать при каждом FIFO-пересчёте, пока статус `awaiting_payment`.
- Не держать зал после начала без оплаты: `hold_expires_at = min(created_at + 24h, time_start_timestamptz)`.
- Сбой charge из `active` при `now < time_start`: `awaiting_payment`, новый `hold_expires_at = min(now + 24h, time_start)`. `prepaid_charged` так не откатывать (деньги уже списаны; сбой remainder → `debt`). Если `now ≥ time_start` — не awaiting, а catch-up (п.2–3 ниже).
- Рост `prepay` из‑за штрафника (§4.3) при `active` без charge: переход в `awaiting_payment`, резерв снимается, FIFO заново. **Не** ставить `hold_expires_at = now+24h` (штрафник не должен продлевать lock зала). Сохранить прежний `hold_expires_at`, если он ещё в будущем; `min(now + 24h, time_start)` — только fail-safe, если expiry NULL или уже в прошлом. Если `now ≥ time_start` — catch-up, не awaiting. Уже `awaiting_payment`: обновить snapshot, **таймер не сбрасывать**.
- Истечение в `awaiting_payment` → `auto_deleted`; `untimely++` только если `organization_allows_writes` **и** add-on активен **и** кассовый период на «сегодня» org **не** закрыт.
- Наследование expiry при recreate после `hold_deleted` — §1.8.
- FIFO не трогает холд после `time_start` / после `hold_expires_at` (§4.2).

**Catch-up worker** (тик пропущен). Правила **по порядку в одном проходе** (строка может сменить фазу дважды за тик):

1. `awaiting_payment` ∧ (`now ≥ hold_expires_at` **или** `now ≥ time_start`) → `auto_deleted`; `untimely++` **только если** `organization_allows_writes` **и** add-on активен **и** кассовый период на «сегодня» org **не** закрыт (иначе зал освободить без бана за простой / выкл. модуль / закрытую кассу). Вторая ветка — fail-safe, если `hold_expires_at` ошибочно позже старта;
2. `active` ∧ `now ≥ time_end` → **не** `auto_deleted` (зал уже был занят, это не просрок холда). Списать prepay если ещё нет, затем remainder; prepay не прошёл → `debt` с `debt_amount = cost`, без `untimely++`; prepay прошёл, remainder нет → обычный `debt` на remainder;
3. `active` ∧ `now ≥ time_start` ∧ `now < time_end` → списать prepay; неудача → `auto_deleted` + `untimely++` только если `organization_allows_writes` **и** add-on активен **и** период не закрыт (не оставлять `active` после старта без charge и не возвращать в `awaiting_payment`). Арендатор в этом окне **не** вызывает cancel. Occupancy персонала после старта — §1.8 (удержать 50 %, remainder нет), не кассовый refund.
4. `active` ∧ `now ≥ time_start − 24h` ∧ `now < time_start` → списать prepay (как T−24 ч); неудача → `awaiting_payment`, новый таймер §4.1. Если этот тик — следствие FIFO/topup, предпочитать charge уже в RPC активации (§1.6), не ждать worker.
5. `prepaid_charged` ∧ `now ≥ time_end` → remainder / `debt`.

### 4.2. FIFO активации

```
wallet_balance     = сумма ledger (topup − prepay_charge − remainder_charge − debt_settle − surcharge + refund …)
                     (при включении контура: + backfill нераспределённых кассовых авансов, §3 п.3)
reserved_prepay    = Σ prepay по lifecycle = active и prepay_charged_at IS NULL
debt_outstanding   = Σ debt_amount по Mini App rentals этого renter
spendable          = wallet_balance − reserved_prepay     // не отрицательный; для debt_settle, surcharge и remainder
available          = 0, если debt_outstanding > 0
                   = spendable  иначе
инвариант          = wallet_balance >= reserved_prepay
```

Брони арендатора в `awaiting_payment` или `active` без списанной предоплаты, сортировка `(rental_date, time_start, created_at)`. **Пропуск:** `now ≥ time_start` или `now ≥ hold_expires_at` (не активировать просроченное; worker §4.1). Также пропуск, если `available = 0` из‑за долга (новые активации).

- если кандидат и `available >= prepay` → активация: если `now` уже в окне 1–24 ч до старта — сразу charge (§1.6 п.2); иначе `active`, `available -= prepay` (резерв вычисляемый);
- иначе `awaiting_payment`, `hold_expires_at` по §4.1 (не продлевать).

Погашение долгов — отдельный проход **до** FIFO: слоты с `debt_amount > 0`, сортировка `(time_end, created_at)`, целиком один слот за шаг, пока `spendable >= debt_amount`.

Remainder в `time_end` — из `spendable` (как `debt_settle`), не из `wallet_balance`. Нехватка → `debt_amount +=` непокрытый remainder, кошелёк не отрицательный.

Cancel внутри окна 24 ч (`now >= time_start − 24h`) из `active` без charge: списание prepay **обходит** `available = 0` (удержание по этой брони). Успех, если `wallet_balance >= prepay` этой строки (её же резерв в `reserved_prepay` это покрывает при инварианте). Чужой резерв не списывать: если `wallet_balance - (reserved_prepay − этот prepay) < этот prepay` → `cancelled` без charge. При живом инварианте неравенство **ложно всегда**. В минус не уходить.

Пересчёт: после пополнения, погашения долга, возврата, отмены, списания, смены штрафного тарифа — под **advisory lock** `(org, renter)`. Сначала `debt_settle` из `spendable`, потом FIFO. Появление долга **не** снимает уже выставленный резерв `active`; тик T−24 ч по таким слотам всё равно charge.

### 4.3. Стоимость

```
hours     = duration_minutes / 60
rate      = hour_rate(location, kind)     // kind = penalty, если penalty_tariff_applied_at задан,
                                         // иначе one_time | recurring; актуальная строка =
                                         // max(valid_from) среди valid_from ≤ rental_date;
                                         // при равном valid_from — max(created_at), затем id
cost      = hours * rate
prepay    = round_half_up(cost / 2, currency_minor)   // ISO minor: VND → 0 знаков
remainder = cost − prepay
```

`prepay + remainder = cost` всегда (не два независимых `cost / 2`). Валюта = `organization_settings.currency_code`; поле `currency` на ставках его дублирует, отдельной валюты зала нет. Нет ставки нужного kind на дату → RPC отказ.

Локация доступна каналу Mini App только если на дату брони есть актуальные строки **всех трёх** `kind` (`one_time`, `recurring`, `penalty`). Иначе create и apply-penalty не молчат с «нет ставки».

На create (и при обновлении штрафника до charge) пишется snapshot `cost` / `prepay` / `remainder` на occurrence (`fixed_amount` = `cost` для карточки сетки). Кассовые `paid_amount` / `payment_status` из 50/50 **не** вести: UI при `channel = miniapp` смотрит `lifecycle`, не кассовый unpaid. После `prepay_charged_at` snapshot заморожен (штрафник не пересчитывает уже списанные 50 % и не меняет `remainder` этой брони). До charge штрафник может обновить snapshot и вернуть `active` без charge в `awaiting_payment` (таймер §4.1) — резерв `reserved_prepay` с этой строки **снимается**, затем FIFO заново по новой prepay (иначе инвариант `wallet_balance >= reserved_prepay` ломается, когда prepay вырос). Уже `awaiting_payment`: тот же пересчёт snapshot, **без** нового `hold_expires_at`. Смена каталога ставок owner **не** трогает уже созданные слоты.

Доначисление только при **раннем** закрытии пакета (§1.5) — **дельта**, не повтор 50/50. Успешный `completed` (все даты used) — без surcharge. Ставка used: `one_time` на дату слота; если `penalty_tariff_applied_at` задан — `max(one_time, penalty)` (защита от дешёвого recurring **и** запрет скинуть штрафника до разового). На каждый used-слот `slot_delta = max(0, recalc_slot − already_charged_slot)` (already = prepay+remainder по ставке, по которой слот реально считали). `surcharge = Σ slot_delta`. Ledger `surcharge_one_time_recalc`: идти по слотам `(rental_date, time_start)`; с каждого `slot_delta` сначала `spendable` (не ниже 0), остаток в `debt_amount` **этого** слота. Не сваливать всю дельту на один rental (иначе FIFO `debt_settle` и карточка врут). Без отрицательного кошелька и без ledger на невзятую часть. Это тот же Mini App-долг, что блокирует новые брони.

### 4.4. Конфликт с уроком студии

Текущий `schedule_location_has_conflict` уже запрещает пересечение group / personal / event / rental (`confirmed`).

Закреплено продуктом:

- арендатор видит уроки как «Занято» и не бронирует поверх;
- студия не создаёт урок поверх аренды;
- исключение: owner / director / **полный operational admin** **отменяют** бронь арендатора канала Mini App (деньги §1.8, не кассовый financial_action), затем ставят урок;
- accountant Mini App occupancy не отменяет. Gate — `member_can_manage_rentals()`, не `member_can_create_rental()` / UI `rentals.write`. HALL-RENT-23 (`cancel_rental` для accountant) остаётся для кассовых слотов 2.5 (`channel = cashier`);
- преподаватель в CRM ставит уроки как сейчас, не как аренду; в Mini App тот же человек — арендатор на **свободное** время.

Двойная роль не сливает баланс аренды с зарплатой и не делает урок списанием с кошелька.

### 4.5. Ограничения создания

Отказ RPC (и сообщение в Mini App), если:

- модуль Mini App неактивен — **create** самообслуживания и ручная бронь **этого** канала; персонал в кассе 2.5 работает; inbox/кошелёк / staff-topup в CRM — да; worker по уже созданным — да (**без** `untimely++`); **renter cancel / delete_hold своих** — да; mint существующей карточки — да; INSERT новой — нет; `renter_submit_topup` — нет;
- org не проходит `organization_allows_writes` — create/topup/auth mint (в т.ч. существующей карточки) нет; worker expiry — да, **без** `untimely++`;
- renter-cancel при `now ≥ time_start` (occupancy персонала до `time_end` — не этот отказ);
- `renters.status ≠ active` (кассовые archived/blocked) **или** `booking_banned_at IS NOT NULL` — **create**; mint существующей карточки при ban/archive/blocked — **да** (долг, холды, topup); revoke сессий не запрещает повторный mint;
- есть долг > 0;
- превышен любой из двух лимитов незавершённых слотов (§1.8);
- cooldown **пересекающегося** интервала **на той же локации** после `hold_deleted` / refund-`cancelled` / `cancelled` без charge;
- локация не `miniapp_enabled` или не той org (снятие флага **не** отменяет живые слоты; create на этот зал — отказ; occupancy кабинета зал не показывает; «Мои записи» — да);
- нет `telegram_id` на карточке (staff create);
- старт < now + 1 час (для пакета — любая дата; тогда весь пакет отклоняется);
- `time_end` ≤ `time_start` (слот не через полночь);
- разовое вне окна 3 недель;
- пакет: после вставки+FIFO хотя бы одна дата пакета всё ещё `awaiting_payment` (ROLLBACK §1.5);
- первая occurrence пакета вне окна 3 недель; `valid_from` ≠ дата первой occurrence;
- постоянная: `valid_to ≠ valid_from + 27 days`;
- сетка времени не 30 мин / длительность < 60 мин;
- конфликт слота;
- нет актуальной ставки часа нужного kind **или** локация без полного набора 3 kind.

`renter_get_occupancy`: диапазон дат **считать на сервере** в TZ организации (текущая пн–вс + две недели); параметры клиента, выходящие за окно, — clamp или отказ (иначе выгрузка сетки студии на год). Мастер пакета — **тот же** `renter_quote_booking` на `[valid_from, valid_to]` (макс. 28 дней, §1.5), busy/free без PII; не второе RPC и не occupancy на год. `location_id` не из канала / чужой org / не `miniapp_enabled` — **тот же** generic отказ, без «зал есть, но выкл.» vs «нет зала». Ответ — занято/свободно + **свои** слоты (id/lifecycle своих); без чужих `renter_id`, имён, сумм, `lifecycle` чужих. Не переиспользовать `get_rentals_for_schedule_week` (там PII). Predicate занятости = `schedule_location_has_conflict` (personal `cancelled_at IS NULL`, slots `valid_from`/`valid_to`, events, rentals `confirmed`) **плюс** `NOT EXISTS schedule_occurrence_cancellations` на дату (как `preview_calendar_event_conflicts`) — один helper на occupancy **и** create, чтобы сетка «свободно» не расходилась с RPC. Конфликт в ошибке create — без имени чужого арендатора. `renter_list_mine` / `renter_get_wallet` — пагинация или ограниченный горизонт (не годы одним RPC). Renter-RPC (occupancy/create/topup/quote) — rate-limit per `(organization_id, telegram_id)` после mint (SQL/`check_edge_rate_limit`), не безлимитный polling сетки.

Кабинет без отдельных RPC не собрать: `renter_bootstrap` (имя студии / `branding_name`, TZ, `currency_code`, locale, allowlisted chat URL, add-on active?; без токена бота и webhook), `renter_list_locations` (id/имя залов `miniapp_enabled` с 3 kind своей org), `renter_quote_booking` / цена в preview пакета (`cost` / `prepay` / `remainder` / kind актуальной ставки; без истории `valid_from` и без каталога выкл. залов), `renter_update_profile` (`display_name` ≤ 80, `contact_phone` через `normalize_renter_phone`; не HTML).

`renter_submit_topup` **гейтится add-on** (модуль выкл. → Mini App topup нет; staff-topup да). **Не** гейтится `status ≠ active` / баном: иначе нельзя закрыть долг с архивной карточки. Поэтому mint существующей при archive/ban — да (§4.5). **Create брони гейтится всеми:** add-on, `organization_allows_writes`, `status = active`, нет бана, нет долга (и двумя лимитами §1.8).

### 4.6. Надёжность (формулы)

```
completed = on_time + untimely_auto_deleted
ratio     = untimely_auto_deleted / completed   // если completed ≥ 4
              // expiry/catch-up no-pay при organization_allows_writes=false
              // или add-on выкл. или finance_period_closed «сегодня»
              // в untimely не входит (зал всё равно освобождается)

если ratio ≥ 0.75 → booking_banned_at = now()
                    revoke renter GoTrue sessions (S29)
                    apply penalty hour rates (если ещё не; нужны ставки penalty —
                    нет ставки: бан и отмена будущего всё равно, алерт owner)
                    cancel all future Mini App occurrences (§1.8), series.status = cancelled
                    (awaiting без prepay → hold_deleted; раннее закрытие пакета → пересчёт used §4.3)
иначе если ratio ≥ 0.50 → apply penalty hour rates
                    (нет ставки: алерт owner, штрафник не ставить;
                     worker не abort всего maintenance tick)
// on_time++ / untimely++ только вместе с идемпотентным терминальным
// переходом (ключ rental_id+phase); повтор worker не ++ повторно
```

`booking_banned` в тексте = `booking_banned_at IS NOT NULL`.

Снятие бана owner/director: `booking_banned_at = NULL`, `penalty_tariff_applied_at = NULL`, обнуление счётчика (`on_time` и `untimely` в 0). Уже прошедшие слоты в истории не стирать. Счета кассы 2.5 (`rental_invoices`) этот RPC **не** удаляет — у канала Mini App счетов нет.

### 5.9. Риски, которые уже закрыты правилами продукта

- Фиктивные холды, которые **истекают** → 24 ч + знаменатель автоудалений + бан. Остаточный риск: массовый `hold_deleted` до expiry в знаменатель не входит; **закрыто двумя лимитами** §1.8 (неоплаченные холды отдельно от paid pack), без отдельного знаменателя на delete.
- Обнуление таймера удали-и-создай тот же слот → наследование `hold_expires_at` (`hold_deleted`) **и** cooldown после refund-`cancelled` / `cancelled` без charge — на **пересечение** интервала **той же локации**, не только точный match и не на другой зал.
- Бронь → отмена ≥24 ч с возвратом (запирание зала чужим балансом) → лимит незавершённых + cooldown пересекающегося интервала.
- Пакет без денег → **ROLLBACK**, если после FIFO дата пакета в `awaiting_payment` (не 4 untimely и бан с первой попытки). Разовая без денег — по-прежнему.
- Дешёвая постоянная + **ранняя** отмена → пересчёт по разовому; то же, если вычистить все будущие даты по одной (`auto_deleted` последней будущей тоже). Успешный `completed` — без пересчёта.
- Двойная активация с одного баланса → FIFO. Активация в окне 24 ч → charge в том же RPC.
- Пополнения «мимо» долга в **новые** холды → `available = 0` пока `debt_outstanding > 0`; `debt_settle`/`surcharge`/`remainder` не едят `reserved_prepay`; already-`active` и их T−24 ч не откатывать.
- Урок «важнее» аренды без согласия → нет overwrite; occupancy Mini App не через кассовый `CancelRentalModal`.
- Путаница преподаватель/арендатор → разные приложения и JWT; запрет member для `actor=renter`.
- Просроченный модуль → create Mini App, INSERT и исходящий бот выключены; mint существующей карточки, cancel/delete_hold своих, worker, касса 2.5, inbox, staff-topup и история в CRM целы; **`untimely++` нет**.
- Одна сессия Telegram на все студии → user на пару org+telegram **и** `auth.storageKey` по org на общем origin.
- Add-on включает lifetime CRM → `request_kind` + activate **без** `access_keys` / **без** `organizations.status=licensed` / без `organization_licenses` + ветка письма.
- JWT арендатора открывает tenant RLS → хук не ставит org-claims при `actor=renter` (игнорирует uao); CRM SQL не читает org из `app_metadata`; renter-RPC без `auth_organization_id()`; RLS fail-closed; тесты вызова командных RPC. Не «REVOKE всех GRANT» — роль `authenticated` общая.
- Invite угадываемого renter-email в команду → непредсказуемый email + запрет member для actor=renter + хук.
- Replay initData / долгий refresh → окно 10 мин + **идемпотентный** hash **и** lock пары org+telegram (разный `auth_date` не плодит user) + проектный timebox 24h (не крутить глобальный `jwt_expiry`) + revoke при бане.
- Topup + 50/50 в регистре удваивают кассу → charge не inflow.
- Пропущенный worker после `time_end` при `active` → долг/settled, не бесплатный `auto_deleted` и не untimely.
- HMAC с перепутанным key/message → отказ; формула §3 п.1. **`signature` входит в HMAC-string** (исключать только `hash`; Bot API **8.0+**). Статьи, которые исключают `signature` из HMAC, расходятся с живым initData.
- `initDataUnsafe` / голый `?org=` / `tgWebAppStartParam` / `auth_date` старше 10 мин → отказ.
- Remainder/`debt_settle` съедают резерв чужого `active` → только `spendable`.
- Backfill кошелька + allocate 2.5 дважды → backfill = перевод (`allocated_amount = amount`).
- Холд Mini App в кассовом inbox/дебиторах → фильтр `channel = cashier`; долги Mini App — отдельный UI, не `financial_debtors_v`.
- Path-prefix Mini App на домене CRM → свой origin, не общий localStorage.
- Webhook `/bot/{bot_id}` → secret header + unguessable `webhook_token`.
- Токен бота в JSON CRM → маска, last-4; webhook_secret не в REST.
- Occupancy с произвольным диапазоном дат / PII → clamp 3 недели + свой RPC без имён; чужой `location_id` — generic.
- QR XSS / публичный bucket → raster only, signed URL через RPC, listing off, без Storage JWT арендатору.
- `javascript:` / произвольный `tg://` в ссылке чата → `https://t.me/<path>` / `tg://resolve` / `tg://user`.
- Direct Link Mini App без Start → не слать `sendMessage` без `bot_started_at` (`allows_write_to_pm` / `requestWriteAccess` не замена Start).
- Все залы студии «улице» → `miniapp_enabled`.
- Демо-орг через activate add-on → add-on не меняет лицензию CRM; Mini App на демо выкл., пока продукт не решит иначе.
- `prepaid_charged` отмена после старта снимает remainder → renter-cancel только до `time_start`.
- Повтор initData (retry) ломает вход → идемпотентный mint по hash, не отказ.
- Rate-limit по `telegram_id` до HMAC → ключ атакующего; сначала IP (`check_edge_rate_limit`).
- `untimely++` при suspended org **или** выкл. add-on → бан за простой студии / просроченный модуль; expiry без инкремента.
- Дедлок create vs worker → слоты по возрастанию, затем `(org, renter)`.
- `signUp` на origin Mini App / предсказуемый пароль GoTrue → нет signup; пароль CSPRNG; только mint.

### 5.10. Остаточные риски (приняты продуктом)

- Занятость уроков студии видна арендатору как «Занято» **на залах с `miniapp_enabled`** (без имён) — сознательная утечка сетки выбранного зала, не всей студии. Хвост чужого пакета за окном 3 недель в сетке не виден; create/preview пакета conflict-check все 4 недели.
- Refresh GoTrue до timebox 24h при украденной сессии; окно initData 10 мин закрывает только первичный mint.
- Массовый `hold_deleted` до expiry не в знаменателе — ограничен лимитом **неоплаченных** холдов (§1.8), не отдельным счётчиком.
- `organization_allows_writes=false`: mint нет (в т.ч. существующей карточки) — арендатор не отменит prepaid до возобновления writes; `member_can_manage_rentals()` тоже false — персонал occupancy Mini App в suspended не отменит. Worker снимает только неоплаченные холды, **без** `untimely++`.
- Google Calendar аренду не синкает (GCAL-0): преподаватель, смотрящий только Google, не видит холд Mini App; источник истины — сетка CRM.
- Кассовый `create_rental_series` лочит даты в порядке preview (не sorted) — **закрывается этапом 1** (выровнять на `(location_id, date)` до Mini App pack в проде). До выравнивания дедлок pack vs series возможен на staging.
- До 4 неоплаченных разовых холдов на 24 ч всё ещё возможны (порог unpaid); пакет без денег по-прежнему ROLLBACK.
- Кассовая дебиторка 2.5 на той же карточке не блокирует Mini App (только `debt_amount` канала); сознательно, не дыра RPC.

## 6. Допущения, зафиксированные при согласовании

1. Reception (`restricted_admin`) по-прежнему **вне** контура аренды.
2. Отмена occupancy Mini App = SQL `member_can_manage_rentals()` (owner / director / полный admin с `admin_can_edit_schedule`), **не** UI `rentals.write` и **не** `member_can_create_rental()` (accountant HALL-RENT-23). Деньги — §1.8, не кассовый `CancelRentalModal`. `cancel_rental` кассы при `channel = miniapp` (экв. `lifecycle IS NOT NULL`) отказывает **всем** ролям. HALL-RENT-23 только для кассы 2.5 (`channel = cashier`).
3. Пакет постоянной аренды = 28 календарных дней от **даты первой occurrence** (`valid_from`; `valid_to = valid_from + 27`); дни недели и часы задаёт арендатор (как сейчас patterns серии). Каждая дата — отдельный холд. Create пакета атомарный **и** ROLLBACK, если после FIFO любая дата пакета в `awaiting_payment`. Первая дата в окне 3 недель. **Раннее** закрытие (пересчёт used) — нет будущих дат **и** хотя бы одна снята `cancelled` / `hold_deleted` / `auto_deleted`; RPC: сначала будущее, потом surcharge. Все даты used → `completed` без пересчёта.
4. FIFO — правило реализации §1.6 (**разовая** без денег + пропорциональный порог 50 % × часы, вычисляемый резерв без таблицы soft-hold; пакет без полной активации — нет). Пока есть Mini App-долг, FIFO не тратит кошелёк на **новые** активации; already-`active` не трогать; `debt_settle`/`surcharge`/**remainder** только из `spendable`.
5. Счётчик в Mini App арендатору можно не выводить в первой поставке; в CRM — обязательно.
6. Исходящие уведомления шлёт **бот студии**, не платформенный бот TangoDB. Direct Link Mini App **не** стартует диалог; **send** только при `bot_started` (§6.31), не при одном `allows_write_to_pm`.
7. Валюта кошелька = `organization_settings.currency_code`.
8. Моменты `time_start` / `time_end` / окно сетки — в `organization_settings.timezone`. Длительности «24 часа» и «1 час» — elapsed на `timestamptz` (не календарные дни; DST не растягивает холд). Пороги vs `now` в RPC — **`now()` Postgres**, не часы клиента/Edge. Неделя Mini App = пн–вс (не номер ISO-недели); `week_starts_on` сетка CRM не использует — Mini App тоже нет.
9. Холд не переживает `time_start` без оплаты; сбой предоплаты в T−24 ч даёт новый таймер до `time_start`, не «вечный» `created_at + 24h` из прошлого. Граница удержания 50 % при отмене = граница charge: `now >= time_start − 24h`. Пропущенный тик после `time_end` при всё ещё `active` — долг/settled (§4.1), не `auto_deleted`. После `time_start` арендатор **не** отменяет (`prepaid_charged` / `active`); staff occupancy — §1.8 до `time_end`.
10. Кассовый контур 2.5 (`rental_tariffs`, счета, `create_rental`) и канал Mini App сосуществуют на одних `renters`/`rentals`; смешивать прайс и 50 % в одной форме нельзя. Саморегистрация не мержит кассовую карточку без `telegram_id`.
11. Сброс бана owner/director снимает и штрафник. Назначение бана **revoke** сессий renter (S29) — выбить устройства; повторный mint разрешён, create RPC-gate.
12. JWT арендатора не получает `claims.organization_id` (иначе часть кода прочитает claim в обход member-check). Хук игнорирует uao при `actor=renter`.
13. Подтверждение пополнения — кассовый inflow (HALL-RENT-9); charge 50/50 в регистр как кассу не писать повторно.
14. HMAC Mini App: key=`WebAppData`, message=`bot_token` (§3 п.1); исключать **только `hash`**; поле `signature` **входит** в HMAC (Bot API 8.0+; Ed25519 except hash+signature — другой контур). Один URL-decode query; не пересобирать JSON `user`; constant-time; повтор hash в окне — идемпотентный mint; `auth_date` ≤ 10 мин; не крутить глобальный `jwt_expiry`; не `initDataUnsafe`.
15. Occupancy-отмена Mini App в CRM — деньги §1.8, не кассовые financial actions.
16. Локация Mini App — `miniapp_enabled` **и** все 3 hour-rate kind; snapshot cost замораживается после charge; смена каталога owner не пересчитывает созданные слоты.
