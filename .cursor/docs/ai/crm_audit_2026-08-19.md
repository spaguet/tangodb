## Критичные

### C1. Оптимистичная посещаемость остаётся при ошибке RPC

**Где:** `tangodb/src/hooks/useAttendance.ts` (`useMarkAttendance`, ~342–539)  
**Также:** `tangodb/src/hooks/usePersonalLessons.ts` (`useMarkPersonalLessonAttendance`, ~582–632)

`mutationFn` при ошибке PostgREST/RPC **возвращает** `{ success: false }` и **не бросает**. `onMutate` уже обновил кэш (статус, `lessonsLeft`, `status: finished`). `onError` срабатывает только на throw, поэтому отката нет. `onSettled` инвалидирует кэш **только при** `result.success`.

UI показывает toast об ошибке, но список/счётчики остаются в оптимистичном состоянии до следующего успешного refetch. К посещаемости C1 относятся только:

- `AttendancePanel` `markAttendance.mutateAsync` ~722 (`!res.success`);
- `AttendancePanel` `markPersonalAttendance.mutateAsync` ~783 (`!res.success`);
- `PersonalLessonAttendanceActions.tsx` ~36–38.

Другие `res.success` в том же файле — **не** C1: ~761 `undoAttendance`, ~891 `recordSingleVisit`, ~935 `closeGroupLesson`, ~965 `reopenLessonClosure`.

**Последствие:** ложный «Пришёл», неверный остаток занятий, абонемент может оптимистично стать `finished`. Повторная отметка идёт уже от искажённого `oldStatus`.

**Как чинить (не сделано):** бросать ошибку из `mutationFn` **или** откатывать кэш в `onSettled`, если `success === false`.

## Высокие

### H1. `npm run lint` (`tsc --noEmit`) падает — 2 ошибки

`vite build` типы не проверяет (esbuild). CI/регрессия завязаны на `npm run lint`, сейчас он красный.

**1.** `tangodb/src/hooks/usePersonalLessonCharges.ts:69`

`netPaidForCharge` ждёт `PaymentWithCorrectionMeta[]`, а в query собирается урезанный объект `{ amount, operationKind, personalLessonChargeId }`.

На рантайме расчёт, скорее всего, работает: `paymentEffectiveAmount` читает только `amount` / `operationKind`. Это ошибка типов и хрупкий контракт.

**2.** `tangodb/src/pages/FinancePaymentsPage.tsx:260`

`formatPersonalPaymentLessonDuration` → `resolvePersonalPaymentLessonMinutes` → `lessonDurationMinutes` → `timeToMinutes` → `normalizeTime`. Второй аргумент типизирован как `{ timeStart, timeEnd }`, а `TeacherRevenueContext.personalLessonById` — как `Pick<PersonalLesson, "teacherMemberId" | "locationId" | "date">`.

Сейчас в Map кладётся **полный** `PersonalLesson`, поэтому на рантайме поля времени обычно есть. Если Map когда-нибудь сузят до объявленного Pick, `lesson` останется truthy без `timeStart`/`timeEnd`: `normalizeTime(undefined)` бросит `TypeError` на `.split` (`scheduleWeek.ts` ~38–45), не обязательно текст `Invalid HH:MM`. Страница «Платежи» упадёт на строке персонального урока без снимка `lessonDurationMinutes`. `resolvePersonalPaymentLessonMinutes` сначала берёт снимок длительности с платежа — падение только если снимка нет.

### H3. Версионирование группового слота: close без reopen на ветке successor

**Где:** `tangodb/src/hooks/useSchedule.ts` ~482–496

Путь «есть successor»: `closeScheduleSlotByDate` → `update` successor. При ошибке update слот уже закрыт (`valid_to`), откат `valid_to = null` **не делается**. Соседний путь insert (~510–520) reopen делает.

**Последствие:** занятие исчезает из сетки (тот же класс, что в `lessons.md` 2026-06-22 / 2026-06-30).

### H4. Query keys Google Calendar без `organizationId`

**Где:**

- `useGoogleCalendarIntegration.ts` — `["google-calendar", "accounts"]`, binding только по `memberId` (`membership?.id`)
- `useOrgGoogleCalendarIntegration.ts` — `["google-calendar", "org-binding"]`, `enabled: canManage` (не от `organizationId`). `canManage` = `role === "owner" || role === "director"`, а `role` из `usePermissions()` — тот же JWT-first, что **H10**
- `useTeamGoogleSyncStatus.ts` — `["google-calendar", "team-sync-metrics"]` / `org-sync-metrics`, `enabled: canViewTeam` (тот же JWT-first `role`)

Нет `useOrgQueryScope().withOrgId` / `enabled` от org. После смены организации TanStack может показать кэш предыдущей org (binding, метрики команды) до refetch.

Аккаунты пользователя (`accounts`) org-независимы — это нормально. Org-binding и team metrics — нет.

### H5. Журнал посещений: преподаватель видит цену `0` у персонального урока

**Где:** `tangodb/src/components/AttendancePanel.tsx` ~1704–1730

Всегда рендерится `formatCurrency(activePersonalLesson.price)`. Нет `showPrice` / `role !== "teacher"`.

`usePersonalLessons` для teacher маскирует `price` и `paidAmount` в `0` (`maskFinancial`), статус `paid` оставляет. В списке `/personal` суммы скрыты (`PersonalLessonsPageContainer`), в журнале — «разовый урок · 0 ₫» (выглядит как бесплатный урок). Строка долга (`price - paidAmount`) показывается **только** если `paid === "no"` **и** `paidAmount > 0`; после маски `paidAmount` всегда 0, поэтому отдельный «ложный долг 0» обычно **не** рисуется.

### H7. Рассинхрон JWT-роли и БД: потенциальный цикл `refreshSession` + `invalidateQueries`

**Где:** `tangodb/src/organization/OrganizationProvider.tsx` (~302–310)

Если `getMemberRoleFromSession(session)` (`member_role` / legacy `role` в JWT) **не совпадает** с `membership.role` из БД, эффект вызывает `supabase.auth.refreshSession()`, а при успехе — `queryClient.invalidateQueries()` **без префикса** (инвалидация всего кэша).

Нет счётчика попыток, нет in-flight guard и нет выхода, если после refresh claim всё ещё не обновился (задержка custom access token hook, смена роли в БД без обновления JWT, баг в `set_active_organization`).

**Уточнение (третья проходка):** это **не** «шторм, пока не совпадёт». Зависимости эффекта включают `session`. Успешный `refreshSession()` в `AuthProvider` всегда делает `setSession(nextSession)` через `onAuthStateChange` — новый объект сессии даже при **тех же** claims. Пока `jwtRole !== dbRole`, эффект запускается снова: refresh → новый `session` → refresh. Это **неограниченный async-цикл** (не React render-loop). Параллельные `refreshSession` не сериализуются.

Каждый успешный refresh зовёт `queryClient.invalidateQueries()` **без префикса**. Вместе с **M5** это повторно гоняет `apply_scheduled_subscription_member_changes` из каждого смонтированного `useSubscriptions()`. С **M12** заново поднимаются entry-sync queries. С `useEnsureOwnMemberProfile` при сбросе `syncedRef` возможен повторный RPC `ensure_own_member_profile`.

**Последствие:** сеть/CPU/PostgREST не отпускают, пока mismatch жив; UI мигает загрузкой; возможны rate-limit Auth и лишние write-on-read RPC. На слабом канале CRM выглядит «зависшей».

**Как чинить:** in-flight ref + лимит попыток / backoff; не ставить `session` в deps, сравнивать claims (`member_role` + `exp`); инвалидировать только org-scoped ключи; если mismatch сохраняется N раз — остановиться и залогировать в Sentry; не refresh на каждый новый объект сессии с тем же payload.

**Уточнение (четвёртая проходка):** при `refreshSession()` с `{ error }` цикл **останавливается** (объект `session` не меняется). Бесконечность возможна только при **успешном** refresh, когда claim `member_role` остаётся старым. Параллельно см. **H10** — пока mismatch жив, UI уже мог отрисоваться с JWT-ролью.

**Уточнение (пятая проходка):**

- `OrgWorkspaceRoute` смотрит `membershipsLoading` = TanStack `isLoading`. При уже закэшированных memberships полный экран загрузки **не** вспыхивает на каждый refetch (`isLoading` false, `isFetching` true). «Мигание» — это refetch всех активных query после голого `invalidateQueries()`, не unmount outlet.
- `useEnsureOwnMemberProfile`: `syncedRef` **не** сбрасывается успешным H7. Повторный RPC `ensure_own_member_profile` идёт только если предыдущий вызов вернул `{ error }` (`syncedRef = null`) **и** `orgLoading` мигнул (инвалидация `organization-context`). На success-пути H7 ensure **не** штормит.
- Нет сверки `jwtMemberId` vs `membership.id` (см. **H10**): если `member_role` совпал, а `member_id` нет, эффект H7 **не запускается**.

### H10. При рассинхроне JWT/БД UI доверяет JWT-роли, а не membership

**Где:** `tangodb/src/organization/OrganizationProvider.tsx` (~188, ~299–310)

```ts
const role = getMemberRoleFromSession(session) ?? membership?.role ?? null;
```

JWT claim (`member_role` / legacy `role`) **приоритетнее** строки `membership.role` из БД. Тот же паттерн для identity:

```ts
const memberId = getMemberIdFromSession(session) ?? membership?.id ?? null;
```

Эффект **H7** сравнивает **только роли**. Если `member_role` совпал, а `member_id` остался от другой org (частичный custom access token hook после `set_active_organization`), refresh **не** запускается.

Call sites `useOrganization().memberId` (не `membership.id`): `PersonalLessonsPageContainer`, `LessonInfoPopup`, `EditLessonPopup`, `PersonalLessonSaleForm`, `ScheduleDebtorsBlock`, `AttendancePanel`, `SubscriptionsPanel`, `SchedulePageContainer`, `ScheduleUpcomingCancellationsBlock`, `ClientNotesPanel`, `useScheduleDebtors` (фильтр `teacherMemberId === memberId` — пустой список долгов сетки), `useClientNotes`, `useExpenses`, `useEnsureOwnMemberProfile`. Клиентский filter `teacherMemberId === memberId` на данных текущей org даёт **пустой** список (UUID не совпадает). Google Calendar binding наоборот берёт `membership?.id` (`useGoogleCalendarIntegration` через `usePermissions().membership`) — два источника identity. `usePermissions().can` / `canAccessPanel` получают тот же JWT-first `role`, поэтому elevated-кнопки и `canManage` GCal живут от claims, не от строки БД.

**Сценарий роли:** админ понизил пользователя в БД (`teacher`), JWT ещё `admin`/`owner`. Клиент показывает навигацию и кнопки elevated-роли. RLS на сервере, скорее всего, отрежет мутации, но:

- пользователь видит экраны/действия, которые потом падают с ошибкой;
- возможны read-only утечки через view, если политика смотрит на JWT (нужно сверять с конкретными RLS);
- усиливает ощущение «CRM зависла» вместе с H7 (мигание + ошибки доступа).

**Сценарий member_id:** teacher «потерял» свои уроки/долги/заметки в UI до обновления JWT, хотя RLS отдаёт строки текущей org.

**Как чинить:** при любом JWT/DB mismatch брать для UI **строку `membership`** (role + id); banner «обновление прав»; не рендерить finance/settings до совпадения claims. Починка H7 без H10 не закрывает окно неверного UI и не ловит рассинхрон одного `member_id`.

### H8. `sync_status = detached` в UI = вечный `pending` (уточнение M12)

**Где:** `lib/googleCalendarApi.ts` `resolveLessonGoogleSyncUiStatus` (~352–360); CHECK в `google_calendar_event_links.sync_status` (`pending | synced | failed | detached`).

`detached` — штатный терминальный статус (пользователь удалил событие в Google; CRM не меняется, см. `architecture.md` / lessons 2026-08-06). Функция резолва обрабатывает только `pending` / `failed` / `synced`. Ветка `else` возвращает **`"pending"`**.

Пока открыт попап урока (`LessonInfoPopup` / `EditLessonPopup`):

- `useGoogleCalendarSyncStatus` ставит `refetchInterval: 15_000` на весь срок `ui === "pending"`;
- `GoogleCalendarSyncStatusBadge` крутит `Loader2` (`animate-spin`) с текстом «Ожидает синхронизации».

Это не «зависший job». Это ожидаемый продуктный путь, который CRM показывает как бесконечную синхронизацию и бесконечно опрашивает RPC.

**Как чинить:** маппить `detached` в отдельный UI-статус (без interval); fallback `"unknown"` без poll; cap/backoff как в M12.

### H9. Повтор «до даты» без верхней границы + последовательный freebusy

**Где:**

- `DatePickerField`: проп `max` **есть**. У repeat «до даты» **не передаётся**: `PersonalLessonSaleForm` (weekly end ~1054; дата слота ~946 тоже без `max`, `min={todayISO}`), `GroupLessonRepeatFields` (его же встраивает `EditLessonPopup`). Не все DatePicker в приложении без `max`: `RecordRentalPaymentModal` (`max={orgToday}`), payroll `paidAt` (`max={todayIso}`). Native `<input type="date">` без `max`: дата **одного** персонального урока в `EditLessonPopup` (~1576, `min={todayISO}` — не expand ряда), отпуск в `TeacherVacationDialog` (start и end). `CancelGroupLessonDialog` — см. **M20**.
- `expandWeeklyRecurrence` / `expandPersonalLessonWeeklySlots` / `expandSlotsToDateRange` / `computeWeeklyOccurrencesInRange` / `computeFixedPeriodEstimate` — нет cap по числу слотов;
- `useGoogleCalendarFreebusy` (~61–72) — последовательный `for … of` + `await fetchTeacherGoogleFreebusy` (**не** `for await`) — по одному Edge Function `google-calendar-freebusy` на каждый слот;
- `invokeFunction` (`googleCalendarApi.ts` ~100–119) — **нет timeout / AbortSignal**.

Режим «N недель» ограничен select `[2, 3, 4, 6, 8, 12]`. Режим «до даты» — нет. Дальняя дата → сотни/тысячи ISO-дат → столько же последовательных HTTP. Пока цикл идёт, `isChecking === true` (баннер «проверка занятости»). Submit **не** блокируется проверкой, но форма выглядит зависшей; один зависший invoke останавливает всю цепочку.

На submit тот же expand уходит в `useAddPersonalLessons` — попытка вставить сотни строк персональных уроков без предупреждения о размере пакета.

Групповой слот с дальним `valid_to` — одна строка в БД (горизонт GCal 90 дней), freebusy в `AddGroupLessonForm` берёт только ближайшую дату. Основной удар — персональные уроки.

**Уточнение (пятая проходка):**

1. **Библиотечный бесконечный `while`.** `expandWeeklyRecurrence` сравнивает ISO-строки. Пустой `endDate` безопасен (`startDate > ""` → `[]`). Но **валидный start + не-ISO end**, который лексикографически ≥ любой ISO (`"invalid"`, `"NaN-NaN-NaN"`): `"2026-08-19" <= "invalid"` истинно (`"2" < "i"`), курсор уходит вперёд **без выхода**. Тот же класс: `expandSlotsToDateRange` (`cursorISO <= rangeEndISO`), `computeWeeklyOccurrencesInRange` (`current <= rangeEnd`), `computeFixedPeriodEstimate` (`cursor <= rangeEnd`). `DatePickerField` / `<input type="date">` отдают только `YYYY-MM-DD`, форма продажи требует непустую дату до submit — до UI почти не доходит. Нет guard `^\d{4}-\d{2}-\d{2}$` в expand. `addDays` на мусоре даёт `"NaN-NaN-NaN"` (`toISODateLocal` на Invalid Date) и тоже может не завершиться, если `rangeEnd` не-ISO.

2. **Freebusy после unmount.** Cleanup эффекта чистит только debounce-timer, не AbortSignal. Зависший `invoke` продолжает цепочку; `requestIdRef` на unmount **не** инкрементируется → риск `setState` на размонтированном дереве и лишние Edge-вызовы.

3. Тот же класс без верхней границы: native date в **отпуске** (нет `max`) и **отмене группы** при `validTo == null` — см. **M20**.

**Как чинить:** `max` на DatePicker / native date (например +12 месяцев); hard cap слотов (например 52) в expand + toast; ISO-guard / max-iterations в `while`; batch/один freebusy-запрос на диапазон; timeout/`AbortSignal` на invoke; не держать `isChecking` без дедлайна.

### H11. Reconnect: эффект в `App` повторяется на каждый ререндер ~3 с

**Где:** `tangodb/src/App.tsx` (~220–228); `useOnlineStatus` (`justConnectionRestored` true 3000 ms); `useInvalidateAfterOfflineSync`; `useOfflineReconciliation`

```ts
useEffect(() => {
  if (!justConnectionRestored) return;
  showToast(t("nav.connectionRestored"), "success");
  // ...
  void invalidateAfterOfflineSync().then(() => openReconciliation());
}, [justConnectionRestored, showToast, t, counts.pending, ..., invalidateAfterOfflineSync, openReconciliation]);
```

Пока флаг true, эффект зависит от **нестабильных** ссылок:

- `useOfflineReconciliation` каждый рендер возвращает **новый** объект и новые функции `openReconciliation` / `closeReconciliation` (не `useCallback`);
- `useOrgQueryScope().withOrgId` — обычная функция в теле хука, **новая на каждый рендер** → `useInvalidateAfterOfflineSync` (deps `[queryClient, withOrgId]`) тоже новый колбэк.
- `showToast` и `t` стабильны (`useCallback`). `counts.pending|conflict|failed` в deps: смена счётчиков очереди за те же 3 с **повторно** запускает эффект.

Это не «если App случайно ререндерится». Эффект **сам себя кормит**: первый проход всегда зовёт `showToast` → `setToast({ msg, type })` (новый объект) → ререндер `App` → новые `openReconciliation` / `invalidateAfterOfflineSync` → эффект снова. Пока `justConnectionRestored` true (~3 с) это **самоподдерживающийся `useEffect`+`setState` цикл** (не бесконечный: флаг гаснет). Даже при пустой офлайн-очереди toast крутится каждый проход; при `pendingTotal > 0` дополнительно штормят invalidate schedule/attendance/**subscriptions** (→ **M5**) и `openReconciliation()`. На слабом канале CRM «мигает» и долбит PostgREST.

**Как чинить:** `useCallback` для `openReconciliation`; мемоизировать `withOrgId` (`useCallback` от `organizationId`); в эффекте ref «уже обработали этот импульс» (`justConnectionRestored` rising edge), не список нестабильных функций.

### H12. PostgREST `max_rows = 1000`: тихая обрезка списков

**Где:** `tangodb/supabase/config.toml` (`[api] max_rows = 1000`); облачный default PostgREST тот же. В `tangodb/src` **нет ни одного** `.range()`. Часть запросов использует `.limit()` (`useOrgAuditLog`, `usePayroll`, `useScheduleCancellations`) — это узкие списки, не справочники ниже. `count: "exact"` есть только как `head: true` в `usePrices` (счётчик строк, не каталог). Клиент **не** читает `Content-Range` у списков ниже. Ошибка не бросается — UI рисует урезанный массив как полный.

Запросы без `.range()` / без узкого фильтра:

| Хук | SELECT | Риск |
|-----|--------|------|
| `useClients` / `useClientDirectory` | все клиенты (directory — ещё и архив) | автокомплит, дубликаты, журнал |
| `useSubscriptions` | все абонементы | журнал посещаемости, продажа, M5 |
| `useAttendanceRecords()` без месяца | вся история | `SubscriptionsPanel`, `DataExportPage` — экспорт «полный», по факту 1000 последних |
| `useAttendanceRecords(yearMonth)` | месяц, `order date desc` | при >1000 отметок за месяц **начало месяца пропадает** |
| `usePersonalLessons()` без диапазона | все уроки | `PersonalLessonSalePanel`, `SubscriptionsPanel`, `FinancePayrollPage` (карта id→урок), `DataExportPage`, `DashboardPage` (operational + teacher-scoped); legacy `SchedulePanel` (не в роутере, **L5**) |
| `usePersonalLessons({ dateRange })` | весь горизонт повтора (**M18**, только `schedule-cell`) | conflict-check видит ≤1000 строк, пропуски overlap |
| `usePayments` за широкий период / тренд | платежи | KPI |

Для attendance / personal_lessons / payments порядок `date` / `created_at` desc → отрезается **хвост в прошлое**. Абонементы — `activation_date` desc (старые активации). Клиенты — `order("last_name")`: обрезка **алфавитная**, не временная. Студия с плотным расписанием: 20 групп × ~12 занятий × 10 человек ≈ 2400 отметок/месяц — журнал посещаемости уже врёт без ошибки.

**Как чинить:** для «справочников» — пагинация или RPC `..._all` с `SECURITY DEFINER` осторожно не надо; цикл `.range(from, from+999)` пока `data.length === pageSize`; для журналов — обязательный `yearMonth`/`dateRange` + проверка count; toast если `rows.length === 1000` (подозрение на truncate); не поднимать `max_rows` «чтобы хватило» без пагинации.

### M12. Google Calendar: статус синка «pending» по умолчанию → бесконечный polling 15 с

**Где:** `useGoogleCalendarSyncStatus.ts` (~30–34); `lib/googleCalendarApi.ts` `resolveLessonGoogleSyncUiStatus` (~352–360)

При «зависшем» job, потерянном worker, `detached` или вечном `null` статусе CRM будет опрашивать RPC бесконечно. Это не зависание React, но постоянный трафик и крутящийся badge.

**Как чинить:** fallback `"unknown"` / `"detached"` без interval; cap на число poll; backoff; таймаут → `"error"` или badge «устарело».

### M18. H9 усиливается conflict-query на весь диапазон повтора

**Где:** `tangodb/src/components/personal-lessons/PersonalLessonSaleForm.tsx` (~285–300)

`conflictCheckDateRange` строится как `min..max` по `freebusySlots` **только если** `mode === "schedule-cell"` (`isScheduleCell`). Иначе `useMemo` возвращает `null`, и `usePersonalLessons({ dateRange })` **не** включается (`enabled: Boolean(conflictCheckDateRange)`).

**Последствие (schedule-cell):** одна форма продажи одновременно гонит N sequential Edge freebusy (**H9**), тяжёлый SELECT на годы вперёд и (на submit) bulk insert (**M19**). CRM не зависает бесконечно, но браузер/PostgREST/Edge могут «подвиснуть» на минуты или упасть по timeout.

**Как чинить:** вместе с cap слотов — ограничить `conflictCheckDateRange` тем же horizon (например 12 недель); не включать conflict-query, пока слотов > cap. Не распространять этот SELECT на standalone, пока нет cap.

### M19. Bulk insert персональных уроков без лимита строк

**Где:** `tangodb/src/hooks/usePersonalLessons.ts` `useAddPersonalLessons` (~327–349)

Все даты одним `supabase.from("personal_lessons").insert(rows)`. При сотнях/тысячах дат (режим «до даты» без cap) возможны:

- превышение лимита тела запроса PostgREST / gateway timeout;
- частичный отказ без понятного UX (в отличие от **M14**, insert атомарен, но пользователь не знает, сколько дат «слишком много»).

**Как чинить:** client-side cap + server-side guard в RPC; при превышении — toast с max N слотов; батчи по 50–100 строк или один RPC `create_personal_lessons_batch`.

### M20. Отпуск преподавателя и отмена группы «диапазон» без верхней границы

**Где:** `TeacherVacationDialog.tsx` (`computeTeacherVacationPreview` → `computeWeeklyOccurrencesInRange`); `CancelGroupLessonDialog.tsx` (`computeWeeklyOccurrencesInRange` при `mode === "range"`).

Это **не** `DatePickerField`. Оба диалога — native `<input type="date">`:

- отпуск: `min` есть, **`max` нет** (можно уйти в 2099);
- отмена группы диапазоном: `min={lesson.date}`, **`max={lesson.validTo ?? undefined}`**. Если у слота задан `validTo`, горизонт уже ограничен слотом. Без `max` только при `validTo == null` (открытый слот) — тогда тот же риск, что **H9**.

`useMemo` разворачивает все weekly-даты слотов в `[start, end]`. Горизонт 2099 × N регулярных слотов (открытый слот или далёкий `validTo`) → десятки тысяч ISO-строк в памяти, потом RPC `cancel_teacher_group_vacation` / `cancel_group_lesson_occurrences` с огромным `cancelDates`. `endDate === ""` в отпуске preview пустой (`!endDate`). Безопасный путь — только после выбора дальней даты.

**Как чинить:** вместе с **H9** — `max` на отпуска (+12 мес); для отмены группы — `max` если `validTo` null, иначе оставить `validTo`; cap `previewDates.length` (например 200) + toast; серверный guard по числу дат.
