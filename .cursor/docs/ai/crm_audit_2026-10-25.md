## Что уже в порядке

Это не надо чинить заново.

- **Посещаемость.** `useMarkAttendance` и `useMarkPersonalLessonAttendance` при `success: false` откатывают оптимистичный кэш в `onSettled`. Раньше ложный «пришёл» оставался до следующего refetch.

- **Reconnect.** В `AppLayout` импульс «связь вернулась» обрабатывается один раз через ref, эффект сам себя не перезапускает.
- **Пагинация уже есть** у `clients`, `subscriptions`, `attendance`, `payments`, `personal_lessons`, `personal_lesson_charges`, `schedule_group_roster`. Там обрез на 1000 строк не тихий: `fetchAllPostgrestRows` листает дальше.

- **Парсер `renterMiniappAddon`** в `paymentConfig.ts` / `platformPaymentContract.ts` нужен, чтобы старый JSON конфига оплаты не ломал разбор. Это не мёртвый код.

## Высокие

### H1. Чеклист первого дня на каждом заходе владельца скачивает операционную историю

**Где:** `tangodb/src/pages/DashboardPage.tsx` монтирует `FirstDayChecklist` для `owner` и `director`.  
**Запросы:** `tangodb/src/components/onboarding/FirstDayChecklist.tsx` (хуки около строк 71–78, ранний `return` около строки 142).

Хуки вызываются до проверки «чеклист скрыт» и «все шаги уже сделаны». Чтобы узнать, что шаг выполнен, код смотрит на `data.length > 0`, но запрос при этом забирает таблицы целиком:

| Хук | Что уходит с сервера |
|-----|----------------------|
| `useClientDirectory()` | все клиенты, включая архив |
| `useSchedule()` | все версии `schedule_slots`, без пагинации |
| `useSubscriptions()` | все абонементы |
| `usePersonalLessons()` | все персональные уроки и снова справочник клиентов |
| `useAttendanceRecords()` без месяца | вся таблица `attendance`, `select("*")` |

У студии, которая уже прошла онбординг, блок на экране не рисуется (`allDone`), но запросы всё равно выполняются на каждом открытии дашборда. `FirstDayChecklist` смонтирован в `DashboardShell` для **любой** вкладки дашборда владельца/директора (в том числе только «Финансы»): тяжёлые хуки стартуют даже когда на экране один `FinancialDashboard`. Посещаемость в чеклисте вызывается с `useAttendanceRecords(undefined, { enabled: true })` — без привязки к видимости блока (в отличие от персональных уроков, где `enabled: modules.personal_lessons`). `staleTime` у посещаемости, абонементов и уроков — 30 с; глобально в `queryClient.ts` задано 5 мин, но `refetchOnWindowFocus` у TanStack Query по умолчанию **включён**. Возврат на вкладку повторяет этот набор. С операционным дашбордом часть ключей (`useClientDirectory`, `useSubscriptions`) совпадает — сеть не дублируется, но чеклист всё равно добавляет расписание, посещаемость и персональные уроки.

**Последствие:** лишние секунды и трафик на главном экране; на большой базе это главный тормоз CRM, хотя пользователь чеклист уже не видит.

**Как чинить, не ломая экран:** не менять смысл шагов. Пока чеклист скрыт (`showFirstDayChecklist === false`: выключены подсказки или вызван `hideFirstDayChecklistUntilSettings`) или организация не выбрана, запросы чеклиста должны быть `enabled: false`. Проверка «есть хотя бы одна строка» — `select` одной колонки с `limit(1)` или `head: true` + `count: exact`, отдельные `queryKey`, не полные операционные хуки. Когда все шаги уже сделаны, блок не рисуется, но лёгкие exists при всё ещё включённом чеклисте остаются: иначе после удаления данных чеклист не вернётся. Полные списки оставить тем экранам, которым они нужны. Отдельным PR, без правок расписания и оплаты.

### H2. Списки без `.range()` молча обрезаются на 1000 строк

**Где:** `max_rows = 1000` в `tangodb/supabase/config.toml`. PostgREST отдаёт не больше 1000 строк и не сообщает клиенту, что хвост отрезан, если в запросе нет `.range()`.

`fetchAllPostgrestRows` это закрывает только для таблиц из раздела «уже в порядке». Без пагинации остаются:

| Запрос | Файл | Чем это кончается |
|--------|------|-------------------|
| Все `schedule_slots` (`select("*")`) | `useSchedule` | сетка и даты журнала строятся из усечённого набора версий слотов |
| Слоты недели (фильтр `valid_from` / `valid_to`, без `.range()`) | `useScheduleForWeek` | то же для живой недели, если пересекающихся версий больше 1000 |
| `financial_debtors_v` целиком | `useFinancialDebtors` | «Финансы → Дебиторы», карточка клиента и KPI дашборда не показывают хвост долгов |
| `subscription_groups` (`select("*")`) | `useSubscriptionGroups` | часть абонементов теряет привязку к группам |
| `lesson_occurrence_substitutes` за всё время | `fetchLessonSubstitutes` | старые и лишние подмены пропадают, неделя может показать не того педагога |
| `subscription_refunds` без фильтра | `useSubscriptionRefunds()` на финансовом дашборде и в выручке | суммы возвратов считаются по первой тысяче |
| `expenses` | `useExpenses` | месяц обычно узкий; вызов без дат упрётся в тот же потолок |
| `single_visits` | `useSingleVisits` | то же: месяц безопаснее, пустой фильтр — нет |
| `other_income` | `useOtherIncome` | то же |
| `subscription_member_changes` целиком | `useAllSubscriptionMemberChanges` | журнал и абонементы: смены состава пары/тройки обрезаются; отложенные замены могут не попасть в расчёт |

Журнал посещаемости, клиенты, абонементы и платежи этим пунктом **не** затронуты: они уже листаются. `useGroupWaitlist` и `useSubscriptionMemberChanges` по одному `subscription_id` / `class_id` обычно укладываются в 1000 строк; риск — именно org-wide выборки без `.range()`.

Справочники `prices`, `locations`, `disciplines`, `classes`, `teacher_pay_rates` тоже читаются без `.range()`, но у одной студии они на порядки меньше 1000 строк — в таблицу не внесены. Выборки по дате или id (`schedule_occurrence_cancellations`, `lesson_occurrence_closures`, `calendar_event_sessions`, `teacher_settlements`, `audit_log_leadership_v` с `limit`) ограничены фильтром. Списочные RPC аренды и отчётов возвращают один `jsonb`: обреза нет, но и границы нет — весь список арендаторов или регистр денег за период приходит одним ответом. Это вопрос объёма, не потери данных.

**Последствие:** потеря не в скорости, а в данных. Экран выглядит успешным (`error` нет), части строк нет. Для должников и слотов расписания это уже реалистично у студии с длинной историей правок сетки.

**Как чинить:** для операционных списков, которые обязаны быть полными, тот же `fetchAllPostgrestRows`. Для экранов с тысячами строк лучше серверная страница (как у входящих оплат аренды, `PAGE_SIZE = 50`), а не выгрузка всего в память браузера. Не смешивать с H1 в одном PR. После смены запроса слотов проверить неделю расписания, журнал посещаемости и отпуск педагога: все трое читают `useSchedule`.

### H3. Экран абонементов держит в памяти всю историю посещений и все персональные уроки

**Где:** `tangodb/src/components/SubscriptionsPanel.tsx` (около строк 133–142).

На каждое открытие `/subscriptions` одновременно стартуют:

- активные клиенты и отдельно полный справочник с архивом (`useClients` + `useClientDirectory`);
- все абонементы;
- все связи абонемент–группа;
- все слоты расписания;
- весь прайс;
- **вся** `attendance` без месяца;
- **все** персональные уроки без даты.

Счётчики визитов считаются на клиенте из этих массивов (`useAttendance` / панель). Виртуализация списка есть только в журнале посещаемости (`VirtualList`). Список абонементов и клиентов рисуется целиком.

Тот же приём на экране экспорта: `DataExportPage` вызывает `useAttendanceRecords()` и `usePersonalLessons()` при монтировании, до нажатия «скачать».

И на вкладке продажи персонального урока: `PersonalLessonSalePanel` вызывает `usePersonalLessons()` без даты и `useSchedule()` целиком, чтобы передать в `PersonalLessonSaleForm` занятость зала (дата, время, `locationId`). Для проверки конфликтов форма уже делает отдельный запрос `lessonsInRangeQuery` по диапазону выбранных дат; полный проп `personalLessons` нужен ей только как запасной вариант, пока диапазон не определён, и в ветке префилла с ячейки сетки (около строки 609). Сужать проп — вместе с проверкой этих двух веток. Экран зарплат — см. M8.

**Последствие:** продажа абонемента и список активных планов ждут и держат данные, которые нужны статистике, а не форме. На большом архиве вкладка тяжелее кассы, хотя касса читает те же кэши.

**Как чинить:** оставить на экране выборки, без которых форма продажи, имена в списке и привязка к группе не работают. `useClientDirectory` не заменять на `useClients()`: `clientMap` и фильтр истории берут архивные имена. `useSchedule()` нужен продаже (`filterGroupsScheduledInDateRange`), это не статистика. Историю посещений и персональные уроки не грузить на монтировании списка. Счётчик `subscriptions.card.visits` рисуется только в раскрытой карточке (`isExpanded`); запрос — по `subscription_id` этой карточки, не `select` всей таблицы и не запрос на каждую строку. Свёрнутый список эти цифры и так не показывает и не должен их ждать (`isLoading` панели сейчас включает оба запроса — после правки не должен). Экспорт: `exportAllDashboardCsv` уже режет attendance и персональные уроки до `statsMonth`. Качать этот месяц в момент явного скачивания, не при открытии страницы и не всю историю ради одного месяца. Колонки и месяц файла не менять. Не менять RPC продажи.

### M2. Правка тарифа может оставить связи преподавателей пустыми

**Статус:** закрыто в **2.12.23** (P05).

**Где было:** `useUpdatePriceMeta` и `syncPriceTeacherMembers` / `syncPriceDisciplines` в `tangodb/src/hooks/usePrices.ts`.

Порядок такой: сначала `UPDATE prices`, потом удаление строк `price_disciplines` / `price_teacher_members`, потом вставка нового набора. Если вставка падает, код пытается вернуть снимок. Если падает уже восстановление, ошибка вставки снимка не проверяется (`restorePriceTeacherMembers` / `restorePriceDisciplines` не смотрят `error`). Если дисциплины уже записались, а преподаватели — нет, мутация возвращает `success: false`, но строка тарифа и дисциплины уже новые. Те же `syncPrice*` вызывает `useCreatePrice`; `deleteCreatedPrice` тоже не смотрит `error`. В RPC уходит и правка, и создание. Поля метаданных, которые уже пишет `useUpdatePriceMeta`: `label`, `description`, `duration_minutes`, `location_id`, legacy `discipline_id` (одна дисциплина или null) плюс связи. Сумму `price` и число занятий этот хук не меняет — их не тащить в ту же функцию.

**Последствие:** после сбоя сети тариф без преподавателей или с новым описанием и старым смыслом ошибки «не сохранилось». Повторное сохранение обычно лечит, пока снимок восстановился.

**Как чинить:** одна SQL-функция на метаданные + связи для правки и для создания, либо проверять ошибку восстановления и не сообщать успех, пока снимок не вернулся. Не менять правила выбора тарифа в продаже в том же PR. Сумму тарифа и число занятий в эту функцию не переносить.

### M3. Откат закрытия слота расписания не проверяет, что откат прошёл

**Статус:** закрыто в **2.12.23** (P05). Атомарная RPC на закрытие+версию не вводилась: проверка ошибки отката и i18n `schedule.error.editCloseRollbackFailed`.

**Где было:** `useSchedule.ts`, `rollbackClose` внутри `useEditGroupSchedule` (около строк 629–678).

Слот закрывается на дату, затем вставляется новая версия. Если вставка не удалась, код возвращает `valid_to` назад и не смотрит, удался ли этот `UPDATE`.

**Последствие:** при обрыве на откате занятие пропадает из сетки с даты правки, новая версия не создаётся. Редкий сетевой случай, данные чинятся повторным редактированием только если слот ещё виден.

**Как чинить:** если откат вернул ошибку, текст для пользователя должен говорить, что серия могла закрыться и правка не встала. Лучше одна RPC, как у `move_group_lesson_occurrence`. Не переписывать всю сетку.

### M4. Подмены преподавателя грузятся все сразу, не за неделю

**Статус:** закрыто в **2.12.24** (P06).

**Где:** `useScheduleForWeek` всегда вызывает `useLessonSubstitutes()`, а `fetchLessonSubstitutes` читает всю `lesson_occurrence_substitutes` без даты и без `.range()`. Тот же хук без диапазона вызывают `AttendancePanel` (журнал) и `useAccessibleLocations` (M7). `SubstituteLessonDialog` список подмен сам не грузит.

Недельная сетка и так ждёт шесть запросов (слоты, отмены, персональные, события, аренда, подмены). Подмены не ограничены той же неделей, что слоты.

**Как чинить:** на недельной сетке фильтр `occurrence_date` по неделе и `fetchAllPostgrestRows`, ключ запроса с датами недели. Вызов без диапазона (журнал, и до M7 — залы) по-прежнему листает всю таблицу: журнал не привязан к неделе сетки. Карточка урока на сетке берёт подмены из данных этой недели. Диалог замены список не запрашивает.

### M5. Каждый активный список персональных уроков тянет весь справочник клиентов

**Статус:** частично в **2.12.24** (P06) — ветки фильтров сведены в `applyPersonalLessonsFilters`; отдельный запрос имён по id страницы не делался (следующий шаг аудита).

**Где:** `usePersonalLessons` вызывает `useClientDirectory({ enabled: queryEnabled })` (`includeArchived: true`) и подставляет ФИО в `clientDisplay`. Флаг `enabled` у справочника уже совпадает с флагом уроков — отдельная проблема не в «вечно включённом» directory, а в том, что при **любом** включённом списке уроков грузится полный архив клиентов, даже если уроки отфильтрованы неделей или одним `clientId`.

Расписание на неделю, журнал, финансы и чеклист из-за этого делят один тяжёлый кэш «все клиенты, включая архив». Два почти одинаковых тела запроса (view преподавателя и базовая таблица, строки ~213–319) легко разъедутся при следующей правке фильтра.

**Как чинить:** не убирать обогащение имён в том же коммите, где режется выборка. Две ветки свести в один построитель фильтров. Таблицу не объединять: преподаватель читает `personal_lessons_teacher_v` и урезанный `personalLessonsSelectTeacher` (без денег), остальные — `personal_lessons`. View нужен из‑за маски и RLS, не из‑за копипасты. Отдельный запрос имён только для id из текущей страницы уроков — следующий шаг, не первый.

### M6. Отметка персональной посещаемости сбрасывает много кэшей

**Статус:** закрыто в **2.12.24** (P06) — узкая инвалидация только в `useMarkPersonalLessonAttendance`; дефолт `invalidatePersonalLessonRelatedQueries` без изменений.

**Где:** `invalidatePersonalLessonRelatedQueries` в `usePersonalLessons.ts`.

Успешная отметка инвалидирует персональные уроки, всё расписание, абонементы, должников, начисления, след долга, статус Google Calendar и платежи. Для денег это оправдано. Для отметки «пришёл / не пришёл» платёжные и долговые ключи лишние, если RPC посещаемости их не меняет.

Актуальная функция — `tangodb/supabase/migrations/20261102000001_lesson_occurrence_substitutes.sql`. Более поздние файлы её не заменяют. Ранняя версия в `20260614200000_personal_attendance_and_date_guard.sql` пакет не трогает — на неё опираться нельзя. Сейчас RPC пишет `personal_lessons.attendance_status` и, если у урока есть `subscription_id`, обновляет `subscriptions.lessons_left` и `status` (`finished` при нуле). Платежи, должников, начисления, след долга и календарь не пишет.

**Как чинить:** сузить только вызов из `useMarkPersonalLessonAttendance`. Оставить инвалидацию персональных уроков, абонементов и расписания. Снять с этой мутации должников, начисления, след долга, платежи и ключ Google Calendar. Дефолт `invalidatePersonalLessonRelatedQueries` не менять: оплата, сторно, restate и списание долга зовут его с широким набором. Иначе пакет на экране абонементов останется со старым `lessons_left`, а журнал денег — со старым долгом после оплаты.

### M7. `useAccessibleLocations` при любой подмене тянет полное расписание

**Статус:** закрыто в **2.12.24** (P06) — `fetchTeacherSubstituteSlotLocationMap`, без `useSchedule()` и org-wide подмен.

**Где:** `tangodb/src/hooks/useLocations.ts`, `useAccessibleLocations` (строки ~69–75).

Для фильтра залов у преподавателя с узким `scope` хук всегда вызывает `useLessonSubstitutes()` (вся таблица подмен, см. M4/H2) и **условно** `useSchedule()` — если в организации есть хотя бы одна подмена, подгружаются **все** `schedule_slots` без пагинации. Хук стоит на тяжёлых экранах: журнал (`AttendancePanel`), абонементы, расписание, касса, прайс, продажа персонального урока.

**Последствие:** у студии с историей замен педагогов открытие журнала или абонементов добавляет к уже тяжёлым запросам экрана ещё полную сетку слотов и полный список подмен — даже когда пользователю нужен только список доступных залов.

**Как чинить:** `mapLessonSubstituteRow` не заполняет `locationId`. Зал подмены берётся из `schedule_slots.location_id` по `schedule_slot_id` (`substituteLocationIds`). Узкий `select` `id, location_id` по id слотов подмен этого преподавателя, не весь `useSchedule()` и не колонка, которой в выборке подмен нет. `useScheduleGroups()` не убирать: он нужен для `scope.schedule_group_ids`. Персональная подмена без слота зал и сейчас не добавляет — это не чинить заодно. Не смешивать с H2 в одном PR: после правки проверить преподавателя с `scope.locations` и с подменой на чужом слоте.

### M8. Экран зарплат пересчитывает расчётные листы при каждом просмотре и грузит все уроки

**Где:** `tangodb/src/pages/FinancePayrollPage.tsx`, `AdminPayrollTable` (строки ~307–330); `useRecalculateTeacherSettlement` в `tangodb/src/hooks/usePayroll.ts`.

При `can("payroll.write")` эффект на `[yearMonth, canWrite]` вызывает `recalculate.mutateAsync(yearMonth)` на каждом монтировании и смене месяца. RPC `recalculate_teacher_settlement` для **каждого** активного сотрудника делает upsert в `teacher_settlements`, пересобирает строки через `payroll_refresh_settlement_lines` и перезаписывает `amount_accrued` и `computed_at`, после чего инвалидирует весь `payrollQueryKey`. То есть просмотр любого месяца, включая давно закрытые, — это запись в БД. Результат мутации эффект не смотрит. Хук при ошибке RPC возвращает `{ success: false }`, `mutateAsync` при этом не отклоняется. Если организация в режиме только чтения (`organization_allows_writes`) или редакция не включает `payroll`, таблица молча показывает старые суммы.

Там же, рядом с месячными `usePayments` и `useSingleVisits({ yearMonth })`, стоят `useSchedule()` (все версии слотов), `usePersonalLessons({ enabled })` без даты и `useSubscriptionGroups()` (оба последних — без `.range()`, см. H2).

**Последствие:** лишняя нагрузка и записи при обычном просмотре, тихое расхождение «открыл месяц — цифры не обновились» в read-only организации, и тяжёлый экран, хотя он помесячный. Если правила ставок или исторические данные менялись, повторное открытие прошлого месяца молча меняет его начисления — это стоит отдельно сверить с ожиданием бухгалтерии.

**Как чинить:** пересчёт по явной кнопке или только для текущего/незакрытого месяца; ошибку мутации показывать тостом. `useRecalculateTeacherSettlement` при ошибке RPC возвращает `{ success: false, error }`, а не бросает исключение: тост вешать на этот результат, не на `onError`. Персональные уроки не обрезать до `yearMonth`, как на `FinancePaymentsPage`. Детализация `computeTeacherAccrualBreakdown` атрибутирует платёж через `resolvePaymentTeacherId` → `personalLessonById.get(payment.personalLessonId)`. Урок может быть другого месяца, чем дата платежа; фильтр по `date` месяца молча выкинет такие проценты. Нужны уроки, на которые ссылаются платежи выбранного месяца, а не все уроки студии. `useSchedule()` и `useSubscriptionGroups()` питают `buildClassTeacherMap` / `groupsBySubId` для групповых платежей — не снимать и не сужать до месяца. Логику `payroll_refresh_settlement_lines` в том же PR не трогать.

### M9. `record_teacher_settlement_payment` возвращает `jsonb` из функции с `RETURNS uuid`

**Где:** `tangodb/supabase/migrations/20261218000004_editions_e3_rpc_gates.sql`, последняя версия функции (строка 3300). Найдено попутно при проверке M8; SQL в остальном в эту проходку не входил.

Гейт редакции добавлен как `RETURN jsonb_build_object('success', false, 'error', 'edition_forbidden', ...)`, а функция объявлена `RETURNS uuid`. PL/pgSQL не проверяет это при создании; при срабатывании гейта вызов падает с ошибкой приведения типа вместо понятного `edition_forbidden`. Соседняя `recalculate_teacher_settlement` (`RETURNS void`) использует `_edition_raise('edition_forbidden')` — так и задумано для не-`jsonb` функций.

**Последствие:** при выключенном `payroll` в редакции попытка выплаты показывает пользователю сырую ошибку Postgres (`invalid input syntax for type uuid`). Деньги не пишутся, но код ошибки для UI теряется. Хук `useRecordSettlementPayment` кладёт `error.message` в `{ success: false }`. `resolveMutationError` считает snake_case техническим мусором и подменяет незнакомый код запасным текстом. Строки `edition_forbidden` в `tangodb/src` сейчас нет, в `RPC_ERROR_KEY_MAP` её тоже нет.

**Как чинить:** новая миграция **после** фактического последнего файла в `tangodb/supabase/migrations/` (на 2026-10-25 это `20261223000001_remove_renter_miniapp.sql`, не `20261218000004` и не дата «сегодня», если она сортируется раньше). Заменить `RETURN jsonb_build_object(...)` на `PERFORM _edition_raise('edition_forbidden');` (`_edition_raise` делает `RAISE EXCEPTION '%', p_code`). Объявление `RETURNS uuid` не менять. Старую миграцию не править. В клиенте добавить `edition_forbidden` в `RPC_ERROR_KEY_MAP` и человеческий ключ в `keys.ts` / `ru.ts` / `en.ts`, иначе тост выплаты покажет общий `finance.payroll.error.record`, а не запрет редакции. Остальные функции из миграции гейтов с `RETURNS uuid`/`void` в этой задаче не трогать: у `enqueue_calendar_sync` (`void`) гейт делает голый `RETURN` — корректно. Поздние миграции `record_teacher_settlement_payment` не переопределяют.

## Чего эта проходка не покрыла

- Прод-данные и реальные размеры таблиц. Потолок 1000 строк подтверждён конфигом и отсутствием `.range()`, не замером на боевой базе.
- RLS, Edge Functions и Dev Console. Роль по-прежнему решает доступ к деньгам; модули меню его не заменяют. Отдельный контур — [аудит безопасности 2026-08-22](crm_security_audit_2026-08-22.md) (JWT/RLS/S01–S40); здесь только отмечено, что лимит refresh и откат посещаемости уже в коде.
- Тесты. `npm run lint` — это тот же `tsc --noEmit` (зелёный); ESLint в проекте нет, поэтому правила вроде `react-hooks/exhaustive-deps` никто не проверяет (пример — эффект пересчёта в M8). Не запускались node-проверки `test:*` (`test:rbac`, `test:finance-reports` и др.), SQL-тесты `test:db:*` (нужен локальный Postgres из `tangodb/scripts/local-db/`) и e2e — их нет. Зелёный `tsc` не заменяет регрессионные сценарии кассы/журнала.
- Браузерный прогон экранов. Менялся только этот документ (и при необходимости строка в индексе `AI_CONTEXT.md`).
- Ложные «неиспользуемые» имена возможны, если символ собирается строкой. Список хуков проверен поиском по идентификатору: снаружи файла вхождений нет.
- Лендинг, скрипты `tangodb/scripts/` и локальный стек `tangodb/scripts/local-db/` (вне `tangodb/src`).

## Промпты реализации (строго по порядку)

Готовые блоки для нового чата. Источник истины — пункты **H1–H3**, **M1–M9** и «Низкие» выше. Продуктовый смысл шагов, чеклиста, продажи, журнала и кассы не менять. Один промпт = один шаг таблицы «Порядок, если брать в работу».

**Ревизия промптов (2026-10-25):** закрыт логический разрыв P01 (allDone без полных выборок); P05 — нет готовой RPC прайса, ориентир `can_manage_prices`; P02 — два queryFn слотов; P03 — client directory, useSchedule на продаже PL; P06/P07 — подмены по диапазону, явная инвалидация M6, кнопка пересчёта зарплат.

**Ревизия промптов (2026-10-25, сверка с кодом):** DoD P01 больше не запрещает exists после allDone. P02 — стабильный `order` с `id`; отпуск педагога не третий queryFn. P03 — архивный справочник остаётся; счётчик визитов только у раскрытой карточки; CSV экспорта — месяц `statsMonth`. P04 — очередь не внутри баннера. P05 — создание тарифа, SECURITY DEFINER, поля `duration_minutes` и legacy `discipline_id`. P06 — журнал не сужать до недели сетки; view преподавателя; инвалидация абонементов обязательна. P07 — уроки зарплаты не резать по `yearMonth`; тост смотрит `{ success: false }`; `edition_forbidden` без ключа в `RPC_ERROR_KEY_MAP` пропадёт; миграция после `20261223000001`. P08 — ключи i18n удалять только если литерал вне `lib/i18n` пуст.

### Как запускать

1. Новый чат на **один** промпт (P01, затем P02, …).
2. Скопировать целиком блок между тройными кавычками.
3. Шаги внутри блока — сверху вниз. Подпункты P06 (M4 → M7 → M5 → M6) тоже по порядку: следующий только после DoD предыдущего.
4. Не начинать P(N), пока P(N−1) не закрыт.
5. Не объединять промпты в один прогон.

### Общие правила (все промпты с кодом)

- Сначала `.cursor/docs/ai/AI_CONTEXT.md`, затем файлы из блока «Прочитай сначала».
- Логика Supabase — только `tangodb/src/hooks/` и `tangodb/src/lib/`. RLS не трогать, `max_rows` не поднимать.
- Не дублировать хуки и компоненты. `SchedulePanel` в роутер не возвращать.
- Парсер `renterMiniappAddon` и чтение канала `miniapp` / `miniapp_debt` не удалять.
- Закрытые пункты [аудита 2026-08-19](crm_audit_2026-08-19.md) не открывать заново.
- Область — `tangodb/`. Dev Console и лендинг не трогать. Новая SQL-миграция допустима только в P05 (если без неё правка тарифа не атомарна) и в P07 (M9). Имя файла должно сортироваться после фактического последнего в `tangodb/supabase/migrations/` (на момент аудита `20261223000001_remove_renter_miniapp.sql`).
