# Аудит: Настройки · Аренда зала

Дата: 2026-08-02  
Раздел: `/settings/hall-rent` (`HallRentSettingsPage`)  
Состав: «Сдача зала арендаторам» (`RentalTariffsSettingsPage`) + «Затраты студии за зал на занятиях» (`VenueCostsSettingsPage`)  
Смежный CRM-контур: расписание аренд, `RentalInfoPopup` / `RecordRentalPaymentModal`, арендаторы, финансы (выручка / оплаты / должники).

Цель документа — зафиксировать пробелы и дефекты для последующей правки. Оценка с позиций: главный бухгалтер, администратор-кассир, владелец/директор сети студий, наёмный преподаватель.

Перекрёстная проверка с кодом CRM (`tangodb/`, 2026-08-02): права в `permissions.ts`, `HallRentSettingsPage`, `RentalInfoPopup`, `CreateRentalDialog`, `RecordRentalPaymentModal`, финансы и карточка арендатора.

---

## 1. Как устроен раздел сейчас

| Блок | Смысл | Кто видит | Кто меняет |
|------|--------|-----------|------------|
| Сдача зала арендаторам | Прайс для внешних арендаторов (почасовой / фикс) | `schedule.write` **и** `finance.read` | те же права |
| Затраты студии за зал | Управленческий расход при своих уроках | `finance.read` | только `owner` / `director` |

Навигация в настройках открыта при `finance.read` (owner, director, accountant).

Два разных контура под одним названием «Аренда зала»:
- **доход** от сдачи зала наружу;
- **внутреннее начисление расхода** на свои занятия (не арендная плата арендодателю-владельцу помещения).

## 2. Главный бухгалтер (обслуживание компаний)

### Что уже есть и полезно
- Версионирование правил затрат (черновик → принять), история периодов действия.
- Разделение внешних арендных платежей и внутренних начислений в финансах / CSV.
- Порог по числу участников на групповых уроках.
- Привязка per-lesson правил к преподавателю, дисциплине, локации.
- Баннер просроченного правила и подтверждение оплат при gap.
- В CRM арендатора уже есть реквизиты, договоры и документы; backend также содержит счета за период, строки счетов, авансы, обеспечительные депозиты и их распределение.
- Финансовый CSV уже включает фактические записи из `rental_payments` с датой платежа, датой аренды, арендатором и способом оплаты.

### Критичные пробелы

1. **Бухгалтер не может настраивать то, что обязан контролировать.**  
   `canManage` для затрат = только owner/director. Accountant с `finance.read` видит историю, но не создаёт, не правит и не принимает версии. На практике главный бухгалтер сети как раз ведёт ставки зала и закрытие периодов — сейчас вынужден просить директора нажать «Принять».

2. **Бухгалтер не видит блок тарифов для арендаторов.**  
   Блок сдачи требует ещё и `schedule.write`, которого у accountant нет. В одном разделе «Аренда зала» бухгалтер видит только расходную сторону и не может сверить прайс дохода.

3. **История версий непрозрачна для сверки.**  
   В списке: номер версии, режим, даты, статус и «пример 4/5 чел.». Нет развёртки: кто из преподавателей, какие локации, суммы, пороги. Принять/отклонить и провести аудит по факту невозможно без устного пояснения директора.

4. **Превью 4/5 человек почти всегда врёт при обязательном преподавателе.**  
   `previewGroupVenueCost(rules, 4)` вызывается без `teacherMemberId` / локации / дисциплины. После обязательного выбора преподавателя matching часто пустой → в UI «0», хотя правила заполнены. Бухгалтер получает ложное ощущение, что правило «нулевое».

5. **Режим «Фиксированная оплата» — одна сумма на всю организацию.**  
   Нет разбивки по локациям/студиям, нет привязки к договору с арендодателем, нет графика платежей арендодателю. Для сети студий и для учёта по юрлицам/залам этого недостаточно.

6. **Нет связи с «реальной» арендой помещения студией у арендодателя.**  
   CRM арендаторов моделирует договоры, счета, авансы и депозиты для тех, **кому студия сдаёт зал**, но раздел venue cost не моделирует договор студии с собственником помещения, входящие счета, НДС и коммуналку. Внутренние `venue_cost_*` — управленческий cost allocation. В UI это слабо отделено от слова «аренда»; при выгрузке в 1С/Excel бухгалтер может спутать управленческий расход и реальный платёж арендодателю.

7. **Нет калькулятора / сметы «что начислится за месяц».**  
   Нельзя задать «преподаватель X, 12 групп, средняя явка 6» и получить ожидаемый расход до принятия правила.

8. **Ошибки валидации — одной фразой.**  
   `venueCosts.error.invalid` не показывает, какое именно поле сломано (даты, пороги, преподаватель, открытый верхний tier). На больших правилах это потеря времени.

9. **Нет экспорта конфигурации тарифов/правил из настроек.**  
   CSV есть по фактическим начислениям в финансах, но снимок «какие ставки действовали / действуют» из раздела настроек не выгрузить для акта сверки между компаниями.

10. **Архив тарифов арендаторов недоступен в UI.**  
    В состоянии редактора есть `status: active | archived`, в payload уходит, но переключателя в форме нет — нельзя корректно «закрыть» старый прайс без удаления/перезаписи.

11. **Долги арендаторов не в «Должниках».**  
    `FinanceDebtorsPage` / `useFinancialDebtors` — только клиентские долги (абонементы / персоналки). Неоплаченные и частично оплаченные аренды зала бухгалтер в общем списке должников не видит; сверка «кто должен студии» неполная.

12. **Оплаты аренды живут в отдельной таблице и выпадают из кассовой сверки.**  
    `rental_payments` ≠ `payments`. В `FinancePaymentsPage` нет фильтра/строк по аренде; в `FinanceRevenuePage` блок «по способу оплаты» (`byMethod`) строится только по клиентским `payments` — **нал/карта/перевод по аренде зала в разбивку не входят**, хотя `rentalTotal` в gross уже добавлен. Итог месяца и «касса по методам» расходятся.

13. **Нет сторно / коррекции оплат аренды.**  
    Для клиентских платежей есть `PaymentCorrectionDialog` и журнал коррекций. Для `rental_payments` — только запись вперёд. Ошибка кассира (не тот метод, дубль, лишняя сумма) чинится вручную вне процесса или «переплатой» без акта.

14. **Нет явного закрытия кассового дня с арендой.**  
    Бухгалтеру нужен срез «сегодня / смена: абонементы + разовые + аренда зала» по методам и по кассиру. Сейчас аренда либо в выручке месяцем, либо в карточке арендатора — операционный Z-отчёт не собирается.

15. **Аудит «кто принял деньги» слаб в UI.**  
    В списке платежей аренды в попапе — сумма и метод, без автора и без комментария к методу (поле `methodComment` в модалке есть в state, ввода нет). Для главного бухгалтера сети при разборе кассы это обязательно.

16. **Нет предупреждения о переплате и лимита в UI.**  
    Статус `overpaid` в модели есть; модалка позволяет ввести сумму > остатка без confirm. Бухгалтер потом видит «Переплата» без объяснения, было ли это аванс / ошибка / депозит.

17. **Три параллельных денежных контура аренды не сведены в единый регистр.**  
    В БД существуют `rental_payments`, `rental_invoice_payments`, `rental_advances`, распределения авансов и движения депозитов. Общая выручка, CSV и `useRentalPayments` читают только `rental_payments`. Оплата счёта, аванс или зачёт депозита могут быть корректны в карточке арендатора, но не попасть в общий кассовый журнал / `byMethod`; обратный риск — повторно записать одно поступление и как оплату брони, и как оплату счёта.

18. **Backend счетов/авансов почти не доведён до рабочего UI.**  
    Есть RPC и хуки создания счёта, оплаты счёта, приёма и распределения аванса, но в приложении вызываются только read-хуки списка счетов и финансовой сводки. В карточке арендатора бухгалтер видит суммы и статусы, однако не может из UI создать/провести счёт, принять аванс или распределить его.

19. **Нет отдельной даты хозяйственной/кассовой операции.**  
    Платёж аренды попадает в период по системному `created_at`; кассир не задаёт дату поступления по банку/эквайрингу и не может корректно внести вчерашнюю операцию после восстановления связи. В результате закрытый период может измениться из-за даты ввода, а не даты фактического поступления.

20. **Смешаны кассовый метод и начисление дохода.**  
    Выручка по аренде считается по дате получения денег, при этом долг — по сумме брони/счёта. Нет отдельного отчёта «начислено за оказанные аренды периода / оплачено / авансы / задолженность» и сверки между датой аренды, периодом счёта и датой платежа. Для управленческого учёта и передачи в бухгалтерию этого недостаточно.

21. **Счёт в CRM — расчётная запись, а не готовый первичный документ.**  
    Есть период, срок оплаты, строки и статус, но нет подтверждённого контура нумерации и формирования печатного счёта/акта, НДС/«без НДС», реквизитов юрлица студии, отправки и фиксации версии документа. Загружать произвольные файлы в карточку можно, но это не заменяет связанный со строками аренды закрывающий документ.

22. **Нет фискального статуса и идентификатора чека.**  
    У платежа хранятся сумма, способ, комментарий, автор и системное время, но нет признака «чек сформирован/не требуется», номера чека, кассы/эквайринговой операции и возвратного чека. Если CRM используется как кассовое рабочее место, нужна интеграция либо обязательная фиксация внешнего чека; требования должны настраиваться по стране и юрлицу.

23. **Отмена брони не образует контролируемую финансовую операцию.**  
    Для серии backend поддерживает `none / full_penalty / partial_penalty / manual`, но UI всегда отправляет `none`; ветка `manual` по суммам фактически no-op; возврат и перенос в аванс в enum **не** заложены. Для разовой отмены передаётся только причина. Уже принятые деньги, удержание по договору, возврат или перенос в аванс не оформляются единым сценарием и не попадают в журнал корректировок.

24. **`created_by` в БД, но не в приложении.**  
    `rental_payments.created_by` заполняется на backend, но `useRentalPayments` не выбирает поле, тип `RentalPayment` не содержит автора, CSV и UI истории платежей не показывают кассира. Для кассовой сверки и разбора споров поле уже есть — нужно только протянуть в API/UI.

25. **В истории версий venue cost нет «кто принял».**  
    В БД у версии есть `accepted_by` / `accepted_at`; `mapVenueCostVersion` мапит только `acceptedAt`, без автора. Бухгалтер при аудите периода не видит, кто утвердил ставки (директор или делегированный пользователь).

26. **Бухгалтер не может создать/изменить бронь в расписании.**  
    `schedule.write` у accountant **нет** (`permissions.ts`: только operational admin и teacher). Бухгалтер может принять оплату (`finance.read`), но не завести аренду и не исправить слот — в малых студиях это лишний ручной шаг «админ бронирует, бухгалтер принимает деньги».

27. **Нет UI редактирования суммы аренды после создания.**  
    `useUpdateRental` реализован в `useRentals.ts`, но **нигде не подключён**; RPC `update_rental` дополнительно требует `member_can_manage_rentals()` (accountant с `finance.read` не проходит), а изменение `fixed_amount` — `can_read_financial()`. Ошибка суммы при бронировании (0, неверный fixed, ручная скидка) не исправляется без директора/скрипта; кассир и бухгалтер застревают на неверном остатке в `RentalInfoPopup` / `RecordRentalPaymentModal`.

28. **Просроченное правило venue cost — только баннер, без рабочего сценария для бухгалтера.**  
    `VenueRuleExpiryNotice` ведёт в настройки, но accountant не может «Принять» версию (`canManage` = owner/director). Подтверждение gap (`venue_rule_acknowledged`) встроено в **клиентские** платежи (`usePayments`, `useSingleVisits`), не в отдельное действие «закрыть период / принять новые ставки». Бухгалтер видит проблему, но не может её закрыть без директора или оплаты урока.

29. **Выручка: rental в gross, но не в счётчике операций.**  
    `FinanceRevenuePage`: `rentalTotal` добавляется в `grossTotal`/`netTotal`, а `stats.count` и блок `byMethod` строятся только из клиентских `payments` — карточка «N платежей» и разбивка по методам не отражают реальную кассу с арендой.

30. **Почасовая / серийная аренда: остаток и статус могут расходиться между экранами.**  
    Schedule/detail уже часто отдают `_rental_effective_amount` **как** `fixed_amount`, поэтому простой `remaining = fixedAmount - paid` на этих path часто «случайно» верен. Но UI ещё показывает raw `calculatedAmount`; `record_rental_payment` считает статус по сырой колонке `rentals.fixed_amount`; карточка арендатора / серии могут жить по другим полям. Итог: кассир/бухгалтер видят разный остаток/статус в зависимости от экрана.

31. **Карточка арендатора: финансы read-only без действий.**  
    `FinanceTab` показывает долги, счета, авансы и депозиты, но нет кнопок «создать счёт», «принять аванс», «оплатить счёт» — только таблицы. Бухгалтер сверяет цифры, но проводки делает вне CRM (см. п. 18).

### Желательные правки (бухгалтер)

- [ ] Дать accountant право создавать/редактировать/принимать venue-cost (или отдельное `venue_costs.manage`).
- [ ] Показывать блок тарифов арендаторов на чтение при `finance.read` (запись тарифов — отдельное продуктовое решение; в поэтапных промптах этап 7 только read).
- [ ] Раскрываемая карточка принятой версии с полной матрицей правил.
- [ ] Превью с выбором преподавателя/локации/дисциплины; не считать «общий» preview по null-scope.
- [ ] Для fixed_period — суммы по локациям (или явная пометка «одна сумма на всю org»).
- [ ] Понятная подпись: «это не платёж арендодателю, а учёт расхода на занятие».
- [ ] Детализация ошибок валидации по кодам.
- [ ] UI архивации тарифов + фильтр active/archived.
- [ ] Экспорт текущих/исторических правил.
- [ ] Включить неоплаченные аренды в должников (или отдельный таб «Арендаторы»).
- [ ] Единый кассовый журнал / byMethod с `rental_payments` (или явная секция «аренда зала»).
- [ ] Сторно/коррекция оплат аренды по тому же контуру, что клиентские платежи.
- [ ] Автор платежа + комментарий метода в UI; confirm при сумме > остатка / режиме «аванс».
- [ ] Спроектировать единый регистр поступлений аренды: бронь, счёт, аванс и депозит без двойного учёта; включить все типы в журнал, `byMethod`, смену и CSV.
- [ ] Довести UI счетов и авансов: создание, проведение, оплата, распределение, отмена распределения и история действий.
- [ ] Хранить отдельно `operation_date` и `created_at`; закрытые периоды менять только через контролируемую корректировку.
- [ ] Добавить отчёт «начислено / оплачено / авансы / долг» по дате аренды, периоду счёта и дате платежа.
- [ ] Определить продуктовый scope первички: печатный счёт/акт, нумерация, НДС, реквизиты организации, версия и отправка — либо явный экспорт во внешнюю бухгалтерию.
- [ ] Добавить статус фискализации/внешнего чека и реквизиты кассовой операции, если применимо для страны и юрлица.
- [ ] При отмене выбирать финансовое действие: без удержания, штраф, возврат, перенос в аванс; результат проводить как отдельную аудируемую операцию.
- [ ] Протянуть `created_by` из `rental_payments` в хук, тип, CSV и историю платежей.
- [ ] В истории venue cost показывать `accepted_by` / `accepted_at` (имя из team).
- [ ] UI редактирования суммы аренды (`useUpdateRental`) с аудитом и правами (бухгалтер / admin с кассой).
- [ ] Отдельное действие «подтвердить просроченное правило» / принять новую версию без клиентского платежа.
- [ ] В выручке: счётчик операций и `byMethod` включают аренду; единая формула остатка по `_rental_effective_amount`.

## 3. Администратор-кассир (операционный admin / ресепшен)

### Фактический доступ сейчас

| Действие | Полный admin (`schedule.write`, `payments.write`) | Reception (`restricted_admin`) | Нужно для кассы |
|----------|---------------------------------------------------|--------------------------------|-----------------|
| Создать разовую аренду / серию | да | нет | да |
| Видеть/выбрать тариф и сумму при создании | **нет** (`finance.read` только owner/director/accountant) | нет | да |
| Записать оплату аренды в `RentalInfoPopup` | **нет** (`canRecordPayment` = `finance.read`) | нет | **критично** |
| Видеть остаток / статус оплаты на блоке | текст статуса в subtitle сетки **да** (без `finance.read`); сумма, остаток и rose-ring — **нет** | нет | да (сумма + ring — этап 1) |
| Открыть `/settings/hall-rent` (прайс) | **нет** | нет | желательно lookup |
| Принять оплату абонемента / персоналки | да (если `admin_can_accept_payments`) | да | да |
| Карточка арендатора: финансы | **нет** (`renters.finance.read` = FINANCIAL_READ) | нет | частично |
| Должники / выручка / журнал оплат | **нет** (`finance.read`) | нет | смена/сверка |

Итог: администратор-кассир — основной человек у стойки — **может забронировать зал, но не может ни выставить сумму по прайсу, ни принять деньги за аренду в CRM**. Оплата аренды доступна только ролям с `finance.read` (директор/бухгалтер), которых у стойки обычно нет.

### Критичные пробелы (касса)

1. **Приём оплаты аренды завязан на `finance.read`, а не на `payments.write`.**  
   `RentalInfoPopup.canRecordPayment` требует `can("finance.read")`. Клиентские платежи идут через `payments.write` / `adminCanAcceptPayments`. Для кассира два разных мира: «деньги за урок — да, деньги за зал — нет».

2. **Создание аренды без финполей → сумма 0.**  
   В `CreateRentalDialog` при отсутствии `finance.read`: `fixedAmount`/`initialPayment` уходят как 0, тариф не выбирается. Кассир бронирует слот «как занятость зала», а бухгалтерия потом вручную догоняет суммы — или бронь так и остаётся бесплатной в учёте.

3. **Прайс из настроек недоступен у стойки.**  
   Тарифы арендаторов требуют `finance.read` + `schedule.write` даже на просмотр списка в настройках. Кассир не может подсмотреть «сколько зал А вечером», кроме как спросить директора или вести бумажку.

4. **Выбор fixed-тарифа не подставляет сумму.**  
   Даже у директора: выбор тарифа в разовой форме не автозаполняет `fixedAmount`. Кассир/админ печатает цифру руками → риск опечатки и расхождения с прайсом.

5. **Почасовой тариф в разовой форме скрыт** (см. F7).  
   Кассир создаёт «на 3 часа сейчас» — в UI только fixed; hourly рассчитан в сериях. Операционный сценарий «разово по часам» ломается.

6. **Нет операционного списка «сегодня не оплатили аренду».**  
   На сетке есть цвет/статус оплаты (для тех, кто видит finance), но нет кассового inbox: неоплаченные на сегодня / просроченные частичные. Admin без finance даже бейдж суммы не видит.

7. **Модалка оплаты сырая для стойки.**  
   - нет поля комментария к методу (state есть, UI нет);  
   - нет confirm при сумме > остатка;  
   - нет чека / копии для арендатора;  
   - после оплаты нет явного «сдача / остаток 0»;  
   - нельзя принять оплату, если статус уже `paid`, даже если нужно дозаписать корректировку (см. сторно у бухгалтера).

8. **Reception-admin вообще вне контура аренды.**  
   `restricted_admin` не имеет `schedule.write` → не создаёт аренды и не видит renters write. Если ресепшен = касса, аренда зала для него закрыта полностью (и запись, и деньги).

9. **Отмена серии с `financialAction: "none"` только.**  
   Кассир/админ отменяет вхождение серии без штрафа/частичного удержания в UI — финансовые последствия отмены не проговариваются у стойки.

10. **Путаница «аренда» vs «затраты студии» у кассира.**  
    Закрытие урока с «арендой» (venue cost) и оплата внешней аренды — разные сущности. Admin без finance.read venue cost не видит; но если когда-то откроют — нужна явная терминология, чтобы кассир не пытался «взять с педагога за зал».

11. **Нельзя указать фактическую дату оплаты.**  
    Операция всегда датируется моментом записи в CRM. Банковский перевод за вчера, вечерняя сверка после полуночи или восстановление после сбоя попадут не в тот кассовый день.

12. **Нет реквизитов чека / эквайринга и контроля выдачи подтверждения.**  
    Кассир выбирает только `cash / transfer / card / other`. Нет номера чека, терминала/кассы, идентификатора банковской операции и статуса «чек выдан». Нельзя быстро доказать, что конкретное поступление прошло по внешней ККТ или эквайрингу.

13. **Корпоративный арендатор со счётом и авансом обслуживается вне рабочего сценария кассира.**  
    Backend умеет счета, авансы и депозиты, но карточка показывает их преимущественно read-only, а кассовая модалка пишет только прямую оплату брони. Кассир не понимает, куда отнести перевод: к конкретной аренде, счёту или авансу.

14. **При отмене нельзя выбрать финансовый результат.**  
    Даже при уже принятой оплате UI отмены серии всегда передаёт `financialAction: "none"`. Нет одной последовательности «отменить → удержать/вернуть/перенести в аванс → выдать подтверждение».

15. **История оплаты недостаточна для ответа клиенту у стойки.**  
    В popup выводятся только сумма и способ. Системное время, кассир, комментарий, номер операции/чека и связь со счётом не показаны, поэтому спорную оплату приходится искать вне карточки аренды.

16. **Статус оплаты на сетке — текст без суммы и без визуального долга.**  
    `SchedulePageContainer` добавляет в subtitle тексты «оплачено / не оплачено» для всех с `paymentStatus` (без проверки `finance.read`), но `LessonBlock` рисует rose-ring только для персоналок (`paid === "no"`). Кассир видит слово «не оплачено», но не сумму и не такой же акцент, как на долге урока — легко пропустить.

17. **Нет правки суммы после брони.**  
    Тот же разрыв, что для бухгалтера: `useUpdateRental` не подключён. Кассир забронировал с суммой 0 (нет `finance.read` при создании) — исправить в CRM некому, только через директора.

18. **Остаток / статус оплаты могут расходиться между экранами.**  
    На schedule/detail backend часто уже отдаёт effective как `fixed_amount`, но модалка/popup смешивают поля, а `record_rental_payment` пишет статус по сырой колонке — при hourly/корректировке кассир может увидеть «не ту» сумму или статус.

19. **`methodComment` в state, поля в UI нет.**  
    Комментарий к методу (перевод, эквайринг) передаётся в RPC только если заполнен в state, но пользователь не может ввести — поле не отрисовано (в отличие от клиентских платежей).

20. **Парадокс ролей у стойки.**  
    Operational admin: `schedule.write` + `payments.write`, но оплата аренды через `finance.read`. Accountant: `finance.read` без `schedule.write` — может принять деньги, но не создать бронь. Ни одна типичная «стойка» закрывает цикл сама.

### Желательные правки (админ-кассир)

- [ ] `canRecordPayment` для аренды: full operational admin с `payments.write` **и** backend `member_can_manage_rentals` (или отдельное `rentals.payments.write`) — **не** голый `payments.write` (reception тоже его имеет); суммы/остаток показывать при этом операционном праве, не только при полном `finance.read`.
- [ ] При создании аренды admin с правом приёма платежей видит тарифы + сумму + начальный платёж (хотя бы read прайса + write оплаты).
- [ ] Lookup прайса: read-only тарифы при `schedule.write` или `payments.write` (без manage venue-cost).
- [ ] Автоподстановка `fixedAmount` из выбранного тарифа; для hourly — превью суммы по длительности.
- [ ] Кассовый список: сегодняшние / просроченные неоплаченные аренды + кнопка «принять оплату».
- [ ] Довести `RecordRentalPaymentModal`: комментарий метода, confirm переплаты, автор в истории.
- [ ] Решить продукт по reception: либо аренда в scope ресепшена, либо явный запрет с подсказкой «зовите admin/director».
- [ ] При отмене — хотя бы подсказка про уже принятые деньги / штраф (не молча `financialAction: "none"`).
- [ ] Поле «дата операции» с ограничением по открытой смене/периоду и отдельным отображением времени создания записи.
- [ ] Выбор назначения платежа: бронь / счёт / аванс / депозит, с защитой от двойного проведения.
- [ ] Реквизиты внешнего чека/эквайринга и действие «распечатать/отправить подтверждение».
- [ ] Единый мастер отмены с возвратом, удержанием или переносом суммы в аванс.
- [ ] На блоке аренды: сумма долга / rose-ring как у персоналок (при операционном праве, без полного finance).
- [ ] UI поля `methodComment` в `RecordRentalPaymentModal`.
- [ ] Единый остаток по effective amount; превью суммы при создании hourly-разовой.

## 4. Владелец / директор сети студий

### Что уже есть и полезно
- Один экран вместо двух разрозненных пунктов меню.
- Тарифы арендаторов с привязкой к локации или «все локации».
- Льготные часы (дни + интервал + цена) для почасового тарифа.
- Per-lesson затраты с разными ставками по залу / направлению / преподавателю.
- Workflow draft → accept без порчи истории.
- Ссылка из расходов (`/settings/hall-rent?new=1`).

### Проблемы удобства и масштаба сети

1. **Дублирование правил «на каждого преподавателя».**  
   Преподаватель обязателен. Для сети из 10+ педагогов и 3 залов директор вынужден копировать одинаковые матрицы вручную. Нет шаблона «базовое правило → применить к выбранным преподавателям», нет «все преподаватели» как явной опции (раньше null означал всех — сейчас запрещён).

2. **Нет фильтра/группировки тарифов по локации.**  
   Плоский список. При нескольких студиях сложно понять, какой прайс относится к какому залу.

3. **Почасовой тариф в настройках есть, в разовой аренде — почти нет.**  
   `CreateRentalDialog` подставляет только `tariffType === "fixed"`. Почасовой живёт в сериях. Директор создаёт «Почасовой зал А» и не понимает, почему в разовой брони его нет.

4. **Приоритет льготных правил всегда 0.**  
   Поле `priority` в БД и в типе есть, в UI не редактируется. При пересечении окон с одинаковым priority сервер ругается на ambiguous overlap — пользователь не может явно задать «вечер важнее дня».

5. **Срок действия у льготного правила не редактируется.**  
   У `RentalTariffRule` есть `validFrom` / `validTo`, в модалке тарифа полей нет — нельзя заранее завести «новогодний прайс» внутри тарифа.

6. **Вложенные карточки и дублирующие подписи.**  
   `HallRentSettingsPage` оборачивает секции в white card; `VenueCostsSettingsPage` внутри снова рисует card для редактора и истории + свой `sectionHint` поверх уже данного `hallRent.studioSubtitle`. На экране шумно, смысл размывается.

7. **Принятую версию нельзя «открыть как есть».**  
   Редактируются только draft. Чтобы посмотреть детали accepted — только создать новый черновик (и риск случайно сохранить). Нет read-only просмотра / «создать копию».

8. **Нет сравнения «сколько берём с арендатора» vs «сколько учитываем себестоимостью урока».**  
   Для директора сети это ключевой управленческий вопрос (загрузка зала внешними vs своими занятиями). На одном экране цифры не сводятся.

9. **Fixed period не масштабируется на сеть.**  
   Одна сумма на org: нельзя «Студия Центр — 120 000/мес, Студия Юг — 80 000/мес» без костылей и ручных расходов.

10. **Пустые состояния слабые.**  
    «Тарифов пока нет» / «Правила ещё не созданы» без CTA «добавить локацию», «открыть арендаторов», короткого «с чего начать».

11. **Права admin.**  
    Операционный admin с расписанием, но без `finance.read`, не попадает в раздел — тарифы аренды может задавать только фин.контур. Для сети, где прайс зала ведёт управляющий студии (admin), это узкое место. **Критичнее:** тот же admin не принимает оплату аренды у стойки (см. §3) — директор думает, что касса закрыта CRM, а по залу деньги идут мимо системы.

### Желательные правки (директор)

- [ ] Массовое назначение одного per-lesson правила на несколько преподавателей / копирование между локациями.
- [ ] Фильтр тарифов и правил по локации.
- [ ] В разовой аренде показывать и hourly (с превью суммы), либо явно подписать в настройках: «почасовой — только для серий».
- [ ] UI приоритета и дат действия у льготных окон.
- [ ] Упростить вёрстку: одна иерархия заголовков, без карточки-в-карточке.
- [ ] Read-only просмотр accepted + «копировать в черновик».
- [ ] Fixed_period по локациям.
- [ ] Онбординг пустого состояния.
- [ ] Прояснить, кто из ролей (admin?) должен вести тарифы аренды.

## 5. Наёмный преподаватель

### Фактический доступ
- В раздел «Настройки · Аренда зала» преподаватель **не попадает** (`finance.read` нет) — с точки зрения конфиденциальности ставок это обычно правильно.
- Преподаватель **может закрывать** свои уроки (closure); сумма «Аренда: …» возвращается только финансовой роли — преподаватель часто видит факт закрытия, но не управленческую сумму.

### Проблемы восприятия и процесса

1. **Слово «аренда» в закрытии урока путает.**  
   Для наёмного педагога «аренда зала» = «с меня сняли за зал». В модели TangoDB это расход студии в P&L, **не** автоматический вычет из зарплаты (`FinancePayrollPage` venue cost не учитывает). Риск конфликтов и недоверия при формулировках в UI журнала/popup.

2. **Нет прозрачного «моего» условия по залу.**  
   Если договор преподавателя «процент минус зал» или «фикс зала с урока» — педагог не видит свою строку правила. Он либо слепо подтверждает явку, либо спорит с администрацией вне системы.

3. **Явка напрямую двигает сумму студии, но педагог об этом не предупреждён.**  
   Пороги «от N участников» зависят от числа присутствовавших при закрытии. Ошибка в счётчике → неверное начисление расхода. Подсказки у кнопки закрытия нет («от числа зависит учёт зала»).

4. **Преподаватель с правом писать расписание всё равно не управляет тарифами арендаторов.**  
   Ожидаемо для финансов; но если студия просит педагога «сам сдай зал другу» — путь только через admin/owner, прайс из настроек педагог не увидит.

5. **Собственный payroll не объясняет «аренду».**  
   В «моей зарплате» нет строки про зал. Если где-то всплыло слово «аренда», сверка невозможна.

### Желательные правки (преподаватель)

- [ ] Переименовать пользовательские строки закрытия урока: «учёт зала студией» / «затраты студии», не «аренда» в контексте зарплаты педагога.
- [ ] Опционально: read-only «ваши условия по залу» (только свои `teacherMemberId` правила), если директор включит показ.
- [ ] Короткая подсказка при закрытии: число участников влияет на учёт зала студией.
- [ ] Не смешивать venue cost с payroll без явной продуктовой модели «вычет зала из ставки».

## 10. Вердикт

Раздел правильно **разделяет** два контура (сдача наружу vs учёт зала на своих уроках) и уже имеет серьёзный backend для версий, начислений, счетов, авансов и депозитов (в т.ч. `created_by` на платежах и `accepted_by` на версиях — данные есть, UI не показывает).

Главный продуктовый разрыв у стойки: **администратор-кассир бронирует зал, но не видит прайс/сумму и не принимает оплату** (`finance.read` vs `payments.write`); статус «не оплачено» на сетке текстом есть, сумма и визуальный долг — нет. **Главный бухгалтер** почти только зритель в настройках затрат (не может принять версию), не видит блок тарифов дохода без отдельного права, а денежный контур аренды фрагментирован: прямые оплаты не во всех кассовых отчётах, счета/авансы read-only в карточке. **Ни кассир, ни бухгалтер** не могут исправить сумму брони в UI (`useUpdateRental` не подключён). До единого регистра и выровненной effective-семантики (включая write-path `record_rental_payment`) кассовую сверку считать неполной.

**Директор сети** упирается в «одна сумма / копируй правила вручную». Для **преподавателя** настройки закрыты корректно, но язык «аренды» при закрытии урока создаёт ложное ощущение личного долга за зал.

Использовать этот файл как чеклист правок; не считать всё обязательным к реализации одним релизом — идти по приоритетам §8.

## 11. Промпты для поэтапной реализации в текущей CRM

Ниже — промпты для Cursor Agent. Выполнять **строго по номерам 1→23** (каждый следующий опирается на предыдущие). Один этап — отдельная задача и отдельная проверяемая порция. Карта F→этап — ниже; детали дефектов — §6 и §8.

**Критическая цепочка зависимостей (не нарушать):**
`1→2` (касса + effective) → `4→5` (агрегаты → регистр) → `6` (правка суммы) → `8` (сторно) → `9` (operation_date) → `10→11` (счета/авансы → отмена) ; параллельно venue: `3`, затем `7→15→16` ; стойка: `7→12→13` (политика reception **до** create с суммой) → `14` ; P2: `17…23` (22 после 12).

### Известные зависимости и ловушки (читать перед этапами)

1. **Frontend ≠ backend.** Сейчас `record_rental_payment` завязан на SQL `can_read_financial()` (owner/director/accountant). Смена только UI-права `payments.write` **не откроет** кассу: нужна узкая миграция RPC/helper, без выдачи полного финансового контура admin. **Не** заменять gate на голый `payments.write` — у `restricted_admin` он уже есть (см. п. 4). При этом `get_rentals_for_schedule_week` уже отдаёт суммы/статус при `member_can_see_rental_sensitive()` (= `member_can_manage_rentals() OR can_read_financial()`), то есть operational admin часто **уже получает** суммы в payload; `RentalInfoPopup` / модалка всё равно прячут их за `finance.read`. В `get_rental_detail` суммы/остаток доступны при sensitive, но **список платежей** и часть контактов — только при `can_read_financial()`; этап 1 должен явно решить: история оплат кассиру через тот же helper или только сумма/остаток. Этап 1 = UI + `record_rental_payment` (+ точечно `get_rental_detail`). Общий запрет «не трогать RLS» не отменяет минимальные RPC/helper-миграции там, где UI-право иначе бесполезно (см. п. 16).
2. **`adminCanAcceptPayments` — не permission.** Это флаг `PermissionOptions` / `admin_can_accept_payments`, который уже входит в `can("payments.write")` для operational admin. В промптах не писать «`payments.write` **или** `adminCanAcceptPayments`» как два равноправных права. Owner/director **не** имеют `payments.write` — у них путь `finance.read`; этап 1 не должен переводить их на `payments.write`.
3. **Accountant не имеет `payments.write`.** Сейчас оплату аренды даёт `finance.read`. Этап 1 обязан **сохранить** приём оплаты для accountant (и owner/director); кассиру добавить операционное право, а не заменить одно другим.
4. **`restricted_admin` уже имеет `payments.write`.** Не выдавать ему оплату/суммы аренды «за компанию» до явной политики этапа 12. Backend: `member_can_manage_rentals()` для reception уже `false` — не расширять sensitive/оплату через голый `payments.write`. **Канонический gate кассы аренды:** `can_read_financial()` **или** (`member_can_manage_rentals()` ∧ право приёма платежей у full operational admin, с учётом org-настройки `admin_can_accept_payments`). **Запрещено** `can("payments.write")` / `payments.write` как единственное условие — reception тоже проходит. Teacher в контур оплаты аренды **не** входит и после этапа 12 (этап 12 = политика reception + lookup; этап 13 = create с суммой по этой политике).
5. **Этап 1 ≠ создание брони с суммой.** После этапа 1 кассир принимает оплату по уже существующей брони с суммой (для приёмки нужна тестовая бронь с amount > 0 от director/accountant). Создание с тарифом/суммой ≠ 0 — **этап 13**; для `restricted_admin` этап 13 смотрит политику **этапа 12** (строго: 12 → 13). Правка суммы 0 — этап 6. F14 (CreateRentalDialog → 0) **не** закрывается этапом 1.
6. **Этап 4 — временный патч агрегатов.** `byMethod`/`count` по `rental_payments` до регистра; **обязательный follow-up этапа 5** — перевести чтение агрегатов на канонический регистр (этапы 8–11 тоже только через него). Не плодить вторую постоянную формулу суммирования. Фильтр периода до этапа 9 — по `created_at` (и provisional `operation_date`); после этапа 9 — по настоящему `operation_date`. Пометка «как аванс» на этапе 4 — только UI/семантика confirm, **без** записи в `rental_advances` (авансы — этап 10).
7. **`operation_date`.** На этапе 5 в read-model допустим provisional `operation_date = created_at`. Полноценное поле, UI даты и закрытие периода — только этап 9.
8. **Venue cost accept + read тарифов на backend.** `save_venue_cost_rule_draft` / `accept_venue_cost_rule_version` сейчас `owner|director` в SQL — этап 7 без миграции этих RPC не даст бухгалтеру manage. Дополнительно: `list_rental_tariffs` сейчас требует `member_can_manage_rentals()` **до** маскировки цен; accountant с `finance.read` **не проходит** даже на список (не только на price). Этап 7: list для `member_can_manage_rentals() OR can_read_financial()`; write тарифов — по-прежнему manage (+ finance, как сейчас). В UI `HallRentSettingsPage`: `canRental = schedule.write && finance.read`, `VenueCostsSettingsPage.canManage = owner|director`, а `RentalTariffsSettingsPage` **не разделяет** read/write — все слои менять согласованно (read-only для accountant).
9. **F6 ≠ «только finance.read» навсегда.** `canAccessSettingsSection("hall-rent")` сейчас избыточен, но этап 7 не должен сузить его так, чтобы сломать этап 12: operational admin с lookup прайса (без полного `finance.read`) либо попадает в `/settings/hall-rent` по отдельному праву тарифов, либо получает lookup **вне** settings (модалка/schedule) — выбрать явно на этапе 12 и не закрывать путь на этапе 7.
10. **Тесты.** В `tangodb/` нет Vitest: RBAC — `npm run test:rbac` (`scripts/rbac-regression-check.mjs`), превью venue cost — `npm run test:venue-cost-preview`, SQL/RPC — `npm run test:db:*` (например `test:db:rental-series`, `test:db:venue-cost`). Typecheck — `npm run lint` (tsc). Не требовать «UI/unit Vitest»: добавлять assert-скрипты / расширять существующие `scripts/*-check.mjs` и SQL-тесты в том же стиле.
11. **Этапы 1 и 2 — одна кассовая порция (рекомендуется один PR).** Этап 1 открывает суммы/оплату. Schedule/detail уже часто отдают `_rental_effective_amount` **под именем** `fixed_amount`, но UI местами смешивает raw `calculatedAmount` / колонки, а `record_rental_payment` до сих пор считает статус по сырому `rentals.fixed_amount`. Этап 2 обязателен сразу после (или в том же PR); без него остаток/статус после оплаты на write-path могут врать.
12. **Этап 12 до этапа 13 (обязательно).** Политика `restricted_admin` и lookup прайса — этап 12; автоподстановка цены / create без скрытого 0 — этап 13. Не делать 13 раньше 12: иначе create для reception либо молча расширится, либо останется дырой. Этап 22 опирается на политику этапа 12.
13. **Этапы 6 и 13 — не только UI.** `update_rental`: всегда `member_can_manage_rentals()`; смена `fixed_amount` — ещё `can_read_financial()`. **Operational admin** проходит первый gate, но **не** второй — без узкого helper (тот же канонический gate, что этап 1) UI `useUpdateRental` для кассира не заработает. **Accountant** не проходит `member_can_manage_rentals()` — нужен отдельный узкий RPC «только сумма/валюта» **или** явная эскалация в UI (не откладывать). Уже есть SQL-ошибка `paidExceedsFixed` при `paid > new_fixed AND new_fixed > 0`, но **дыра**: `new_fixed = 0` при уже оплаченном **не** блокируется — на этапе 6 усилить hard block на любое `new_amount < paid`. `create_rental`: ручной `fixed_amount > 0` без `tariff_id` требует `can_read_financial()`; при переданном `tariff_id` сумма считается на сервере и этот gate **не** срабатывает; `initial_payment > 0` всегда требует `can_read_financial()`. Цены в `list_rental_tariffs` маскируются `can_read_financial()`; сам list — ещё и `member_can_manage_rentals()` (см. ловушку 8 / этап 7 для accountant). Узкие helper-миграции — по той же логике, что этап 1 для `record_rental_payment` (не голый `payments.write`); для admin на backend учитывать org-флаг `admin_can_accept_payments`, как во frontend `can("payments.write")`. Lookup/цены этапа 12 и create этапа 13 — один helper, не два.

Для `restricted_admin` — **строго по политике этапа 12** (если 12 запретил — не расширять; если разрешил прайс/бронь/оплату — расширь gate этапов 1/12 на create, не дублируй UI). На backend уточни gates: ручной `fixed_amount > 0` без `tariff_id` → нужен тот же кассовый helper, что этапы 1/12; путь с `tariff_id` **уже** считает сумму на сервере без `can_read_financial`, но **чтение цены/списка тарифов** (`list_rental_tariffs` маскирует `price`) и `initial_payment > 0` всё ещё за `can_read_financial` — открой их тем же helper, без полного finance. Ручной override — только с правом и пометкой/причиной. Расчёт не копировать по компонентам: общая функция + сверка с сервером при сохранении; показать источник цены и breakdown. Тесты: `npm run test:db:rental-series`, сценарии fixed, (если A) hourly/льготы/полночь, override. Критерий готовности: бронь не уходит с 0 из-за скрытых финполей; цена объяснима; выбранный вариант hourly согласован с UI настроек; reception согласован с этапом 12.

### Этап 14 (P1). Локации, fixed period, архив и фильтры

> Fixed-period venue cost — суммы по локациям при совместимости со старым org-wide (F1/F8 смежно с архивом тарифов). Миграция и расчёт: старые версии дают прежний результат. У тарифов арендаторов: UI архивации через `status`, фильтр active/archived, группировка/фильтр по локации. **Архивация = write тарифов** (owner/director / `canWriteTariffs` после этапа 7), не accountant с read-only. Архив нельзя выбрать для новой брони, история старых аренд сохраняется. Тесты: legacy org-wide, location-specific, архив, историческая ссылка, RBAC архива. Критерий готовности: сеть ведёт суммы по залам без поломки прошлых периодов.

### Этап 18 (P2). Массовое копирование правил

> В per-lesson редакторе: один набор правил на несколько преподавателей и копирование между локациями. Перед сохранением — счётчик создаваемых правил, конфликты, дубли; операция атомарна. «Все текущие преподаватели» = разворот в явные правила, если wildcard запрещён; объясни поведение для будущих педагогов. Тесты: bulk create, rollback при конфликте, копирование. Критерий готовности: матрица на 10 педагогов без ручного копипаста.

Критерий готовности: ambiguous overlap устраняется из UI без правки БД.
